# AGENTS.md

Guidance for AI coding agents working in this repository. Human contributors: see [CONTRIBUTING.md](CONTRIBUTING.md) and [README.md](README.md). The documentation for users and module authors is at [doc.saymyframe.com](https://doc.saymyframe.com).

SMF (Say My Frame) is a Flutter CLI (`smf create`) that generates apps from independent modules (routing, DI, Firebase, features, ...). It is a Dart pub workspace managed by Melos. Every package is versioned and published to pub.dev on its own.

## The module model

- A module declares the roles it provides, requires or uses (router, DI, state management, ...) instead of depending on the modules that implement them. It puts code into typed sockets instead of patching files, and never learns which provider of a role was selected. The model is `package:smf_contracts/smf_contracts.dart`; `package:smf_contracts/core.dart` is its core without concrete roles.
- `packages/smf_pipeline/` is the generation pipeline of `smf create`. It imports only `core.dart` and knows no concrete module or role; `test/architecture_test.dart` checks this.
- The CLI offers the modules listed in `packages/smf_flutter_cli/lib/src/modules.dart`:

  | Package | Module (`-m`) | What it is |
  | --- | --- | --- |
  | `smf_flutter_core` | `flutter_core` | Provides the app entry, which every app has exactly one of (`FlutterCoreModule`, brick `bricks/flutter_core`). |
  | `smf_go_router` | `go_router` | Provides the router role. |
  | `smf_bloc`, `smf_riverpod` | `bloc`, `riverpod` | Provide the state management role; an app has at most one. |
  | `smf_home_flutter` | `home` | The feature `home` (`HomeModule`), the start screen at `/home`; requires the router role. |
  | `smf_bottom_tabs` | `bottom_tabs` | Provides the layout role: tabs in a bar at the bottom for the destinations of the features, which the router builds its main navigation around. The layout requires the router role. |
  | `smf_get_it` | `get_it` | Provides the dependency injection (DI) role and registers in get_it the services that the modules of the app declare. |
  | `smf_event_bus` | `event_bus` | Provides the events role: a service on the event_bus package through which parts of the app that do not know each other exchange events. |
  | `smf_firebase_core` | `firebase_core` | Infrastructure without a role that sets up Firebase; a run in a terminal offers it among the modules of its kind. |
  | `smf_firebase_crashlytics` | `firebase_crashlytics` | Provides the crash reporting role with Firebase Crashlytics (an app can have several providers of it); depends on `smf_firebase_core`. |
  | `smf_firebase_analytics` | `firebase_analytics` | Provides the analytics role with Firebase Analytics (several providers too); depends on `smf_firebase_core` and logs each screen the user sees through a listener of the router. |

- Within `smf_contracts`, `test/architecture_test.dart` keeps the core free of concrete roles. A module package checks in its own `test/architecture_test.dart`, with `ModulePackage` of `package:smf_pipeline/testing.dart`, that its code uses only the module model and the modules it depends on, and what the package depends on. A module package other than `smf_flutter_core` renders the apps of its tests with `smf_flutter_core` as a dev dependency, for their app entry; its `lib/` imports no other module but those it depends on. Dev dependencies between module packages must not form a cycle, because pub.dev resolves them when it analyzes a package: `smf_flutter_core` has none on modules, and of two modules whose tests need each other's role, one tests with a provider of its own in `test/`. `tools/package_graph_test.dart` checks the packages of the workspace for a cycle.

## Layout

```
packages/
  smf_contracts/              # the module model: modules, roles, sockets, contributions
  smf_pipeline/               # the generation pipeline of `smf create` and the contract test harness
    fixture_registry/         # the apps of the fixtures: snapshots, their Flutter matrix with its app tests, and the app of several providers
    test/fixtures/            # fake modules for the features of the model that no real module uses yet
  smf_modules/
    smf_contribution_engine/  # a standalone engine that patches Dart files; no module uses it
    smf_<module>/             # first-party modules: go_router, get_it, firebase_*, event_bus, home, flutter_core, bloc, riverpod, bottom_tabs
  smf_flutter_cli/            # the `smf` binary: the modules it offers, and the terminal, files and processes of the machine
tools/                        # bundle_bricks.dart and sync_cli_version.dart; banlist.dart, coverage_check.dart, test_annotations.dart and workspace_members.dart with their tests; package_graph_test.dart, build_workflow_test.dart, workflow_apps_test.dart, each_app_test.dart, firebase_registration_test.dart, matrix_plan_test.dart, app_tests_test.dart, app_test_imports_test.dart and workspace.dart, which the last two share; the tools read the members of the workspace with workspace_members.dart
```

Dependencies point one way only: `smf_contracts` ← `smf_pipeline` and modules ← `smf_flutter_cli`. Contracts never depend on modules, the pipeline or the CLI; the pipeline never depends on a module. Modules use `smf_pipeline` only in their tests, for the contract harness.

## The core principle: modules are independent

Module independence is the foundation of the project. Never break it, not even to fix a bug quickly.

- A module knows **only** the modules it lists in `ModuleDescriptor.dependsOn`, and only in one direction. For example, `firebase_analytics` depends on `firebase_core`, but `firebase_core` knows nothing about its dependents.
- A module never references another module's generated artifacts (classes, files, packages) unless it declares that dependency, and it should avoid needing to.
- Nothing is hardcoded for a particular combination. Any selection of modules and variants (e.g. state manager `bloc` / `riverpod`) must generate an app that compiles.
- Modules describe *what* they need through the DSLs in `smf_contracts`: routes (`RoutesData` of the router role), DI (`DiRegistration` of the DI role), code for sockets (`SocketContribution`s) and bricks. The router and DI modules turn those descriptions into code. A feature module must not assume a specific router or DI container.
- Generated UI talks only to its state-management layer (a Cubit via `context.read`, a Riverpod provider via `ref`), never directly to a DI container or infrastructure service.
- State-manager variants: a module whose code depends on the state manager declares `Variants` of the state management role in its descriptor, keyed by the id of each provider (`bloc`, `riverpod`), and each variant adds the package of its state manager with the constraint `any`, leaving the version to the provider (see the fixture `fake_feature` in `packages/smf_pipeline/test/fixtures/`).
- The package of a provider of a role, such as `flutter_riverpod` of `riverpod`, goes into another module only through its variant for the provider, with the constraint `any`, or through its `dependsOn` on the provider: the pipeline rejects any other module that adds it in an app with the provider. A module that imports or exports such a package adds it itself, even when it depends on the provider; a provider of a role may import, for a fragment, the package that a module which gives the role data adds.

## Commands

Dart 3.12.2 is pinned in CI (`.github/workflows/build.yml`). The formatter output depends on the SDK version.

```bash
melos bootstrap             # resolve the workspace and re-bundle every brick (needs the Mason CLI: dart pub global activate mason_cli)
melos run format            # format lib/test/bin/tool/app_tests/example of every package, and tools/
melos run analyze           # dart analyze --fatal-infos --fatal-warnings, every package and tools/
melos run banlist           # no file uses the names the module model replaced (tools/banlist.dart)
melos run test              # dart test in every package with a test/ dir, and in tools/
melos run check             # format:check + analyze + banlist + test
melos run test:coverage     # test, and write coverage/lcov.info and a report of the tests in build/test-results/ of each package (needs dart pub global activate coverage)
melos run coverage:check    # after test:coverage: the tests cover every line and branch of lib/ (tools/coverage_check.dart)
```

CI has a job that runs these checks, with coverage for SonarCloud, and jobs with Flutter that generate apps with `smf create --no-input --skip-external-setup --no-dart-fix --strict` and run `flutter analyze` on each: `packages/smf_flutter_cli/tool/matrix.dart` for the modules of the CLI and `packages/smf_pipeline/fixture_registry/tool/matrix.dart` for the fixture modules. Each takes a directory for the apps and needs `flutter` on the `PATH`. Then it copies into each app the tests that apply to it (`MatrixAppTest`), from the `app_tests/` directories of the packages, such as the start-up of Firebase with its platform side mocked, adds the dev dependencies of those tests with `flutter pub add dev:…`, and runs `flutter analyze` and `flutter test`: tests of what only a running app shows, which are not part of the generated apps. A library of the package of each tool registers its tests: `smfAppTests()` of `packages/smf_flutter_cli/lib/matrix_app_tests.dart`, which no other library of the CLI imports, and `fixtureAppTests()` of `packages/smf_pipeline/fixture_registry/lib/matrix_app_tests.dart`. A new `MatrixAppTest` goes there with the apps it `appliesTo`; one that applies to no app fails the run, and `test/matrix_app_tests_test.dart` of its package fails on it without Flutter. In the files of `app_tests/`, `{{app_name}}` becomes the name of the package of the app and `{{<key>}}` a value of `MatrixAppTest.values`; a placeholder that nothing fills fails the run. A value that depends on a choice of a role, such as the route the app starts on, comes from the role through `MatrixApp.hook`, the data and choices of the roles of the app (`routerRole.startIn(routerRole.hookInput(app.hook!))`), not from the modules the app has. A dev dependency from the Flutter SDK takes its descriptor after `@`, as `flutter pub add` reads it: `integration_test@{sdk: flutter}`. With `--add-app-tests`, the directory of an app and the directories of some of its `MatrixAppTest`s, the matrix tool of the CLI adds those tests, their dev dependencies and the configuration of their mocks to an app that `smf create` generated outside the matrix, where only `{{app_name}}` is filled, and runs nothing else. The start check, `packages/smf_flutter_cli/app_tests/start/integration_test/start_check.dart`, is an entry of the app rather than a test: it runs `main()` of the app, waits for the first screen to settle and writes whether the app started and showed it without an error. It knows no module, only `main()` in `lib/main.dart`, which the app entry role puts into every app (`AppEntryRole.mainFile`) whichever module provides it, and a `WidgetsApp` at the root, which `MaterialApp` and `CupertinoApp` build. So the CLI keeps it rather than the provider of the app entry, and a new provider gets it too. The apps of the matrix only analyze it, and CI starts it on a device (see below). It applies to every app, so the matrix runs `flutter test` in each, with the tests that the modules put into the app.

An app test runs in every app with its module, whatever else the app has. A test of a module whose start-up or services reach its platform side declares the mocks of that side, a function in one of its files in `test/` (`MatrixAppTest.mocks`, a `MatrixMocks`). The matrix writes `test/flutter_test_config.dart` into an app with such tests, which sets up the mocks of every test that applies to the app in a `setUpAll` before the tests of each test file, so that the tests of any module may run the start-up of the app. The job `Generated apps (several providers)` runs `packages/smf_pipeline/fixture_registry/tool/several_providers_matrix.dart`, which takes a directory and no names of apps: it checks the one app with every module of the registry of several providers (`severalProvidersModules()`), which has each module of the CLI that provides a role an app can have several providers of, fixture providers of those roles, whose start-up and services go through platform channels that no test of the CLI knows, and a fixture whose start-up waits for a timer. It runs there the app tests of the CLI and of its modules, with the mocks of the fixtures (`severalProvidersAppTests()`), and `fixture_registry/test/fixture_registry_test.dart` fails when the registry misses such a module of the CLI or a fixture provider of such a role. A test that runs `main()` of the app runs it in `tester.runAsync`, so that a start-up that waits for a timer or for I/O does not keep the fake time of the test waiting forever. It fails on an error of `main()`, which `runAsync` would only report to `FlutterError.onError`, and puts back `FlutterError.onError`, `PlatformDispatcher.instance.onError` and `ErrorWidget.builder`, which a start-up may replace, once `main()` returns, as `startApp` of `fixture_registry/app_tests/router_screens/test/screens.dart` does. An app test calls none of the functions of a role that an app can have several providers of, such as `createCrashReporter()`, which reach every provider: what another provider does, only the tests of its own module know. A test of a provider uses the implementation of its own module instead, such as `createCrashlyticsCrashReporter()`, and checks only what reaches its own platform side. Each tool reports with `--app-tests --json` the uses of such functions of the roles of the modules of its matrix in the Dart files of its app tests (`roleFunctionUses` of `appTestsReport`), and `tools/app_tests_test.dart` fails on each use, and when a tool does not report them.

A test of the contract of a role names the role in `MatrixAppTest.roles` and selects its apps by the roles of the app (`app.hook!.presentRoles`), never by the ids of the modules that provide it. The fixture registry keeps the tests of the router role: `router_screens` checks that the router calls the listeners of the screen once for each screen the user sees, its error screen included, gives each navigator observers of its own and closes the route on top with the back button of the system, and `router_fallback` checks the fallback screen of the app entry, which the router shows when no route starts the app. Its `layout_screens`, a test of the router role and of the layout role, checks that every listener hears of each switch between the destinations of the layout, whose branches have observers of their own, and `screen_views` of `smf_firebase_analytics`, which checks the screen that the app logs first, is a test of the router role too. The run fails when such a test applies to no app of a provider of its role, when it selects its apps or takes its values by the id of a provider of its role (`MatrixAppTests.roleProblems`), and when no test of a role of the `testedRoles` of the tool applies to an app of a provider of it: the router role in both tools, and the layout role in that of the fixtures. The tests of the CLI and of the fixture registry pin their `testedRoles` and the roles of those tests. So a new provider of a role gets its tests. A test of what only one provider does names no role and selects the apps of that provider by its id, an exception of `_ofOneProvider` in `tools/app_tests_test.dart`: `go_router_screens`, for the notifications of the delegate of go_router that leave the page on top as it is and for `push()` after a refresh of its routes, and `bottom_tabs_screens`, for a tap on a tab of the bar. The fixture registry has every module of the CLI that provides the router role or the layout role, which `fixture_registry/test/fixture_registry_test.dart` checks, so the tests of the fixtures run with each.

Each directory right in the `app_tests/` of a package is the directory of one `MatrixAppTest`. `tools/app_tests_test.dart` runs each matrix tool once with `--app-tests --json`, which reports its `MatrixAppTest`s (`appTestsReport`), and fails when no tool lists such a directory, when a file lies right in `app_tests/`, and when a tool lists a directory that does not exist or is not one of them. It also fails when an app test that a package of modules keeps applies to an app of the matrix once the modules of that package are taken out of the modules of the app and out of its `everyModuleWith`, or when the matrix of its tool has none of them, so that it runs only in apps with the modules it tests, whichever modules the matrix has today, while the app tests of a package of no module, such as the start check of the CLI, may apply to every app; and when `declaresModule` of `tools/workspace.dart` takes a package in which a tool finds modules for a package of no module. The report also names, for each test, the modules whose ids its tool uses: those whose id, replaced by another in an app of the matrix, changes whether the test applies to the app or the values of its files there. The check fails on the id of a module that the test does not know (`knownModules` of `tools/workspace.dart`: the modules of the package that keeps it and of the packages of modules they depend on, or, for a package of no module such as the fixture registry, the fixture modules among its dependencies), but for the exceptions of `_ofOneProvider`; and when a tool, or the library that registers its tests, imports a package of modules whose app tests it does not register, or another package of the workspace that the check does not list as needed. `tools/app_test_imports_test.dart` fails when a file of `app_tests/` imports a file of the app, as `package:{{app_name}}/<path>` or by a relative path that leads into `lib/` of the app, that no role of `smf_contracts` guarantees (`RoleInterface`), that no brick of the modules of its package, or of the modules they depend on, generates, and that its own directory does not put into `lib/`. So the app tests of a package of no module, such as the start check of the CLI, may import, of the files that modules generate, only those that the roles guarantee, and those of the fixture registry also the files of the fixture modules it depends on. `app_tests/` stays out of the analysis of its package, of its published archive (`.pubignore`) and of SonarCloud, but `melos run format` formats it; give a `testWidgets` there an explicit `timeout`.

The matrix tools take the names of apps after the directory, such as `'go_router with layout'`, and then check only those. The apps with every module, one for each combination of the providers of the roles that take one (`everyModuleAppsOf` of `lib/matrix.dart`), grow with the product of their numbers, so the tools take a pairwise covering of them unless told otherwise: every pair of providers of two such roles that an app can have is in one of the apps of the covering, and so is every module (`EveryModuleCombinations` of `lib/src/matrix_plan.dart`). Options before the directory choose the apps (`MatrixToolOptions`): `--combinations 3-wise` covers every triple instead, and `--combinations all` takes every combination; `--every-module` checks only the apps with every module, and `--app` with the name of one of them, such as `'every module (riverpod)'`, only that one; `--shard <i>/<n>` checks only the i-th of n shares of the apps of a run. With `--plan`, alone or with `--every-combination`, a tool prints instead the plan of the jobs of CI for its apps, as one line of JSON (`matrixPlanOf`): the combinations that the apps with every module of its matrix cover, `pairwise`, or with `--every-combination` `all` up to 100 of them and `3-wise` beyond; the shards of the matrix, one for each 24 apps that its jobs check (`appsPerShard`); and, from the tool of the CLI, the names of the apps with every module that CI generates, one for each job: `apps`, a pairwise covering, which CI builds for Android and iOS and checks on Windows; `start`, a pairwise covering of those without the modules whose steps need an external service, which it starts on devices; and `entries`, one app for each provider of the app entry, the role that owns the Android and Xcode projects, which it archives and configures with Firebase. `tools/matrix_plan_test.dart` checks the plans of both tools. With `--create`, a directory and a name, the tool of the CLI generates in the directory the apps with every module of the covering, or with `--app` the one of that name, without checking them, each named after the providers of the roles that take one other than the first provider of each (`MatrixApp.everyModuleWith`), such as `start_app` and `start_app_riverpod`; a provider of a role that an app can have several providers of, such as crash reporting, which every app with every module has, adds nothing to the name. It passes any further argument to `smf create`, such as `--org`, and exits with 64, generating nothing, when the name starts with `-`, which `smf create` would take for an option. With `--without-external-steps` after `--create`, it leaves out the modules whose steps need an external service (`PostGenStep.external`), those that depend on them and those that are then left without a provider of a role they require, so that the apps start as they are generated. In a directory whose path has letters beyond ASCII, where `flutter analyze` of Flutter 3.44 and 3.47 fails on every system, the matrix tools analyze the apps with `dart analyze --fatal-infos` instead.

In CI, the job `Plan` of `.github/workflows/apps.yml` runs both tools with `--plan`. The jobs of the two matrices take one shard of the plan each, and the jobs that build, archive, start or check an app with every module one app of it each, from the matrix of the job, `${{ fromJSON(needs.plan.outputs.<list>) }}`; every job has a fixed timeout. The workflows never select an app by a name that they write, such as `every module (bloc)`, which names the provider of each role that has several and changes when another role gets a second provider. So a new provider of a role, such as a second app entry, changes the plan rather than the workflows, and more apps make more jobs rather than longer ones, but for the job of the CLI from pub.dev (see below). Each job `Generated apps (<registry>, <i>/<n>)`, of the registry `real` or `fixtures`, checks its shard of the apps of the matrix in a directory with a space in its name, then its shard of the apps with every module in a directory whose name has letters beyond ASCII too. `Android (<app>)` generates its app of `apps` with `--create --app` and builds it with `flutter build apk --debug`. `.github/scripts/each_app.sh` runs a command for each app of a directory, such as the one that `--create --app` generates there, and fails at the end when it failed for any; `tools/each_app_test.dart` tests it. `tools/workflow_apps_test.dart` reads the steps of the workflows, as bash or PowerShell reads them, and the scripts of `.github/scripts`, and fails when one selects an app of a matrix tool by a name it writes, also through a variable that holds the path of the tool; refers by its name to an app of `--create`, in a command or as its working directory; runs `smf create` itself, or names the modules of an app with `-m` or `--modules`; refers to the package of a module outside a step that runs the tests of that module, but for the steps it lists with their reasons; runs a matrix tool for a whole selection of apps in one job (`--create` without `--app`, `--every-module` without `--app` or `--shard`, or the matrix without `--shard`), or with an `--app` or a `--shard` that does not come from the matrix of the job; or computes its `timeout-minutes`. It also fails when a job takes its matrix from the outputs of a job that refers to a secret, which the runner may leave out, and when a job on Linux or macOS generates an app to build without restoring the cache of Gradle or of Swift Package Manager.

`Android start (<app>)` generates its app of `start` with `--create --without-external-steps --app`, adds the start check to it with `--add-app-tests`, and starts it on an Android emulator with `.github/scripts/start_app.sh`, which `iOS start (<app>)` runs on an iOS simulator. The script builds a debug app with the check as its entry (`flutter build apk` or `flutter build ios --simulator`, with `-t`), installs it anew, launches it with `adb` or `xcrun simctl` and reads the line that the check writes to `smf_start_check` in the temporary directory of the app: `passed`, or `failed: ` and the problems. Nothing connects to the app. `flutter test`, which CI ran before, must reach the VM service of the app it installed, and on the emulators and simulators of CI it sometimes never did. So the script makes one try, and prints the log of the app and fails when the check fails, when the app stops before the check writes its result, as in a crash at start-up, and when no result comes in time. `Android with Firebase (<app>)` and `iOS with Firebase (<app>)` generate their app of `entries`, one for each provider of the app entry, add the start check to it and start it the same way, once `test/flutterfire_configure_test.dart` of `smf_firebase_core` configured it, since the placeholder of the options throws at start-up: the test runs the `flutterfire configure` of the README of the app in the Firebase project of CI, `saymyframe-app-cli`, with the key of a service account of the project from the secret `FIREBASE_SERVICE_ACCOUNT`, and skips an app that does not depend on `firebase_core`. The apps have the organization `com.saymyframe.ci` and the name `firebase_start_app` for the first provider of the app entry, and `firebase_start_app_<providers>` for another, after the providers other than the first of their roles; the names stay when another role gets a second provider. So flutterfire finds the Firebase apps that an earlier run registered, and the test fails when the project has more than one app with the id of the app. Only the runs of `build.yml` let flutterfire register a Firebase app that the project does not have yet, through the input `register_firebase_apps` of `apps.yml`, which gives the test `SMF_FIREBASE_REGISTER=1`: the run of the pull request into main that brings a new provider of the app entry registers its apps, one job for each platform. Runs at the same time, such as the jobs of the nightly run, could register an app each, so in any other run the test fails before flutterfire when the project has no app with the id, and `tools/firebase_registration_test.dart` fails when a workflow other than `build.yml` lets it register, or `build.yml` does not. The job `Firebase key` tells the jobs with Firebase whether the secret is there: without it, as in a pull request from a fork, they do not run.

The jobs `macOS` and `Windows` run the tests of every package and of `tools/` on the macOS and Windows runners of GitHub, with the pinned Flutter, 3.44.2, from its release archive; a test of something that only one system does is marked `@TestOn('mac-os')` or `testOn: 'windows'`. On macOS, `iOS (<app>)` generates its app of `apps` with `--create --app` in a directory whose name has a space and letters beyond ASCII, and builds it for the iOS simulator; the jobs of `iOS` and `iOS start` run two at a time, since GitHub runs only a few macOS jobs of a repository at once. `iOS archive (<app>)` generates its app of `entries`, and `test/crashlytics_archive_test.dart` of `smf_firebase_core` archives it with `flutter build ipa --no-codesign`: it adds the build phase for Crashlytics with the Ruby gem xcodeproj, as `flutterfire configure` does on macOS, fixes the phase with the command from the README of the app, and skips an app that does not depend on `firebase_crashlytics`. For iOS, the configuration test of `iOS with Firebase (<app>)` fixes the phase for Crashlytics with the command from the README of the app too, before the app starts on an iPhone simulator. `Windows (<app>)` checks its app of `apps` with `--every-module --app` in a directory with a space in its name and in one whose name has letters beyond ASCII too, and generates it once more as a user does, with the full `dart fix` (`--create --app` with `--dart-fix`), in a directory whose name has letters beyond ASCII, to analyze and test it. SMF generates the apps in `%TEMP%` and moves them to another drive. The job `Windows` also finds the FlutterFire CLI through `dart.bat`, with `smf create --explain` for each app of `entries`. A job of `build.yml`, `Firebase CLI install (Windows)`, runs the install script of the Firebase CLI on Windows for real.

The jobs with Flutter are in the reusable workflow `.github/workflows/apps.yml`, which takes the version of Flutter, the version of its Dart and the SHA-256 of its archive for each system. `build.yml` runs them with the pinned Flutter on pushes to main, on pull requests into main and when someone starts it by hand on any branch. A pull request into another branch, such as one that collects the pull requests of a larger change, runs only the job of the checks; the jobs with Flutter run later, in the pull request of that branch into main. `nightly.yml` runs them every night, and when someone starts it by hand, with every stable release of Flutter that the generated apps allow. `packages/smf_flutter_cli/tool/flutter_versions.dart` finds those releases: it intersects the Flutter and Dart constraints of the apps of the matrix of the CLI, which the pipeline merges from the `PubspecContribution.environment`s of their modules, and takes the releases from the lists that Flutter publishes for Linux, macOS and Windows. The jobs on Linux run with each of them, and the jobs on macOS and Windows with the oldest and with the latest patch of each minor version. With the latest release, the jobs of the matrices check every combination of the providers, or a 3-wise covering of more than 100 (the input `every_combination`), in more shards, while the apps that CI builds and starts stay the pairwise coverings. The nightly run skips the jobs without Flutter, and the comparison of the brick of `flutter_core` with `flutter create`, since the brick follows the template of the pinned Flutter. It also checks what users install: the job `CLI from pub.dev` of each version activates `smf_flutter_cli` from pub.dev with `dart pub global activate`, which resolves its dependencies from pub.dev rather than from the workspace, generates with it the apps with every module of that release, one for each combination of the providers of the roles that take one, with the full `dart fix`, and runs `flutter analyze`, `flutter test` and `flutter build apk --debug` in each. The CLI on pub.dev has the modules of its release, which may differ from those of the workspace, so `packages/smf_flutter_cli/tool/every_module_apps.dart`, run in a package of its own that depends on the active version, prints the arguments of `smf create` of those apps from `matrixOf` of the release, and the workflow names no module there either. A release without the plan of CI cannot cover them, so this job alone checks its apps one after another. A failure there affects the users of the published version, and its fix needs a release. What Gradle downloads for the Android builds goes into one cache for every version of Flutter, by the Android files of the bricks of the modules and the week, since Maven Central answers 403 to a runner that downloads too much, and what Swift Package Manager downloads for the iOS builds, `~/Library/Caches/org.swift.swiftpm`, goes into one by the week. Every job that builds for Android or iOS restores the newest one of its platform, and `Android` and `iOS` of the first app of the plan save them, in the runs of `build.yml` and, in the nightly run, only with the latest Flutter (the inputs `save_gradle_cache` and `save_swiftpm_cache`), so they get new versions of plugins within a week even without pushes.

The job `CI` of `build.yml` sums up the other jobs of the workflow: it needs all of them and fails when one of them failed or was cancelled. A skipped job counts as passed only in a pull request into a branch other than main, which skips the jobs with Flutter. Every other run runs every job, so there `CI` fails on a skipped job too, and a mistake in the condition of the jobs with Flutter cannot let a pull request into main pass without them. The ruleset of main requires the checks `CI` and `PR title`, so the ruleset does not have to change when jobs come and go. A job added to `build.yml` goes into the `needs` of `CI` too. `tools/build_workflow_test.dart` fails when one is missing there, and when `CI` lacks `if: ${{ !cancelled() }}`, without which a failed job would skip `CI` and a ruleset would take the skipped check as passed. A new run of `build.yml` cancels the run of its concurrency group that is still in progress: `build-<number of the pull request>` for a pull request, and `build-<ref>` otherwise. `.github/workflows/cancel.yml` runs when a pull request is closed and joins the group of the pull request with `cancel-in-progress`, so the run of Build of a merged or closed pull request stops; `tools/build_workflow_test.dart` fails when no workflow does so.

When a test of a package or of `tools/` fails in CI, the page of the run lists it at the top as an annotation, with the name of the test, its message, and its file and line. Every `dart test` in the workflows writes a JSON report with `--file-reporter json:build/test-results/<name>.json` in the directory it runs in, under a name that no other run in its job uses. `.github/scripts/each_app.sh` gives the report of the command it runs for each app the name of the app, `<name>.<app>.json`, so that the run for the next app does not replace it. The last step of each job with tests runs `dart tools/test_annotations.dart` whenever Dart is set up, even after a failed step or in a cancelled job. It turns each test in those reports that failed, or that started and never finished, into an annotation. `tools/test_annotations_test.dart` fails when a run of tests in a workflow writes no report or the same report as another run in its job, and when a job with tests does not run the tool after them.

Run the CLI from source. It finds the Flutter SDK through `flutter` on the `PATH` before it generates anything, and runs `flutter pub get`, `dart fix` and `dart format` in the new app:

```bash
cd packages/smf_flutter_cli
dart run bin/smf_flutter.dart create my_app -o /tmp/out --org com.example --no-input --on-conflict replace
```

Modules are chosen with `-m`, and every option of `create` comes from the command line with `--no-input`. `--explain` prints what would be generated and whether the machine is ready, without changing anything.

## Generated files and templates

- `lib/bundles/*_bundle.dart` are generated from `bricks/` by `tools/bundle_bricks.dart`, which `melos bootstrap` runs. Never edit them by hand. Change the brick, re-bundle and commit the result. CI fails if a committed bundle differs from what the bricks produce.
- `bricks/**/__brick__/**` holds mason templates, not Dart. They are excluded from analysis and formatting. They use mason syntax: `{{app_name.snakeCase()}}`.
- Bricks have no mason hooks. The pipeline rejects a brick with hooks and runs none: modules check the machine and run tools through `Preflight` and `PostGenStep` contributions.
- The snapshots in `packages/smf_flutter_cli/test/snapshots/` and `packages/smf_pipeline/fixture_registry/test/snapshots/` hold the files of the apps the CLI and the fixtures render. When a change alters them, update them with `SMF_UPDATE_SNAPSHOTS=1 dart test test/snapshot_test.dart` in the package and review the diff.
- `smf_firebase_core` generates `lib/firebase_options.dart` as a placeholder in the form that `flutterfire configure` writes, which throws an `UnsupportedError` until the FlutterFire CLI fills it in, and initializes Firebase with it in `bootstrap()`. Its preflight checks look for the Firebase CLI, a Firebase login, the FlutterFire CLI and, on macOS, the Ruby gem xcodeproj; elsewhere a check tells that the Xcode project is set up on a Mac. They only warn: a run in a terminal offers to set up what it can, asking first. After generation it runs `flutterfire configure` in the terminal with the ids of the app; that needs a Firebase account, so a run with `--no-input` or `--skip-external-setup` generates the app with the placeholder and prints the command to run later. A follow-up of that step (`PostGenStep.followUps`), which runs only after it and only on macOS, points the build phase for Crashlytics that flutterfire adds at the upload script in `build/ios/SourcePackages`, which `flutter build ipa` needs.

## Tests

- Tests live in each package's `test/`. Sonar counts coverage only within the package that runs the tests, so a module's code needs tests in that module.
- Keep coverage at 100% of the lines and branches of `lib/` with tests that pin behavior someone relies on, never with tests that only touch a line. Remove code that cannot run instead of covering it. Code that no automated test can run, such as the terminal of a user, goes between `// coverage:ignore-start` and `// coverage:ignore-end`, with the reason in a comment next to it. Don't use `coverage:ignore-file`: the file then drops out of `lcov.info` and Sonar counts all of it as uncovered. `melos run test:coverage` measures branches as well as lines, and `melos run coverage:check` after it fails on any line or branch of `lib/` that the tests do not cover, with its `path:line`. CI runs both.
- The contract harness of `package:smf_pipeline/testing.dart` checks a module against the rules of the roles it declares and renders every app it can be part of. `packages/smf_flutter_cli/test/modules_test.dart` runs it over every module the CLI offers, and a module package runs it over itself in its own tests. New modules must pass it.
- For each package of a provider of a role that a module adds, the harness builds a case of the module with that provider, `<module> with <provider>` or `<module> (<provider of its variant>) with <provider>`, when they can be in one app. So the registry of a module's tests holds the providers of the roles it requires or uses, the providers it has variants for, and the providers whose packages it adds.
- Generator tests check generated code for real: they parse it or type-check it with the analyzer, not just string-match.
- Tests are hermetic: no network, no Flutter SDK, temp dirs cleaned up. The few that need more skip themselves unless CI provides it: an app from `flutter create` (`SMF_FLUTTER_CREATE_APP`), an app with Crashlytics to archive on macOS (`SMF_CRASHLYTICS_APP`), an app with Firebase to configure with flutterfire for a platform in a Firebase project, with the key of a service account of the project (`SMF_FIREBASE_APP`, `SMF_FIREBASE_PLATFORM`, `SMF_FIREBASE_PROJECT`, `SMF_FIREBASE_SERVICE_ACCOUNT`, and `SMF_FIREBASE_REGISTER=1` to let flutterfire register the app in the project when the project has none with its id), or a machine where the Firebase CLI may be installed (`SMF_INSTALL_FIREBASE_CLI=1`).
- A bug found but not fixed gets a test for the *correct* behavior, marked `skip: 'Bug: <description>'`. Never write a test that locks buggy behavior in. The fix removes the `skip`.

## Git and PRs

- Use [Conventional Commits](https://www.conventionalcommits.org/) with the package's short name as scope: `fix(go_router): ...`, `feat(contracts): ...`, `test(cli): ...`, `chore(ci): ...`. `melos version` derives version bumps and CHANGELOGs from them.
- Name branches `fix/<topic>`, `feat/<topic>`, `chore/<topic>`, `docs/<topic>`, `test/<topic>`.
- A PR is squash-merged: the squash commit takes the title of the PR as its only line, so the title must be a Conventional Commit too, and CI checks the title of every PR (`.github/workflows/pr-title.yml`). A breaking change needs `!` in the title, such as `feat(contracts)!: ...`: a `BREAKING CHANGE:` footer in a commit of the branch does not reach main.
- A larger change may collect its PRs in a branch of its own. The PR of that branch into main is merged with a merge commit rather than squashed, so that each commit of the branch, such as the squash commit of each of its PRs, reaches main as it is, and `melos version` reads each on its own. So the `!` of a breaking change goes into the title of the PR into that branch that makes the change.
- Once a branch is pushed, add new commits on top. Don't force-push or rewrite pushed history unless a maintainer asks.
- Don't bump package versions or edit CHANGELOGs by hand. `melos version` does both, and its preCommit hook syncs `packages/smf_flutter_cli/lib/version.dart`.
- Keep PRs focused: one concern per PR, one logical change per commit.
