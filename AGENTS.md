# AGENTS.md

Guidance for AI coding agents working in this repository. Human contributors: see [CONTRIBUTING.md](CONTRIBUTING.md) and [README.md](README.md). The documentation for users and module authors is at [doc.saymyframe.com](https://doc.saymyframe.com).

SMF (Say My Frame) is a Flutter CLI (`smf create`) that generates apps from independent modules (routing, DI, Firebase, features, ...). It is a Dart pub workspace managed by Melos. Every package is versioned and published to pub.dev on its own.

## The module model

- A module declares the roles it provides, requires or uses (router, DI, state management, ...) instead of depending on the modules that implement them. It puts code into typed sockets instead of patching files, and never learns which provider of a role was selected. The model is `package:smf_contracts/smf_contracts.dart`; `package:smf_contracts/core.dart` is its core without concrete roles.
- `packages/smf_pipeline/` is the generation pipeline of `smf create`. It imports only `core.dart` and knows no concrete module or role; `test/architecture_test.dart` checks this.
- The CLI offers the modules listed in `packages/smf_flutter_cli/lib/src/modules.dart`:

  | Package | Module (`-m`) | What it is |
  | --- | --- | --- |
  | `smf_flutter_core` | `flutter_core` | Provides the app entry, which every app has exactly one of (`FlutterCoreModule`, brick `bricks/flutter_core`). |
  | `smf_go_router` | `go_router` | Provides the router role. |
  | `smf_bloc`, `smf_riverpod` | `bloc`, `riverpod` | Provide the state management role; an app has at most one. |
  | `smf_home_flutter` | `home` | The feature `home` (`HomeModule`), the start screen at `/home`; requires the router role. |
  | `smf_bottom_tabs` | `bottom_tabs` | Provides the layout role: tabs in a bar at the bottom for the destinations of the features, which the router builds its main navigation around. The layout requires the router role. |
  | `smf_get_it` | `get_it` | Provides the dependency injection (DI) role and registers in get_it the services that the modules of the app declare. |
  | `smf_event_bus` | `event_bus` | Provides the events role: a service on the event_bus package through which parts of the app that do not know each other exchange events. |
  | `smf_firebase_core` | `firebase_core` | Infrastructure without a role that sets up Firebase; a run in a terminal offers it among the modules of its kind. |
  | `smf_firebase_crashlytics` | `firebase_crashlytics` | Provides the crash reporting role with Firebase Crashlytics (an app can have several providers of it); depends on `smf_firebase_core`. |
  | `smf_firebase_analytics` | `firebase_analytics` | Provides the analytics role with Firebase Analytics (several providers too); depends on `smf_firebase_core` and logs each screen the user sees through a listener of the router. |

- Within `smf_contracts`, `test/architecture_test.dart` keeps the core free of concrete roles. A module package checks in its own `test/architecture_test.dart`, with `ModulePackage` of `package:smf_pipeline/testing.dart`, that its code uses only the module model and the modules it depends on, and what the package depends on. `roleClassNameProblems` of the same library checks that the code in `lib/` of a package and of the module packages it depends on takes the name of each class that a role requires from the role, such as `LayoutRole.appShell.name`, rather than spelling it out in a string; `test/role_class_names_test.dart` of `smf_flutter_cli` and of `fixture_registry` runs it. A module package other than `smf_flutter_core` renders the apps of its tests with `smf_flutter_core` as a dev dependency, for their app entry; its `lib/` imports no other module but those it depends on. Nor does a module package name the modules that depend on it: `packages/smf_flutter_cli/test/modules_test.dart` fails when the `lib/` of a module package, but its bundles, or its `bricks/`, `example/` or `README.md` has a word of the id of such a module that the id of the module of the package lacks, whatever its case and also inside a camelCase name, such as `crashlytics` in `smf_firebase_core`. Dev dependencies between module packages must not form a cycle, because pub.dev resolves them when it analyzes a package: `smf_flutter_core` has none on modules, and of two modules whose tests need each other's role, one tests with a provider of its own in `test/`. `tools/package_graph_test.dart` checks the packages of the workspace for a cycle.

## Layout

```
packages/
  smf_contracts/              # the module model: modules, roles, sockets, contributions
  smf_pipeline/               # the generation pipeline of `smf create` and the contract test harness
    fixture_registry/         # the apps of the fixtures: snapshots, their Flutter matrix with its app tests, the app of several providers, and the apps of the broken providers
    test/fixtures/            # fake modules for the features of the model that no real module uses yet, and providers of roles with a known bug
  smf_modules/
    smf_contribution_engine/  # a standalone engine that patches Dart files; no module uses it
    smf_<module>/             # first-party modules: go_router, get_it, firebase_*, event_bus, home, flutter_core, bloc, riverpod, bottom_tabs
  smf_flutter_cli/            # the `smf` binary: the modules it offers, and the terminal, files and processes of the machine
tools/                        # bundle_bricks.dart and sync_cli_version.dart; banlist.dart, coverage_check.dart, native_build.dart, test_annotations.dart and workspace_members.dart with their tests; package_graph_test.dart, build_workflow_test.dart, workflow_apps_test.dart, each_app_test.dart, start_app_test.dart, firebase_registration_test.dart, flutterfire_version_test.dart, sonar_lcov_test.dart, matrix_plan_test.dart, app_tests_test.dart, app_test_imports_test.dart and workspace.dart, which the last two share; the tools read the members of the workspace with workspace_members.dart, the only file that reads them from the root pubspec, as banlist.dart checks
```

Dependencies point one way only: `smf_contracts` ← `smf_pipeline` and modules ← `smf_flutter_cli`. Contracts never depend on modules, the pipeline or the CLI; the pipeline never depends on a module. Modules use `smf_pipeline` only in their tests, for the contract harness.

## The core principle: modules are independent

Module independence is the foundation of the project. Never break it, not even to fix a bug quickly.

- A module knows **only** the modules it lists in `ModuleDescriptor.dependsOn`, and only in one direction. For example, `firebase_analytics` depends on `firebase_core`, but `firebase_core` knows nothing about its dependents.
- A module never references another module's generated artifacts (classes, files, packages) unless it declares that dependency, and it should avoid needing to.
- Nothing is hardcoded for a particular combination. Any selection of modules and variants (e.g. state manager `bloc` / `riverpod`) must generate an app that compiles.
- Modules describe *what* they need through the DSLs in `smf_contracts`: routes (`RoutesData` of the router role), DI (`DiRegistration` of the DI role), code for sockets (`SocketContribution`s) and bricks. The router and DI modules turn those descriptions into code, and the contract harness checks that the files of the provider of the DI role call or tear off the factory of every registration and its dispose function (the rule `di.registrations_rendered` of the role). A feature module must not assume a specific router or DI container, and neither do its tests. They check what the module gives a role through the data of the role, which the role reads from `ContractResult.hook`, the hook request of the app of a case of the harness, with functions such as `diRole.graphOf(diRole.hookInput(result.hook!))`, `routerRole.startIn` and `layoutRole.destinationsIn`, and through what each socket got, in the order the pipeline rendered it, with the fragments of the render hooks of the roles (`RenderedApp.socketOrders`). They tell the files that a provider changed by their owner, and never read `RouterRole.appRouterFactoryFile`, `DiRole.dependenciesFile` or `LayoutRole.appShellFile`, in which the providers of those roles render what the modules give them, nor `AppEntryRole.bootstrapFile`, `AppEntryRole.mainFile` and `lib/app.dart`, into which the provider of the app entry renders the start-up and the root of the app. Only the package of the provider tests those files. `tools/banlist.dart` bans their constants and paths in the tests of the module packages, except as the key of a map, for the files of a provider that a test defines, and in the tests of the package that provides each.
- Generated UI talks only to its state-management layer (a Cubit via `context.read`, a Riverpod provider via `ref`), never directly to a DI container or infrastructure service.
- State-manager variants: a module whose code depends on the state manager declares `Variants` of the state management role in its descriptor, keyed by the id of each provider (`bloc`, `riverpod`), and each variant adds the package of its state manager with the constraint `any`, leaving the version to the provider (see the fixture `fake_feature` in `packages/smf_pipeline/test/fixtures/`).
- The package of a provider of a role, such as `flutter_riverpod` of `riverpod`, goes into another module only through its variant for the provider, with the constraint `any`, or through its `dependsOn` on the provider: the pipeline rejects any other module that adds it in an app with the provider. A module that imports or exports such a package adds it itself, even when it depends on the provider; a provider of a role may import, for a fragment or in a file that its render hook generates, the package that a module which gives the role data adds.

## Commands

Dart 3.12.2 is pinned in CI (`.github/workflows/build.yml`). The formatter output depends on the SDK version.

```bash
melos bootstrap             # resolve the workspace and re-bundle every brick (needs the Mason CLI: dart pub global activate mason_cli)
melos run format            # format lib/test/bin/tool/app_tests/example of every package, and tools/
melos run analyze           # dart analyze --fatal-infos --fatal-warnings, every package and tools/
melos run banlist           # no file uses a name that the repository bans, such as one the module model replaced (tools/banlist.dart)
melos run test              # dart test in every package with a test/ dir, and in tools/
melos run check             # format:check + analyze + banlist + test
melos run test:coverage     # test, and write coverage/lcov.info and a report of the tests in build/test-results/ of each package (needs dart pub global activate coverage)
melos run coverage:check    # after test:coverage: the tests cover every line and branch of lib/ (tools/coverage_check.dart)
```

CI has a job that runs these checks, with coverage for SonarCloud, and jobs with Flutter that generate apps with `smf create --no-input --skip-external-setup --no-dart-fix --strict` and run `flutter analyze` on each: `packages/smf_flutter_cli/tool/matrix.dart` for the modules of the CLI and `packages/smf_pipeline/fixture_registry/tool/matrix.dart` for the fixture modules. Each takes a directory for the apps and needs `flutter` on the `PATH`. Then it copies into each app the tests that apply to it (`MatrixAppTest`), from the `app_tests/` directories of the packages, such as the start-up of Firebase with its platform side mocked, adds the dev dependencies of those tests with `flutter pub add dev:…`, and runs `flutter analyze` and `flutter test`: tests of what only a running app shows, which are not part of the generated apps. A library of the package of each tool registers its tests: `smfAppTests()` of `packages/smf_flutter_cli/lib/matrix_app_tests.dart`, which no other library of the CLI imports, and `fixtureAppTests()` of `packages/smf_pipeline/fixture_registry/lib/matrix_app_tests.dart`. A new `MatrixAppTest` goes there with the apps it `appliesTo`; one that applies to no app fails the run, and `test/matrix_app_tests_test.dart` of its package fails on it without Flutter. In the files of `app_tests/`, `{{app_name}}` becomes the name of the package of the app and `{{<key>}}` a value of `MatrixAppTest.values`; a placeholder that nothing fills fails the run. A value that depends on a choice of a role, such as the route the app starts on, comes from the role through `MatrixApp.hook`, the data and choices of the roles of the app (`routerRole.startIn(routerRole.hookInput(app.hook!))`), not from the modules the app has, as the tests of a module read it from `ContractResult.hook` of a case of the contract harness. A test that needs to know more of what the modules of the app give a role, such as the services that they register, gets Dart files for the app (`MatrixAppTest.generatedFiles`): the library that registers the test writes them from `MatrixApp.hook`, each by its path in the app, such as `integration_test/di_role/registered_services.dart` from `diRole.graphOf(diRole.hookInput(app.hook!))`. The matrix writes them next to the files of the test as they are, with no placeholder filled, and the run fails on a generated file at the path of another file of the tests of the app, or at a path that is not a plain relative path in the app, such as one with `..`. A dev dependency from the Flutter SDK takes its descriptor after `@`, as `flutter pub add` reads it: `integration_test@{sdk: flutter}`. With `--add-app-tests`, the directory of an app and the directories of some of its `MatrixAppTest`s, the matrix tool of the CLI adds those tests, their dev dependencies and the configuration of their mocks to an app that `smf create` generated outside the matrix, where only `{{app_name}}` is filled, and runs nothing else. With `--app` and the name of an app with every module, and with `--without-external-steps` when `--create` had it, the tool adds the tests to the app that `--create --app` generated as that app: `addAppTestsTo` gets that app of the matrix (`app`), fills the values of the tests and writes the files that they generate. With the start check among the tests, the tool also adds each other test with a probe that applies to the app (`appTestsFor`), and it fails on a named test that does not apply to the app. Without `--app`, a test that generates files fails, since the files come from the roles of an app of the matrix. The start check, `packages/smf_flutter_cli/app_tests/start/integration_test/start_check.dart`, is an entry of the app rather than a test: it runs `main()` of the app, waits for the first screen to settle and writes whether the app started and showed it without an error. It knows no module, only `main()` in `lib/main.dart`, which the app entry role puts into every app (`AppEntryRole.mainFile`) whichever module provides it, and a `WidgetsApp` at the root, which `MaterialApp` and `CupertinoApp` build. So the CLI keeps it rather than the provider of the app entry, and a new provider gets it too. Once the first screen settled, the check runs the probes of the tests that went into the app with it, one after another and for at most 60 s in all, and adds their problems to its line, each after the name of its test. A test declares its probe in `MatrixAppTest.startProbe` (`MatrixStartProbe`): a function in its `integration_test/`, of the type `Future<List<String>> Function(Future<void> Function() settle)`, that goes through the running app without a test framework and returns what is wrong. The matrix writes the list of the probes of the tests of the app, `integration_test/start_probes.dart` (`startProbesFile`), into an app with a test that runs them (`MatrixAppTest.readsStartProbes`), as the start check does, so the check knows no probe either. It prints the probes that it ran, with the time of each, to the log of the device. The apps of the matrix only analyze it, and CI starts it on a device (see below). It applies to every app, so the matrix runs `flutter test` in each, with the tests that the modules put into the app.

An app test of a module runs in every app with its module, whatever else the app has. A test of a module whose start-up or services reach its platform side declares the mocks of that side, a function in one of its files in `test/` (`MatrixAppTest.mocks`, a `MatrixMocks`). The matrix writes `test/flutter_test_config.dart` into an app with such tests, which sets up the mocks of every test that applies to the app in a `setUpAll` before the tests of each test file, so that the tests of any module may run the start-up of the app. The job `Generated apps (several providers)` runs `packages/smf_pipeline/fixture_registry/tool/several_providers_matrix.dart`, which takes a directory and no names of apps: it checks the one app with every module of the registry of several providers (`severalProvidersModules()`). That app has each module of the CLI that provides a role an app can have several providers of; fixture providers of those roles, which start asynchronously and whose start-up and services go through platform channels that no test of the CLI knows; `fake_service_log`, a fixture that provides both roles with services created synchronously, which note each call that reaches them; a fixture whose start-up waits for a timer; and `get_it` and `fake_events`, for the tests of the DI role and of the events role that the CLI keeps. The tool runs there the app tests of the CLI and of its modules, with the mocks of the fixtures, and the tests of the analytics role and of the crash reporting role (`severalProvidersAppTests()`, see below). `fixture_registry/test/fixture_registry_test.dart` fails when the registry misses such a module of the CLI, a fixture provider of such a role or the service log, and `fixture_registry/test/matrix_app_tests_test.dart` fails when a test of `severalProvidersAppTests()` does not apply to the app. A test that runs `main()` of the app runs it in `tester.runAsync`, so that a start-up that waits for a timer or for I/O does not keep the fake time of the test waiting forever. It fails on an error of `main()`, which `runAsync` would only report to `FlutterError.onError`, and puts back `FlutterError.onError`, `PlatformDispatcher.instance.onError` and `ErrorWidget.builder`, which a start-up may replace, once `main()` returns, as `startApp` of `fixture_registry/app_tests/router_screens/test/screens.dart` does. An app test of a module calls none of the functions of a role that an app can have several providers of, such as `createCrashReporter()`, which reach every provider: what another provider does, only the tests of its own module know. A test of a provider uses the implementation of its own module instead, such as `createCrashlyticsCrashReporter()`, and checks only what reaches its own platform side. Only a test of the contract of such a role calls those functions, since what the role does with every provider is its contract: it names the role in `MatrixAppTest.roles`, a package of no module keeps it, such as the fixture registry, and it looks only at what reaches the providers that its package knows. Each tool reports with `--app-tests --json` the roles of each of its app tests and the uses of such functions of the roles of the modules of its matrix in the Dart files of the test, each with the role of the function (`roles` and `roleFunctionUses` of `appTestsReport`). `tools/app_tests_test.dart` fails on each use but those in a test of the role of the function that a package of no module keeps, and when a tool does not report the uses.

A test of the contract of a role names the role in `MatrixAppTest.roles` and selects its apps by the roles of the app (`app.hook!.presentRoles`), never by the ids of the modules that provide it. The fixture registry keeps most tests of the router role. `router_screens` checks that the router calls the listeners of the screen once for each screen the user sees, its error screen included, gives each navigator observers of its own, closes the route on top with the back button of the system and creates its configuration once (`router_config_test.dart`). `router_listeners` checks, in the apps with the listeners of the screen of the fixture analytics and of the fixture screen log, that the router calls each listener on its own, as `RouterRole.screenListeners` asks, so that one that throws keeps no other from hearing the screen and what it throws reaches no handler of the errors of the app. `router_fallback` checks the fallback screen of the app entry, which the router shows when no route starts the app. The `layout_screens` of the fixture registry, a test of the router role and of the layout role, checks that every listener hears of each switch between the destinations of the layout, whose branches have observers of their own, and that `push()` or `replace()` of a location in the main navigation from a page shown over it throws a `StateError` that leaves the stack and the listeners as they are (`main_navigation_test.dart`). `screen_views` of `smf_firebase_analytics`, which checks the screen that the app logs first, is a test of the router role too, and so is `router_walk` of the CLI (`routerWalkAppTest()`). For it the matrix writes into the app `integration_test/router_walk/locations.dart`, the locations of the routes of `routerRole.facadeOf` that need no values, the first 20 at most (`routerWalkLimit`). The test starts the app with `main()`, and `walkRoutes()` of `walk.dart`, in the same directory, goes to each location with `go()` of `appRouter.navigatorOf()`: the page on top of the innermost navigator on the screen must be named after the route, the screen of the route must be shown, and no `ErrorWidget` and no error of Flutter may appear. The walk uses no test framework, so the start check runs it on a device too: `probeRoutes()` of `walk.dart` is the probe of the test.

The CLI keeps the tests of the DI role and of the events role. For `di_role` (`diRoleAppTest()`), the matrix writes the services of an app whose modules register some into `integration_test/di_role/registered_services.dart`, from `diRole.graphOf`. Once `bootstrap()` ran, every service must resolve, a singleton or a lazy singleton to the same instance each time; once `resetDependencies()` ran, none may; and once `registerDependencies()` ran again, all must. The test checks the services with `problemsOfResolving()` of `integration_test/di_role/probe.dart`, which the probe of the test in the same file, `probeServices()`, runs on a device for the start check. It resolves each service once, and a singleton or a lazy singleton a second time to compare the instances, but calls none of them, since on a device the apps with Firebase use a real project. The DI role requires `resetDependencies()` of its provider in `lib/core/di/dependencies.dart` (`DiRole.resetDependencies`): it disposes of the services that the container created, with the dispose function of each registration, in the reverse order of the registrations, creates no service only to dispose of it, and removes every service, so that `registerDependencies()` can run again. `get_it` does so by resetting its container. The fixture registry keeps `di_disposal`, a test of the DI role too, for the apps with `fake_registrations`, whose services note what their dispose functions do: it checks that order there, and that a lazy singleton that nothing resolved is neither created nor disposed of. `events_role` (`eventsRoleAppTest()`) fires events of its own through `createCommunicationService()`: every listener of a type gets each event of that type once, in the order the events were fired; a listener of another type gets none of them and no error; a cancelled subscription gets no more events; and the stream of `on<T>()` has only the events fired after it is listened to, not one fired before, even after `on<T>()` returned the stream, as the events role says. Whether a listener of a type that an event extends or implements gets the event is up to the provider, so the test does not look. The matrix of the fixtures runs `events_role` and `router_walk` only in its apps with every module, which run `flutter test` for other tests already, and `di_role` only in its apps whose services have every lifetime.

The service of a role that an app can have several providers of, `createAnalyticsService()` of the analytics role or `createCrashReporter()` of the crash reporting role, calls each provider on its own. A provider that throws, or whose future fails, keeps no other from the call, and its failure does not reach the code that called, which may not await the call. The failure of a crash reporter does not reach the handlers of the errors either, which would report it to the same crash reporter again, without end. Each analytics service gets a copy of its own of the parameters of a call. A provider whose factory throws, or whose asynchronous start fails, is left out, so that the app starts and works with the others. In debug mode, the app prints each such failure (`RoleImplementation`, `AnalyticsRole` and `CrashReportingRole`). The fixture registry keeps the tests of these roles, `analytics_role` and `crash_reporting_role`, which `severalProvidersAppTests()` registers for the app with every module of its registry. They call those functions, and look only at what reaches the fixture providers of the roles: `fake_service_log`, which notes each call, and which a test can make throw, fail, throw from its factories, or change the parameters that its analytics service gets; and the platform side of the other fixture providers.

The run fails when a test of a role applies to no app of a provider of its role, when it selects its apps, takes its values or generates its files by the id of a provider of its role (`MatrixAppTests.roleProblems`), and when no test of a role of the `testedRoles` of the tool applies to an app of a provider of it. Those are the router role, the DI role and the events role in the tools of the CLI and of the fixtures, the layout role in that of the fixtures too, and the analytics role and the crash reporting role in that of several providers. The tests of `smfAppTests()`, `fixtureAppTests()` and `severalProvidersAppTests()` pin their `testedRoles` and the roles of their tests. So a new provider of a role gets its tests. A test of what only one provider does names no role and selects the apps of that provider by its id, an exception of `_ofOneProvider` in `tools/app_tests_test.dart`: `go_router_screens`, for the notifications of the delegate of go_router that leave the page on top as it is and for `push()` after a refresh of its routes, and `bottom_tabs_screens`, for a tap on a tab of the bar. The fixture registry has every module of the CLI that provides the router role or the layout role, which `fixture_registry/test/fixture_registry_test.dart` checks, so the tests of the fixtures run with each.

A test of a role that passes whatever the provider of the role does checks nothing. So the fixture package `fake_broken` has providers of roles with one known bug each, which keep every rule of their roles that the contract harness checks, so that only a running app shows the bug: `BrokenModule`, a fixture module under an id of its own with a change of the code that it renders, which brings in the bug, such as a fake router that calls the listeners of the screen one after another; `BrokenDiModule`, the fake DI container with the registration of one service in a condition that is false when the app runs; and `BrokenLayoutModule`, a layout of its own. `brokenProviders()` of `packages/smf_pipeline/fixture_registry/lib/broken_providers.dart` gives each its role, its bug, the other modules of its app, only those that the tests of the app need, and the tests that must fail on the bug, each a `MatrixExpectedFailure` with the path of its test file in the app, its full name and a reason. The job `Generated apps (broken providers)` runs `fixture_registry/tool/broken_providers_matrix.dart`, which takes a directory and generates there the app of each broken provider, the app with every module of its small registry (`MatrixFailingApp`). It adds to the app the tests of the apps of the fixtures and of the app of several providers that apply to it (`brokenProviderAppTests()`), and runs `flutter test --reporter json` once the app with them passes `flutter analyze` (`runFailingApps` of `packages/smf_flutter_cli/lib/matrix.dart`). Each test that must fail has to fail first on a failed expectation whose message contains its reason, such as the `reason:` of the expectation that the bug breaks, and every other test has to pass, but for a test that its declaration skips (`expectedFailureProblems`, in `lib/src/expected_failures.dart` of the same package). In a widget test, flutter_test reports a failed expectation as an error that refers to what it printed before, so there the first failure is the first thing that it printed as thrown. The job runs in Build, and in the nightly run only with the latest Flutter (the input `broken_providers` of `apps.yml`). `fixture_registry/test/broken_providers_test.dart` fails, without Flutter, on a broken provider that breaks a rule of its role that the harness checks; whose app the harness renders with errors; whose expected failure names a test file that the tests of its app do not have once, a test that the file does not declare, or a reason that neither the file nor a file of its tests that it imports by a relative path writes, such as `probe.dart` of `di_role`, with names and reasons read as templates of the values they interpolate; that is in a registry of apps that must work; or whose app lacks a file of the app that one of its tests imports. It also fails on a role whose contract the app tests check with neither a broken provider nor an exemption with its reason in `brokenProviderExemptions`, which is empty, and on an exemption of a role that the app tests do not check or that has a broken provider.

Each directory right in the `app_tests/` of a package is the directory of one `MatrixAppTest`. `tools/app_tests_test.dart` runs each matrix tool once with `--app-tests --json`, which reports its `MatrixAppTest`s (`appTestsReport`), and fails when no tool lists such a directory, when a file lies right in `app_tests/`, and when a tool lists a directory that does not exist or is not one of them. It also fails when an app test that a package of modules keeps applies to an app of the matrix once the modules of that package are taken out of the modules of the app and out of its `everyModuleWith`, or when the matrix of its tool has none of them, so that it runs only in apps with the modules it tests, whichever modules the matrix has today, while the app tests of a package of no module, such as the start check of the CLI, may apply to every app; and when `declaresModule` of `tools/workspace.dart` takes a package in which a tool finds modules for a package of no module. The report also names, for each test, the modules whose ids its tool uses: those whose id, replaced by another in an app of the matrix, changes whether the test applies to the app, the values of its files there or the files it generates there. The check fails on the id of a module that the test does not know (`knownModules` of `tools/workspace.dart`: the modules of the package that keeps it and of the packages of modules they depend on, or, for a package of no module such as the fixture registry, the fixture modules among its dependencies), but for the exceptions of `_ofOneProvider`; and when a tool, or the library that registers its tests, imports a package of modules whose app tests it does not register, or another package of the workspace that the check does not list as needed. `tools/app_test_imports_test.dart` fails when a file of `app_tests/` imports a file of the app, as `package:{{app_name}}/<path>` or by a relative path that leads into `lib/` of the app, that no role of `smf_contracts` guarantees (`RoleInterface`), that no brick of the modules of its package, or of the modules they depend on, generates, and that its own directory does not put into `lib/`. So the app tests of a package of no module, such as the start check of the CLI, may import, of the files that modules generate, only those that the roles guarantee, and those of the fixture registry also the files of the fixture modules it depends on. `app_tests/` stays out of the analysis of its package, of its published archive (`.pubignore`) and of SonarCloud, but `melos run format` formats it; give a `testWidgets` there an explicit `timeout`.

The matrix tools take the names of apps after the directory, such as `'go_router with layout'`, and then check only those. The apps with every module, one for each combination of the providers of the roles that take one (`everyModuleAppsOf` of `lib/matrix.dart`), grow with the product of their numbers, so the tools take a pairwise covering of them unless told otherwise: every pair of providers of two such roles that an app can have is in one of the apps of the covering, and so is every module (`EveryModuleCombinations` of `lib/src/matrix_plan.dart`). Options before the directory choose the apps (`MatrixToolOptions`): `--combinations 3-wise` covers every triple instead, and `--combinations all` takes every combination; `--every-module` checks only the apps with every module, and `--app` with the name of one of them, such as `'every module (riverpod)'`, only that one; `--shard <i>/<n>` checks only the i-th of n shares of the apps of a run. With `--plan`, alone or with `--every-combination`, a tool prints instead the plan of the jobs of CI for its apps, as one line of JSON (`matrixPlanOf`): the combinations that the apps with every module of its matrix cover, `pairwise`, or with `--every-combination` `all` up to 100 of them and `3-wise` beyond; the shards of the matrix, one for each 24 apps that its jobs check (`appsPerShard`); and, from the tool of the CLI, the names of the apps with every module that CI generates, one for each job: `apps`, a pairwise covering, which CI builds for Android and iOS and checks on Windows; `start`, a pairwise covering of those without the modules whose steps need an external service, which it starts on devices; and `entries`, one app for each provider of the app entry, the role that owns the Android and Xcode projects, which it archives and configures with Firebase. `tools/matrix_plan_test.dart` checks the plans of both tools. With `--create`, a directory and a name, the tool of the CLI generates in the directory the apps with every module of the covering, or with `--app` the one of that name, without checking them, each named after the providers of the roles that take one other than the first provider of each (`MatrixApp.everyModuleWith`), such as `start_app` and `start_app_riverpod`; a provider of a role that an app can have several providers of, such as crash reporting, which every app with every module has, adds nothing to the name. It passes any further argument to `smf create`, such as `--org`, and exits with 64, generating nothing, when the name starts with `-`, which `smf create` would take for an option. With `--without-external-steps` after `--create`, it leaves out the modules whose steps need an external service (`PostGenStep.external`), those that depend on them and those that are then left without a provider of a role they require, so that the apps start as they are generated. In a directory whose path has letters beyond ASCII, where `flutter analyze` of Flutter 3.44 and 3.47 fails on every system, the matrix tools analyze the apps with `dart analyze --fatal-infos` instead.

The workflows never select an app by a name that they write, such as `every module (bloc)`, which names the provider of each role that has several and changes when another role gets a second provider. A step that saves such a cache fails the check when it saves only in some jobs of its matrix, by a condition on its strategy or matrix such as `strategy.job-index == 0`; when its key does not hash what `tools/native_build.dart` writes for the apps of the job once they are generated; and when no step after the build compares what the build added to the restored cache, as a step after the restore measured it, with `NATIVE_CACHE_SAVE_ABOVE_MB` from the `env` of the workflow. The check also fails when a workflow calls `apps.yml` with `save_gradle_cache` or `save_swiftpm_cache` not limited to the runs on main (`github.ref == 'refs/heads/main'`), or when `apps.yml` defaults them to true.

Nothing connects to the app. `flutter test`, which CI ran before, must reach the VM service of the app it installed, and on the emulators and simulators of CI it sometimes never did. So the script makes one try, and prints the log of the app and fails when the check fails, when the app stops before the check writes its result, as in a crash at start-up, and when no result comes in time. Runs at the same time, such as the jobs of the nightly run, could register an app each, so in any other run the test fails before flutterfire when the project has no app with the id, and `tools/firebase_registration_test.dart` fails when a workflow other than `build.yml` lets it register, or `build.yml` does not. The job `Firebase key` tells the jobs with Firebase whether the secret is there: without it, as in a pull request from a fork, they do not run. The jobs with Firebase activate the version of the FlutterFire CLI that `smf_firebase_core` activates on the machine of a user. `packages/smf_modules/smf_firebase_core/tool/flutterfire_version.dart` prints it on one line of JSON, `{"version":…,"check":…}`, with the name of the check of the machine as `smf create --explain` shows it, which names the versions that the check accepts. `tools/flutterfire_version_test.dart` fails when a workflow or a script of `.github/scripts` activates `flutterfire_cli` with a version that it writes or with none, or writes the name of the check with a version.

The jobs `macOS` and `Windows` run the tests of every package and of `tools/` on the macOS and Windows runners of GitHub, with the pinned Flutter, 3.44.2, from its release archive; a test of something that only one system does is marked `@TestOn('mac-os')` or `testOn: 'windows'`. On macOS, `iOS (<app>)` generates its app of `apps` with `--create --app` in a directory whose name has a space and letters beyond ASCII, and builds it for the iOS simulator; the jobs of `iOS` and `iOS start` run two at a time, since GitHub runs only a few macOS jobs of a repository at once. `iOS archive (<app>)` generates its app of `entries`, and `test/crashlytics_archive_test.dart` of `smf_firebase_crashlytics` archives it with `flutter build ipa --no-codesign`: it adds the build phase for Crashlytics with the Ruby gem xcodeproj, as `flutterfire configure` does on macOS, fixes the phase with the command from the README of the app, and skips an app that does not depend on `firebase_crashlytics`. In `iOS with Firebase (<app>)`, once the configuration test configured the app, `test/flutterfire_phase_test.dart` of `smf_firebase_crashlytics` fixes the build phase for Crashlytics that flutterfire added with the command from the README of the app, before the app starts on an iPhone simulator; it fails when flutterfire added no such phase, and skips an app that does not depend on `firebase_crashlytics`. `Windows (<app>)` checks its app of `apps` with `--every-module --app` in a directory with a space in its name and in one whose name has letters beyond ASCII too, and generates it once more as a user does, with the full `dart fix` (`--create --app` with `--dart-fix`), in a directory whose name has letters beyond ASCII, to analyze and test it. SMF generates the apps in `%TEMP%` and moves them to another drive. The job `Windows` also activates through `dart.bat` the version of the FlutterFire CLI that the tool of `smf_firebase_core` prints, and finds the CLI with `smf create --explain` for each app of `entries`, by the name of its check that the tool prints too. A job of `build.yml`, `Firebase CLI install (Windows)`, runs the install script of the Firebase CLI on Windows for real.

The jobs with Flutter are in the reusable workflow `.github/workflows/apps.yml`, which takes the version of Flutter, the version of its Dart and the SHA-256 of its archive for each system. `build.yml` runs them with the pinned Flutter on pushes to main, on pull requests into main and when someone starts it by hand on any branch. A pull request into another branch, such as one that collects the pull requests of a larger change, runs only the job of the checks; the jobs with Flutter run later, in the pull request of that branch into main. `nightly.yml` runs them every night, and when someone starts it by hand, with every stable release of Flutter that the generated apps allow. `packages/smf_flutter_cli/tool/flutter_versions.dart` finds those releases: it intersects the Flutter and Dart constraints of the apps of the matrix of the CLI, which the pipeline merges from the `PubspecContribution.environment`s of their modules, and takes the releases from the lists that Flutter publishes for Linux, macOS and Windows. The jobs on Linux run with each of them, and the jobs on macOS and Windows with the oldest and with the latest patch of each minor version. With the latest release, the jobs of the matrices check every combination of the providers, or a 3-wise covering of more than 100 (the input `every_combination`), in more shards, while the apps that CI builds and starts stay the pairwise coverings. The job of the broken providers runs only with the latest release: whether the tests of the roles fail on the bugs hardly depends on the release, but for how flutter_test reports a failure, which a new release may change. The nightly run skips the jobs without Flutter, and the comparison of the brick of `flutter_core` with `flutter create`, since the brick follows the template of the pinned Flutter. It also checks what users install: the job `CLI from pub.dev` of each version activates `smf_flutter_cli` from pub.dev with `dart pub global activate`, which resolves its dependencies from pub.dev rather than from the workspace, generates with it the apps with every module of that release, one for each combination of the providers of the roles that take one, with the full `dart fix`, and runs `flutter analyze`, `flutter test` and `flutter build apk --debug` in each. The CLI on pub.dev has the modules of its release, which may differ from those of the workspace, so `packages/smf_flutter_cli/tool/every_module_apps.dart`, run in a package of its own that depends on the active version, prints the arguments of `smf create` of those apps from `matrixOf` of the release, and the workflow names no module there either. A release without the plan of CI cannot cover them, so this job alone checks its apps one after another. A failure there affects the users of the published version, and its fix needs a release. Maven Central answers 403 to a runner that downloads too much, so what Gradle downloads for the Android builds goes into a cache, and so does what Swift Package Manager downloads for the iOS builds (`~/Library/Caches/org.swift.swiftpm`). Each cache serves every version of Flutter and is keyed by what the app of a job builds with and by the week. Once the app is generated and configured, `tools/native_build.dart` writes into a file of the workspace, whose hash is in the key, the plugins of the app with native code for the platform, with the versions that pub resolved (the plugins of the Flutter SDK left out), plus its Gradle files without the ids of the app for Android, or the Swift packages that its Xcode project refers to itself for iOS. For apps that download nothing for the platform, such as the app of the start check for iOS, it writes no file, and the job neither restores nor saves a cache. Every job that builds for Android or iOS, `CLI from pub.dev` included, restores the cache of its app, or else the newest one of its app from an earlier week, or else the newest one of its platform. When it did not find the cache of its app, it saves that cache after a successful build, but only if the build added more than `NATIVE_CACHE_SAVE_ABOVE_MB` (100 MB) to what it restored. `apps.yml` sets that threshold in its `env` with the reason: a cache is saved whole, over 1 GB for Gradle, so an app that needs only a few MB more than the cache of another app downloads them in each run instead of storing a near copy, while an app that builds with another version of Gradle or of its plugins gets a cache of its own. Only the runs on main save, because the runs of every branch find the caches of main: `build.yml` passes `save_gradle_cache` and `save_swiftpm_cache` for its runs on main, and the nightly run passes them for its latest Flutter on main. Both are false by default. When jobs save the same key at once, the first one wins. A job still downloads what the cache that it restored lacks, such as what its app needs beyond the cache of another app. So every job that builds for Android puts `.github/gradle/maven_central_mirror.gradle` into `~/.gradle/init.d`, and every build of Gradle there takes what it would download from Maven Central from the mirror of Maven Central that Google keeps. A build that declares no repository of plugins, such as the included build of the Gradle plugin of Flutter, gets the mirror before the Gradle Plugin Portal, which would send it on to Maven Central for the Kotlin Gradle plugin. `tools/workflow_apps_test.dart` fails on a job on Linux that runs Gradle for Android without a step before that puts the script there (`mavenCentralProblemsOf`).

The job `CI` of `build.yml` sums up the other jobs of the workflow: it needs all of them and fails when one of them failed or was cancelled. A skipped job counts as passed only in a pull request into a branch other than main, which skips the jobs with Flutter. Every other run runs every job, so there `CI` fails on a skipped job too, and a mistake in the condition of the jobs with Flutter cannot let a pull request into main pass without them. The ruleset of main requires the checks `CI` and `PR title`, so the ruleset does not have to change when jobs come and go. A job added to `build.yml` goes into the `needs` of `CI` too. `tools/build_workflow_test.dart` fails when one is missing there, and when `CI` lacks `if: ${{ !cancelled() }}`, without which a failed job would skip `CI` and a ruleset would take the skipped check as passed. A new run of `build.yml` cancels the run of its concurrency group that is still in progress: `build-<number of the pull request>` for a pull request, and `build-<ref>` otherwise. `.github/workflows/cancel.yml` runs when a pull request is closed and joins the group of the pull request with `cancel-in-progress`, so the run of Build of a merged or closed pull request stops; `tools/build_workflow_test.dart` fails when no workflow does so.

When a test of a package or of `tools/` fails in CI, the page of the run lists it at the top as an annotation, with the name of the test, its message, and its file and line. Every `dart test` in the workflows writes a JSON report with `--file-reporter json:build/test-results/<name>.json` in the directory it runs in, under a name that no other run in its job uses. `.github/scripts/each_app.sh` gives the report of the command it runs for each app the name of the app, `<name>.<app>.json`, so that the run for the next app does not replace it. The last step of each job with tests runs `dart tools/test_annotations.dart` whenever Dart is set up, even after a failed step or in a cancelled job. It turns each test in those reports that failed, or that started and never finished, into an annotation. `tools/test_annotations_test.dart` fails when a run of tests in a workflow writes no report or the same report as another run in its job, and when a job with tests does not run the tool after them.

Run the CLI from source. It finds the Flutter SDK through `flutter` on the `PATH` before it generates anything, and runs `flutter pub get`, `dart fix` and `dart format` in the new app:

```bash
cd packages/smf_flutter_cli
dart run bin/smf_flutter.dart create my_app -o /tmp/out --org com.example --no-input --on-conflict replace
```

Modules are chosen with `-m`, and every option of `create` comes from the command line with `--no-input`. `--explain` prints what would be generated and whether the machine is ready, without changing anything.

## Generated files and templates

- `lib/bundles/*_bundle.dart` are generated from `bricks/` by `tools/bundle_bricks.dart`, which `melos bootstrap` runs. Never edit them by hand. Change the brick, re-bundle and commit the result. CI fails if a committed bundle differs from what the bricks produce.
- `bricks/**/__brick__/**` holds mason templates, not Dart. They are excluded from analysis and formatting. They use mason syntax: `{{app_name.snakeCase()}}`.
- Bricks have no mason hooks. The pipeline rejects a brick with hooks and runs none: modules check the machine and run tools through `Preflight` and `PostGenStep` contributions.
- A brick has the same files in every app. A file whose path depends on the data of a role or on its choice, such as one file for each item that the modules give the role, comes from the render hook of the template of the role or of its provider, as the text of the file by its path in the app (`RoleOutput.files`). The pipeline takes it as it is: it renders no mustache in it, fills no tag and adds no import; `dart fix` and `dart format` of the new app then go over a Dart file among them as over the rest of the app. Otherwise it is a file of the app like those of the bricks. Its path is inside the app, where the kind of the module of a provider may generate files, and no brick or other hook generates the same file. Since the path comes from data, it must also be one that every machine can write, without a control character, a character that Windows forbids in the name of a file or a segment that ends with a dot or a space, and it is not a directory of another file of the app or in what is a file of the app, whatever the case. Its owner is the owner of the hook, and the contract harness, the snapshots and the matrix see it like any other file; a Dart file of the hook of a provider may import what its fragments may. The harness also reports a file of the app, of a brick or of a hook, where code generation or the localizations of Flutter write theirs. The provider of the clock in the fixture package `fake_roles` generates a file for each time zone this way.
- Code of a template that depends on whether a role is in the app is a variable of its brick with a `RoleVar` in `BrickContribution.vars`: the code for an app with the role and the code for one without it, each a `Fragment` with the imports it needs or a string of code that needs none. The pipeline takes the value by the presence of the role, as it applies a contribution by its `when`, so one line of a template serves both apps, where two mustache sections under `has_<role>` would hold the code and its import twice. The role is one that the contributor provides, requires or uses. The variable is a fragment variable in every app, whichever value the app gets, so a template reads it rightly in every app or in none: as it is, `{{{name}}}`, not in a path, and only in a Dart library when either value has imports. The pipeline adds the imports of the value that the app gets to the Dart files of the brick that read the variable. It is read outside every mustache section, that of the presence flag of another role included: code that needs a second role goes into a brick of its own, contributed with `when` of that role. A `RoleVar` holds no plain data for mustache, such as a list or a boolean. The variables of a render hook take none: a hook asks for the presence of the roles that its role requires or uses itself (`RoleHookInput.has`). The module `fake_clock_user` of the fixture package `fake_roles` reads the time zones of the clock this way.
- A post-generation step may continue another step, such as with a fix of a file that the tool of that step writes: it names that step by its id in `PostGenStep.followUpOf`, runs right after it once that step succeeded, and is left for later with it when that step does not run or fails. A step that others may continue has an id (`PostGenStepId`: the module that contributes the step and a name), which the module publishes as a constant of its module class. A module continues only its own steps and those of the modules it depends on directly, so a module knows nothing of the modules that continue its steps. The pipeline reports a step with the id of another module, two steps with one id, a step that the module may not continue or that the app does not have, a `when` on a step that continues another, and steps that continue each other in a cycle.
- The snapshots in `packages/smf_flutter_cli/test/snapshots/` and `packages/smf_pipeline/fixture_registry/test/snapshots/` hold the files of the apps the CLI and the fixtures render. When a change alters them, update them with `SMF_UPDATE_SNAPSHOTS=1 dart test test/snapshot_test.dart` in the package and review the diff.
- `smf_firebase_core` generates `lib/firebase_options.dart` as a placeholder in the form that `flutterfire configure` writes, which throws an `UnsupportedError` until the FlutterFire CLI fills it in, and initializes Firebase with it in `bootstrap()`. Its preflight checks look for the Firebase CLI, a Firebase login, the FlutterFire CLI and, on macOS, the Ruby gem xcodeproj; elsewhere a check tells that the Xcode project is set up on a Mac. They only warn: a run in a terminal offers to set up what it can, asking first. After generation it runs `flutterfire configure` in the terminal with the ids of the app; that needs a Firebase account, so a run with `--no-input` or `--skip-external-setup` generates the app with the placeholder and prints the command to run later. The id of that step is `FirebaseCoreModule.configureStep`, and `smf_firebase_crashlytics` continues it with a step that runs only on macOS and points the build phase for Crashlytics that flutterfire adds at the upload script in `build/ios/SourcePackages`, which `flutter build ipa` needs. The section `Crashlytics` that `smf_firebase_crashlytics` adds to the README of the app gives the command of that fix, to run after `flutterfire configure` by hand on macOS.
- Every app gets `AGENTS.md`, a guide for coding agents that work on the app, and `CLAUDE.md`, whose whole content is `@AGENTS.md`. The template of the app entry role generates both, whichever module provides the role, and `AppEntryRole.agentSections` is the socket of the sections of the guide. The template of a role contributes `AgentNote.ofRole(text)` under the description of the role, such as `routerRole.description`: where its files are, how code uses it and what code must not do. Such a note never names a provider or its package. A provider adds `AgentNote(text)` under the same heading, and a module without a role under a heading of its own. A note tells only what the code of the app does not show, and names a file in backticks by its path from the root of the app. The structural rule `app_entry.agent_guide_paths` reports a path that the app does not have, in every app that the contract harness renders. So a note about a file of a role that the app may lack is a contribution of its own with `when:`, and a note that depends on the data of a role comes from a render hook. The section of the app entry comes first and the others in the order of their headings, so the guide of an app does not depend on which modules provide its roles.

## Tests

- Tests live in each package's `test/`. Sonar counts coverage only within the package that runs the tests, so a module's code needs tests in that module.
- Keep coverage at 100% of the lines and branches of `lib/` with tests that pin behavior someone relies on, never with tests that only touch a line. Remove code that cannot run instead of covering it. Code that no automated test can run, such as the terminal of a user, goes between `// coverage:ignore-start` and `// coverage:ignore-end`, with the reason in a comment next to it. Don't use `coverage:ignore-file`, which the banlist fails on: the file then drops out of `lcov.info` and Sonar counts all of it as uncovered. `melos run test:coverage` measures branches as well as lines, and `melos run coverage:check` after it fails on any line or branch of `lib/` that the tests do not cover, with its `path:line`. CI runs both.
- The contract harness of `package:smf_pipeline/testing.dart` checks a module against the rules of the roles it declares and renders every app it can be part of. `packages/smf_flutter_cli/test/modules_test.dart` runs it over every module the CLI offers, and a module package runs it over itself in its own tests. New modules must pass it.
- For a module, the harness builds a case for each subset of the roles it only uses and each combination of providers of the role of its variants, of each role it requires and of each role of the subset. It leaves out a combination of providers that would give an app two providers of a role that takes one, such as another router next to a module that depends on go_router, unless no combination of the subset can be in an app with the module; then it keeps them all, and their cases report why. A case names the provider of each of its roles that has several in the registry, such as `fake_analytics (get_it) with di`, so the names change when a role gets a second provider. For each package of a provider of a role that a module adds, the harness also builds a case of the module with that provider, `<module> with <provider>` or `<module> (<provider of its variant>) with <provider>`, when they can be in one app. So the registry of a module's tests holds the providers of the roles it requires or uses, the providers it has variants for, and the providers whose packages it adds, and the harness builds an app of the module with each. `ContractHarness.uncheckedProviders()` lists each provider of a role that a module requires or uses which can be in an app with the module but provides the role in no app of the cases of the module; `packages/smf_flutter_cli/test/modules_test.dart` and `packages/smf_pipeline/fixture_registry/test/fixture_registry_test.dart` expect none.
- Generator tests check generated code for real: they parse it or type-check it with the analyzer, not just string-match.
- Tests are hermetic: no network, no Flutter SDK, temp dirs cleaned up. The few that need more skip themselves unless CI provides it: an app from `flutter create` (`SMF_FLUTTER_CREATE_APP`), an app with Crashlytics to archive on macOS (`SMF_CRASHLYTICS_APP`), an app with Crashlytics that flutterfire configured for iOS, to fix its build phase for Crashlytics on macOS (`SMF_CONFIGURED_APP`), an app with Firebase to configure with flutterfire for a platform in a Firebase project, with the key of a service account of the project (`SMF_FIREBASE_APP`, `SMF_FIREBASE_PLATFORM`, `SMF_FIREBASE_PROJECT`, `SMF_FIREBASE_SERVICE_ACCOUNT`, and `SMF_FIREBASE_REGISTER=1` to let flutterfire register the app in the project when the project has none with its id), or a machine where the Firebase CLI may be installed (`SMF_INSTALL_FIREBASE_CLI=1`).
- A bug found but not fixed gets a test for the *correct* behavior, marked `skip: 'Bug: <description>'`. Never write a test that locks buggy behavior in. The fix removes the `skip`.

## Git and PRs

- Use [Conventional Commits](https://www.conventionalcommits.org/) with the package's short name as scope: `fix(go_router): ...`, `feat(contracts): ...`, `test(cli): ...`, `chore(ci): ...`. `melos version` derives version bumps and CHANGELOGs from them.
- Name branches `fix/<topic>`, `feat/<topic>`, `chore/<topic>`, `docs/<topic>`, `test/<topic>`.
- A PR is squash-merged: the squash commit takes the title of the PR as its only line, so the title must be a Conventional Commit too, and CI checks the title of every PR (`.github/workflows/pr-title.yml`). A breaking change needs `!` in the title, such as `feat(contracts)!: ...`: a `BREAKING CHANGE:` footer in a commit of the branch does not reach main.
- A larger change may collect its PRs in a branch of its own. The PR of that branch into main is merged with a merge commit rather than squashed, so that each commit of the branch, such as the squash commit of each of its PRs, reaches main as it is, and `melos version` reads each on its own. So the `!` of a breaking change goes into the title of the PR into that branch that makes the change.
- Once a branch is pushed, add new commits on top. Don't force-push or rewrite pushed history unless a maintainer asks.
- Don't bump package versions or edit CHANGELOGs by hand. `melos version` does both, and its preCommit hook syncs `packages/smf_flutter_cli/lib/version.dart`.
- Keep PRs focused: one concern per PR, one logical change per commit.
