# AGENTS.md

Guidance for AI coding agents working in this repository. Human contributors: see [CONTRIBUTING.md](CONTRIBUTING.md) and [README.md](README.md). The documentation for users and module authors is at [doc.saymyframe.com](https://doc.saymyframe.com).

SMF (Say My Frame) is a Flutter CLI (`smf create`) that generates apps from independent modules (routing, DI, Firebase, features, ...). It is a Dart pub workspace managed by Melos. Every package is versioned and published to pub.dev on its own.

## The module model

- A module declares the roles it provides, requires or uses (router, DI, state management, ...) instead of depending on the modules that implement them. It puts code into typed sockets instead of patching files, and never learns which provider of a role was selected. The model is `package:smf_contracts/smf_contracts.dart`; `package:smf_contracts/core.dart` is its core without concrete roles.
- `packages/smf_pipeline/` is the generation pipeline of `smf create`. It imports only `core.dart` and knows no concrete module or role; `test/architecture_test.dart` checks this.

- Within `smf_contracts`, `test/architecture_test.dart` keeps the core free of concrete roles. A module package checks in its own `test/architecture_test.dart`, with `ModulePackage` of `package:smf_pipeline/testing.dart`, that its code uses only the module model and the modules it depends on, and what the package depends on. `roleClassNameProblems` of the same library checks that the code in `lib/` of a package and of the module packages it depends on takes the name of each class that a role requires from the role, such as `LayoutRole.appShell.name`, rather than spelling it out in a string; `test/role_class_names_test.dart` of `smf_flutter_cli` and of `fixture_registry` runs it. A module package other than `smf_flutter_core` renders the apps of its tests with `smf_flutter_core` as a dev dependency, for their app entry; its `lib/` imports no other module but those it depends on. Nor does a module package name the modules that depend on it: `packages/smf_flutter_cli/test/modules_test.dart` fails when the `lib/` of a module package, but its bundles, or its `bricks/`, `example/` or `README.md` has a word of the id of such a module that the id of the module of the package lacks, whatever its case and also inside a camelCase name, such as `crashlytics` in `smf_firebase_core`. Dev dependencies between module packages must not form a cycle, because pub.dev resolves them when it analyzes a package: `smf_flutter_core` has none on modules, and of two modules whose tests need each other's role, one tests with a provider of its own in `test/`. `tools/package_graph_test.dart` checks the packages of the workspace for a cycle.

## Layout

```
packages/
  smf_contracts/              # the module model: modules, roles, sockets, contributions
  smf_pipeline/               # the generation pipeline of `smf create` and the contract test harness
    fixture_registry/         # the apps of the fixtures: snapshots, their Flutter matrix with its app tests, the app of several providers, and the apps of the broken providers
    test/fixtures/            # fake modules for the features of the model that no real module uses yet, and providers of roles with a known bug
  smf_modules/
    smf_contribution_engine/  # a standalone engine that patches Dart files; no module uses it
    smf_<module>/             # first-party modules: go_router, get_it, firebase_*, event_bus, shared_preferences, home, settings, onboarding, local_notifications, sign_in, google_sign_in, apple_sign_in, flutter_core, bloc, riverpod, bottom_tabs, gen_l10n, material_theme
  smf_flutter_cli/            # the `smf` binary: the modules it offers, and the terminal, files and processes of the machine; setup_steps.json, the catalog of the steps by hand of its modules
tools/                        # bundle_bricks.dart and sync_cli_version.dart; banlist.dart, coverage_check.dart, native_build.dart, test_annotations.dart and workspace_members.dart with their tests; package_graph_test.dart, build_workflow_test.dart, workflow_apps_test.dart, each_app_test.dart, start_app_test.dart, build_apk_test.dart, firebase_registration_test.dart, flutterfire_version_test.dart, firebase_cli_version_test.dart, sonar_lcov_test.dart, matrix_plan_test.dart, app_tests_test.dart, app_test_imports_test.dart and workspace.dart, which the last two share; the tools read the members of the workspace with workspace_members.dart, the only file that reads them from the root pubspec, as banlist.dart checks
```

Dependencies point one way only: `smf_contracts` ← `smf_pipeline` and modules ← `smf_flutter_cli`. Contracts never depend on modules, the pipeline or the CLI; the pipeline never depends on a module. Modules use `smf_pipeline` only in their tests, for the contract harness.

## The core principle: modules are independent

Module independence is the foundation of the project. Never break it, not even to fix a bug quickly.

- A module knows **only** the modules it lists in `ModuleDescriptor.dependsOn`, and only in one direction. For example, `firebase_analytics` depends on `firebase_core`, but `firebase_core` knows nothing about its dependents.
- A module never references another module's generated artifacts (classes, files, packages) unless it declares that dependency, and it should avoid needing to.
- Nothing is hardcoded for a particular combination. Any selection of modules and variants (e.g. state manager `bloc` / `riverpod`) must generate an app that compiles.
- Modules describe *what* they need through the DSLs in `smf_contracts`: routes, and the guards that keep the user from them until a condition holds (`RoutesData` of the router role), DI (`DiRegistration` of the DI role), the entries of the settings screen (`SettingsEntry` of the settings screen role), the steps of the onboarding (`OnboardingStep` of the onboarding screen role), the texts that a user sees (`TextsData` of the localization role), code for sockets (`SocketContribution`s) and bricks. The providers of those roles turn the descriptions into code, and the contract harness checks that the files of the provider of the DI role call or tear off the factory of every registration and its dispose function (the rule `di.registrations_rendered` of the role), and that the files of the provider of the settings screen role create the widget of every entry, through an import of its file with a prefix that no import of another file has (the rule `settings_screen.entries_rendered`). It also checks that the files of the provider of the router role create the `GuardedNavigation` that the role generates in an app with guards, read `guardChanges`, and name `ShowOver` and `ClosePages`, two of the answers of that class (the rule `router.guards_asked`). Only the tests of the role in a running app show whether the provider asks the guards as the role says. In an app with a layout and destinations, it checks that those files read `appDestinations`, the list of the destinations that the layout role generates (the rule `router.destinations_shown`). It also checks that, in an app with steps, the files of the provider of the onboarding screen role read `appOnboardingSteps`, the list of the steps that the role generates (the rule `onboarding_screen.steps_shown`). A feature module must not assume a specific router or DI container, and neither do its tests. They check what the module gives a role through the data of the role, which the role reads from `ContractResult.hook`, the hook request of the app of a case of the harness, with functions such as `diRole.graphOf(diRole.hookInput(result.hook!))`, `routerRole.startIn`, `layoutRole.destinationsIn`, `settingsScreenRole.entriesIn`, `onboardingScreenRole.stepsIn` and `localizationRole.textsIn`, and through what each socket got, in the order the pipeline rendered it, with the fragments of the render hooks of the roles (`RenderedApp.socketOrders`). They tell the files that a provider changed by their owner, and never read `RouterRole.appRouterFactoryFile`, `DiRole.dependenciesFile`, `LayoutRole.appShellFile` or `LocalizationRole.textsFile`, in which the providers of those roles render what the modules give them, nor `AppEntryRole.bootstrapFile`, `AppEntryRole.mainFile` and `lib/app.dart`, into which the provider of the app entry renders the start-up and the root of the app. Only the package of the provider tests those files. `tools/banlist.dart` bans their constants and paths in the tests of the module packages, except as the key of a map, for the files of a provider that a test defines, and in the tests of the package that provides each. Nor do they read the screen in which the provider of the settings screen role shows the entries: it is a file of that provider, which no role names, so the banlist does not know it. `packages/smf_flutter_cli/test/modules_test.dart` fails when a test of a module package takes more of the class of a module of another package than its `id`, such as the directory in which a provider writes its files, unless its module depends on that module.
- A guard of the routes (`RouteGuard`) has a stage (`GuardStage`), `welcome` or `identity`. The app asks its guards by stage, then in the order of the modules, then as their module declares them. So the onboarding comes before a sign-in whatever the order of the modules on the command line, and no module names another to place its guard. The list of stages is closed. A guard that is neither takes the stage that its flow belongs to, as the doc of `GuardStage` says, and the order of the modules places it among the guards of that stage. So the app may ask it before the guard that asks who the user is, and it allows while it cannot tell who the user is. A guard also says whether the router brings the user back to where they were once it allows again (`RouteGuard.resumes`, `true` unless the guard says otherwise). When a guard with `false` stops allowing, the router remembers no location for it and forgets what it remembered, for another guard too, such as the location that the user was on when the onboarding started again. The user then comes to the screen that the app starts on, as the next user should after a sign-out. The generated class looks at the guards each time it is asked about a location or told that a guard notified. It takes a guard to have stopped when the guard does not allow and allowed at the look before. So a guard that does not allow from the first launch has not stopped, and the location that the app is opened with is shown after the flows of a first launch. A location that is asked for after the guard stopped is remembered. A guard that stops and allows again between two looks, such as one that does not notify, is not seen to stop. In the app, the stage shows only in the order of `routeGuards`.
- A guard without a condition is a gate over the whole app. A guard can stand for a condition that only some routes ask for instead (`RouteGuard.condition`), and it then keeps the user only from those routes. A role publishes the condition as a constant, a `RouteCondition` with the role and a name, such as an account for a role that knows who the user is. A feature asks for it on a route (`Route.conditions`), and the routes below that route ask for it too. A module that requires or provides the role declares the guard, whose function says whether the condition holds. So the feature and the module with the guard know the role and not each other. The app asks its gates first and then its guards of conditions, those of each kind by stage, then in the order of the modules, then as their module declares them, so a gate that does not allow always decides. In the app, a guard of a condition has `routes`, the full names of the routes that ask for it, which the template of the role collects from every module (`RouterFacade.routesAsking`). The app has nothing else of a condition. An app may have no guard for a condition, because it lacks the role or the module with the guard. The routes that ask for it then show like any other, and the router role reports nothing. A role that publishes a condition may warn of that itself: its hooks see the guards of the app (`RouterFacade.guardFor`) when it requires or uses the router role. The rule `router.routes` reports a condition of a role that the module does not list, and a condition on a route that every user gets to: a route of the main navigation, a start candidate or a route above one, and a route in the flow of a guard of the module. The rule `router.guards` reports a guard of a condition whose role its module neither requires nor provides, and a second guard of a module for one condition. The template of the role reports the guards of two modules for one condition, and `--start` refuses a route that asks for one. A guard of a condition may show the target of a gate of its module. The two then have one flow, which is over only once both allow: the screens of a sign-in whose gate lets everyone in still show while its guard of the account does not allow. While a condition does not hold, a request for a route that asks for it opens the target of the guard over the page that the user is on, and the request waits. Back returns to that page and drops the request. Once the condition holds, the router closes the pages of the flow and does what was asked: `push()` shows the route over the page that the user was on and completes with the value of its page, `go()` shows it in place of the stack, and `replace()` in place of that page. A location from the platform, or one that is asked for before the app has a page, opens the target over the screen that the app starts on. The routes of the flow of such a guard show while the condition does not hold, as a sign-in screen that a guest opens. A request for one of them that is made on a page shows it as the code asked, over that page for `push()` and in place of the stack for `go()`. Asked for with no pages, as by a link, it would stand alone, with no way back into the app. So it opens over the screen that the app starts on, with that screen alone below it, back leads into the app, and the router closes it once the condition holds. A flow that a gate keeps open too is the gate's, and takes the place of the stack. A further request for such a route does nothing while a page of the flow is among the pages, on top or below another page. When a condition stops holding, the router closes each page that asks for it with the pages over it, and a page with none below it leaves for the screen that the app starts on. So a screen never closes itself, and never navigates, after it changed what a guard reads: the router has done both by then. That goes for a screen of a flow that made its guard allow, and for a page that asks for a condition and ends it itself, as a screen of an account with a sign-out. A `pop()` after the change closes the page that is on top by then: the page that the user asked for, whose `push()` then completes with `null`, or the page below the one that the router closed, which may be the main navigation of the app. For a route that asks for two conditions, the target of the first guard that does not allow opens. Once that guard allows, the router closes its flow and asks about the request again, so the target of the second guard opens in turn. The `routes` of a guard do not inherit in the app: the template lists each route below a route that asks, and a developer who adds a route by hand adds the routes below it too. The class that the role generates decides all of this (`GuardedNavigation`), and answers a provider with what to do: `ShowInstead` of a location that takes the place of the stack, as for a gate; `ShowOver` of the target of a guard for a request for a route that asks for its condition, and of a page of its flow that is asked for with no pages; `ShowNothing` for a further request while the flow is open; and `ClosePages` for the pages on top that have to leave, which are the pages of a flow that is over, the pages that ask for a condition that stopped holding, and the pages over them. A provider tells the class the routes of the pages that a location is asked for on top of, and the answer depends on those pages. So a provider never asks with no pages about a location that it shows over a page, nor about one that it goes to for a request that it asked about with the pages: a router whose redirect runs for its own navigation, with no pages, keeps those calls from the class. It keeps the one request that waits while a page of the flow is among its pages, makes it again once `ClosePages` took the last of them, and drops it when they leave in another way. It also drops the request when `ClosePages` says so (`dropsRequest`): the pages that close reach below the flow, so the page that the request was made on closes too, as one that asks for another condition, which stopped holding. The class knows that from how many pages it opened the flow over. The `push()` of a page that the provider closes completes with `null`, at once or when the frame is over. Until its next build the navigator may still have the route of such a page, and a screen that closes itself in that time, or the back button of the system, closes that route and no page of the provider. It tells of each page whether it can close the page on its own. And the listeners of the screen hear only of pages that the user saw, so not of the page below a flow that closes when the request shows another page over it. The class remembers a location only for a gate, and opens a flow only when it is asked. That is a known limit: a link to a route that asks for a condition, which opens the app behind a gate that does not allow, as on a first launch with an onboarding, is lost once the gate allows while the condition does not hold. The user is then on the screen that the app starts on, though the same link opens the flow over that screen when no gate is in its way. For the same reason two guards with one flow read one notifier. A link to a page of the flow of such a guard is lost behind a gate with another flow as well: the class never remembers a location in a flow.
- Generated UI talks only to its state-management layer (a Cubit via `context.read`, a Riverpod provider via `ref`), never directly to a DI container or infrastructure service.
- The preferences role keeps the settings of the app that are no secret, such as the theme mode. A token, a password, an API key or an encryption key never goes there. A module, or the template of a role, that remembers a setting gives the role a restorer (`PreferencesRole.restorers`), a function that gets the preferences in the platform phase of `bootstrap()`, reads its keys and keeps the preferences for its writes. A restorer is synchronous and awaits nothing: the role does not wait for an asynchronous one and does not catch what it throws. A key is `<owner id>.<setting>`, such as `theme.mode`, where the owner is the module or the role whose code keeps the setting. No module and no template of another role calls `createAppPreferences()`, and only `bootstrap()` calls `initPreferences()` (the rule `preferences.factory_calls` of the role). A restorer keeps the current value when nothing is saved under its key, and may run more than once, since `initPreferences()` runs again in a test of the next launch of the app. An app test shows that a setting is remembered by writing its key through `AppPreferences`, running `initPreferences()` again and reading the state, and that it is saved by reading the key after a choice; running `initPreferences()` again right after a choice proves nothing, since memory has the value already. Nor does it stand for the next launch once a key was removed: the restorer then keeps the value that the state has. Apple takes a token once, so the service keeps that credential for the credential object in an `Expando`. `signInWith` of the identical object signs in with it once and drops it, and a sign-in with another credential object sends its own token. A sign-in again with a credential of another user (`user-mismatch`) or of an identity without a user (`user-not-found`) is `invalidCredentials` and signs nobody out. Firebase also answers `user-not-found` for the user's own credential when the server deleted the account, such as on another device, so the service then reloads the user. For a deleted user the reload fails with a code of a session that has ended, and the service signs the user out and fails with `recentSignInRequired`. A token whose nonce Firebase took before (`missing-or-invalid-nonce`) is `invalidCredentials` too, and `provider-already-linked` is `unknown`. For a call with a credential, the hint of a way to sign in that is not enabled names Google or Apple, and for Google the script of the app as well. `deleteAccount(fresh:)` signs the user in again with the credential. For a credential of Apple on iOS and macOS, where Firebase revokes, it then revokes the tokens of Apple with the authorization code of that credential before it deletes the account. A credential of Apple without a code fails there with `notConfigured`. The service checks that a user is signed in right before the revocation, since the future of the Firebase SDK never completes without one. A revocation that fails keeps the account and is `notConfigured`, with a hint that has what Firebase answered, the Services ID and the OAuth code flow configuration of the Apple sign-in method (the Apple team ID, the Key ID and the private key) and the link to the sign-in methods of the project. Answers that have nothing to do with the setup get their own reasons: `network-request-failed`, `too-many-requests`, `user-disabled` and a session that has ended. The module uses the localization role: in an app with it, the service sets the language of Firebase to the one that the app is in before it asks for the message of a password reset, with a `RoleVar` of its brick. Its section of the README of the app, `Firebase Authentication`, tells where the ways to sign in are enabled in the Firebase project and which of them the mode `anonymous` needs. In an app with Google sign-in, it also tells what the script sets up for Google and how to register the SHA of the key of a release. In an app with Apple, it tells how to enable Apple in the Firebase console, with the key that the revocation needs.
- The notifications role covers the notifications of the app: the permission to show them, a notification that the app shows now or at about a time to come, and the tap of the user on one. An app has at most one provider. The provider implements `NotificationsService` of `lib/core/notifications/notifications_service.dart` (`NotificationsRole.serviceFile`) and contributes it as a `RoleImplementation`. The template of the role does the rest, whichever module provides the role. It generates `lib/core/notifications/app_notifications.dart` (`NotificationsRole.controllerFile`) with `appNotifications`, through which the code of the app shows, schedules and cancels notifications, and lists those still to come with `scheduled()`. `initNotifications()` creates the service and starts `appNotifications` with it in the platform phase of `bootstrap()`, and only `bootstrap()` calls it (the rule `notifications.start_calls`, which also reports a module that calls `appNotifications.start()`). No module, and no template of another role, calls `createNotificationsService()`, and only the files of the implementation of the provider import the file of `NotificationsService` (the rule `notifications.factory_calls`). The role registers nothing in a DI container. `appNotifications.permission` is `granted`, `denied` or `notAsked`. On Android 13 and later, an app that may not show notifications looks the same whether it asked or not, so the role requires the preferences role and remembers under `NotificationsRole.askedKey` (`notifications.asked`) that it asked. The controller asks the service again when it starts, after a request, and each time the user comes back to the app. `appNotifications.request()` asks the user only when the app may not show notifications, takes the permission from the service once the user has answered, and shares one question between two requests made at once. Where the platform has no question to show and the app may not show notifications, as on Android before 13, the provider's `request` opens the settings of the system for the notifications of the app instead, so the user needs only one request to turn them on. Scheduling is inexact: a notification shows at about its time, which needs no permission for exact alarms. The id of a notification is a 32-bit integer. A notification with an owner, such as a push message that the app shows itself, names its owner under `NotificationsRole.ownerKey` (`notifications.owner`) in its data and has a negative id, so it never takes the place of a notification of the app. `appNotifications.taps` and `launchTap` leave out the taps on such a notification, and those with a negative id, and `tapsOf(owner)` and `launchTapOf(owner)` give them to the owner, so the code of the app sees each tap once. The template also generates `android/app/src/main/res/drawable/ic_notification.xml`, the small icon of a notification on Android (`NotificationsRole.androidIcon`), and a file that keeps that icon in a release build, which would otherwise remove it when it shrinks the resources. Every provider shows the notifications in the channel `NotificationsRole.defaultChannel`, which has the name of the app in the settings of the system. The role uses the settings screen role, the onboarding screen role and the localization role. In an app with a settings screen, the template adds `NotificationsSetting`, an entry that shows whether the app may show notifications and either asks or opens the settings of the system. In an app with an onboarding, it gives the onboarding the step `notifications.permission`, of the stage `permission`. Its second button is Not now, and the onboarding shows it while the permission is `notAsked`. Their texts are texts of the template, in English and in Ukrainian. In an app with neither, nothing asks for the permission, and the README of the app and the guide for coding agents tell the developer where to call `appNotifications.request()`. The mocks of the platform side of a provider start as on a first launch, and a request grants the permission. The tests of `smf_contracts` run the generated controller with stand-ins for the libraries of Flutter. In the fixtures, `fake_notifications` of `fake_infra` provides the role, with the permission and the scheduled notifications in memory, on a system that has no question for the permission. In the CLI, `local_notifications` provides it on flutter_local_notifications, with `LocalNotificationsService` of `lib/core/notifications/local_notifications_service.dart`, which it opens asynchronously. Before it shows a notification, it cancels the scheduled one of the same id, whose alarm Android keeps. A notification carries its data as the JSON of a map in the payload of the plugin, and a tap with a payload that the app did not write has no data. The plugin does not tell whether the system showed its question for the permission. So during a request the service watches the lifecycle of the app, which the question takes out of the foreground until the user answers. When the app stayed in the foreground and still may not show notifications, the service opens the notification settings of the app. That happens on Android before 13, and on Android 13 and later or iOS once the system asks no more. A request that starts while the app is out of the foreground, such as under the control center of iOS, opens no settings, since a question then changes nothing that the app sees.
- The push role covers push messages: the address of the device, to which a backend sends messages through the provider, the messages that arrive, and the taps of the user on them. An app has at most one provider, and the role requires the notifications role. The provider implements `PushService` of `lib/core/push/push_service.dart` (`PushRole.serviceFile`) and contributes it as a `RoleImplementation`. The template of the role does the rest, whichever module provides the role. No module, and no template of another role, calls `createPushService()`, and only the files of the implementation of the provider import the file of `PushService` (the rule `push.factory_calls`). The role registers nothing in a DI container. `appPush` asks the service for the address when it starts, without waiting for it, and again each time the user comes back to the app while it has none. It follows the new addresses that the service tells of, and prints each in debug mode. `appPush.messages` tells of each message that arrives while the app is in the foreground. Where the platform does not show such a message itself (`PushService.platformShowsInForeground`), `appPush` shows one with a title or a body with `appNotifications.show()`, as a notification whose owner is the role (`NotificationsRole.ownerKey`), with a negative id and with the message as JSON under `PushRole.messageKey` (`push.message`) in its data. `appPush.taps` has the taps on the messages that the platform showed, from the service, and on those that `appPush` showed, from `appNotifications.tapsOf()`. `appPush.launchMessage` is the message whose tap launched the app, from the service or from `appNotifications.launchTapOf()`. The notifications of the app leave the taps of the role out of `appNotifications.taps`, so the code of the app sees each tap once. A provider never asks for the permission to show notifications, which belongs to the notifications role, and never keeps the notifications of the app from showing while the app is in the foreground. Every push message reaches an iPhone through APNs, so the template gives the iOS app the entitlement `aps-environment` with the value `development`, with the step by hand `app_entry.ios_app_id` that it needs, and `remote-notification` among its `UIBackgroundModes`. On iOS the address needs the APNs token, which only a build signed with that entitlement gets: a simulator on a Mac gets one, one on a macOS virtual machine never does, and an iPhone needs a paid team. SMF does not check the team of the developer. The section `Push messages` of the README of the app (`PushRole.readmeHeading`) tells a developer with a free team to remove the key to run the app on an iPhone. The mocks of the platform side of a provider give the device an address that stays the same from one launch of the app to the next. The tests of `smf_contracts` run the generated controller with stand-ins for the libraries of Flutter. In the fixtures, `fake_push` of `fake_infra` provides the role and keeps the address of the device in memory. The first start registers the device, which gets its address a while later, as an iPhone gets its APNs token, and the next starts have the same address. In the CLI, `firebase_messaging` provides the role on the firebase_messaging package, below 17, which needs firebase_core 5, with `FirebasePushService` of `lib/core/push/firebase_push_service.dart`. The address is the registration token of Firebase Cloud Messaging. On iOS the plugin gives none before the APNs token comes, and the service answers `null` then, as for any failure of the plugin. When the APNs token comes later, the iOS plugin of 16.7 tells the app of no token. So while something listens to `addressChanges`, the service reads the APNs token with `getAPNSToken()`, which needs no network, with waits that double from half a second up to eight seconds, for at most two minutes, and then tells of the registration token. Its timer stops with the last listener, so the next start of the push messages leaves no timer of the old service behind. firebase_messaging answers iOS for every notification that arrives in the foreground, the local notifications of the app too, with presentation options that are none by default, so the service sets an alert, a badge and a sound when it is created. In the manifest of the Android app, the module names `NotificationsRole.defaultChannel` and the drawable `NotificationsRole.androidIcon` as the channel and the small icon of a message that Android shows in the background. Its section of the README of the app, `Firebase Cloud Messaging`, tells how to upload the APNs key to Firebase, that the App ID has to be in the team of the key, and how to send a test message.
- State-manager variants: a module whose code depends on the state manager declares `Variants` of the state management role in its descriptor, keyed by the id of each provider (`bloc`, `riverpod`), and each variant adds the package of its state manager with the constraint `any`, leaving the version to the provider (see the fixture `fake_feature` in `packages/smf_pipeline/test/fixtures/`). - The package of a provider of a role, such as `flutter_riverpod` of `riverpod`, goes into another module only through its variant for the provider, with the constraint `any`, or through its `dependsOn` on the provider: the pipeline rejects any other module that adds it in an app with the provider. Once the app is configured, `test/enable_sign_in_test.dart` of `smf_firebase_auth` checks the sign-in methods of the project, and skips an app that does not depend on `firebase_auth`. Every job with Firebase asks the project as a client, with the API key of the app: a sign-in with a password for an address that has no account, which creates nothing. A project with Email/Password answers `INVALID_LOGIN_CREDENTIALS`, or `EMAIL_NOT_FOUND` without the protection against the enumeration of addresses. One without it answers `PASSWORD_LOGIN_DISABLED`, and one in which Authentication was never set up `CONFIGURATION_NOT_FOUND`: the test fails on these with what they mean and with who enables the methods. The apps of CI are in the mode `required`, so it asks for Email/Password alone, and no job creates an anonymous user. One job enables the methods first: the test runs the script of the app there, with the command of the README of the app, the key of the service account as `GOOGLE_APPLICATION_CREDENTIALS` and no `--project`. It expects the exit code 0, the line with which the Firebase CLI names the methods that it enabled, `firebase.json` as it was, no new file in the app, and no changed file but those that the ways to sign in of the app need. In an app with Google sign-in, the script runs as the service account and so leaves Google out, which the project of CI has enabled already. The job configures the Android app alone, so the test then checks the client of the server of Google in its Firebase file. It then deletes the SHA-1 and SHA-256 of the debug key of the runner, which the script prints, if this run registered them, so that two runs never delete each other's. That job is the one that gets `SMF_FIREBASE_ENABLE_SIGN_IN=1`: the job `Android with Firebase` of the first app of the plan, in a run of `build.yml`, so that two jobs never write to the project at once. When the script fails, the test tells a lack of a permission of the service account from an API that is not enabled, from credentials that the Firebase CLI did not take and from any other failure. For a lack of a permission, it names the permissions that the Firebase CLI printed as denied. Google names each as `permission: '<name>'` in its answer, which the Firebase CLI prints with its error. An example is `serviceusage.services.enable`, which the Firebase CLI needs to provision the app of the project through which it enables the methods. Only when the Firebase CLI printed none does the test run the script once more with `--debug`, and it takes from that output only the permissions that the Firebase CLI says its account lacks. When that names none either, the test lists the permissions that `firebase deploy --only auth` is known to ask for. It names a role to grant only for a permission that the reference of the IAM roles of Google Cloud lists for the role (`rolesWith` of `test/support/sign_in_methods.dart`): Service Usage Admin for `serviceusage.services.enable`, which Firebase Admin lacks, and Firebase Admin for the permissions of `firebase`, `firebaseauth` and `firebasehosting`. For any other permission, the reader picks the role. `test/sign_in_methods_test.dart` tests what each answer and each failure means, without the network. `tools/firebase_registration_test.dart` holds `SMF_FIREBASE_ENABLE_SIGN_IN` to the input `register_firebase_apps` too, and fails when a second job gives the test the variable, or when the job that gives it has a matrix and does not keep it to its first job with `strategy.job-index == 0`. The start step of `Android with Firebase (<app>)` then sends the app a push message. The probe of `firebase_messaging` asks for it, and the step gives `start_app.sh` the answer `firebase_messaging`: `test/push_delivery_test.dart` of `smf_firebase_messaging`, with `SMF_FIREBASE_PROJECT`, and with the key of the service account in a file that only this step has. So the message adds about a minute to each of these jobs, one for each provider of the app entry. The test writes a report of its own, `push_delivery_test.json`, and the step is an exception of `modulePaths` with its reason. `iOS with Firebase (<app>)` gives no answer. The iOS simulator on the macOS virtual machine of CI never gets the token of the Apple Push Notification service, so the app there has no address, and its probe does not count that as a problem. The job `Firebase key` tells the jobs with Firebase whether the secret is there: without it, as in a pull request from a fork, they do not run. The jobs with Firebase activate the version of the FlutterFire CLI that `smf_firebase_core` activates on the machine of a user. `packages/smf_modules/smf_firebase_core/tool/flutterfire_version.dart` prints it on one line of JSON, `{"version":…,"check":…}`, with the name of the check of the machine as `smf create --explain` shows it, which names the versions that the check accepts. `tools/flutterfire_version_test.dart` fails when a workflow or a script of `.github/scripts` activates `flutterfire_cli` with a version that it writes or with none, or writes the name of the check with a version. The Firebase CLI of these jobs is the latest one of npm, which has the command of every module: `firebase_auth` needs 15.34.0 or later, whose `firebase deploy --only auth` adds no web app to a project that has apps. Its check of the machine and the script of the app refuse an older one themselves. `tools/firebase_cli_version_test.dart` fails when a workflow or a script installs or runs `firebase-tools` in a version that it writes, which CI would go on installing once a module needs a later one.

The jobs `macOS` and `Windows` run the tests of every package and of `tools/` on the macOS and Windows runners of GitHub, with the pinned Flutter, 3.44.2, from its release archive; a test of something that only one system does is marked `@TestOn('mac-os')` or `testOn: 'windows'`. On Windows a test has 90 seconds, three times the default of `dart test` (`--timeout 3x`): the runner tests four packages at a time on four cores, and a test that analyzes apps can take ten times as long there as on a laptop. So a test that is slow only there needs no timeout of its own. On macOS, `iOS (<app>)` generates its app of `apps` with `--create --app` in a directory whose name has a space and letters beyond ASCII, and builds it for the iOS simulator; the jobs of `iOS` and `iOS start` run two at a time, since GitHub runs only a few macOS jobs of a repository at once. `iOS archive (<app>)` generates its app of `entries`, and `test/crashlytics_archive_test.dart` of `smf_firebase_crashlytics` archives it with `flutter build ipa --no-codesign`: it adds the build phase for Crashlytics with the Ruby gem xcodeproj, as `flutterfire configure` does on macOS, fixes the phase with the command from the README of the app, and skips an app that does not depend on `firebase_crashlytics`. In `iOS with Firebase (<app>)`, once the configuration test configured the app, `test/flutterfire_phase_test.dart` of `smf_firebase_crashlytics` fixes the build phase for Crashlytics that flutterfire added with the command from the README of the app, before the app starts on an iPhone simulator; it fails when flutterfire added no such phase, and skips an app that does not depend on `firebase_crashlytics`. `Windows (<app>)` checks its app of `apps` with `--every-module --app` in a directory with a space in its name and in one whose name has letters beyond ASCII too, and generates it once more as a user does, with the full `dart fix` (`--create --app` with `--dart-fix`), in a directory whose name has letters beyond ASCII, to analyze and test it. SMF generates the apps in `%TEMP%` and moves them to another drive. The job `Windows` also activates through `dart.bat` the version of the FlutterFire CLI that the tool of `smf_firebase_core` prints, and finds the CLI with `smf create --explain` for each app of `entries`, by the name of its check that the tool prints too. A job of `build.yml`, `Firebase CLI install (Windows)`, runs the install script of the Firebase CLI on Windows for real.

The jobs with Flutter are in the reusable workflow `.github/workflows/apps.yml`, which takes the version of Flutter, the version of its Dart and the SHA-256 of its archive for each system. `build.yml` runs them with the pinned Flutter on pushes to main, on pull requests into main and when someone starts it by hand on any branch. A pull request into another branch, such as one that collects the pull requests of a larger change, runs only the job of the checks; the jobs with Flutter run later, in the pull request of that branch into main. `nightly.yml` runs them every night, and when someone starts it by hand, with every stable release of Flutter that the generated apps allow. `packages/smf_flutter_cli/tool/flutter_versions.dart` finds those releases: it intersects the Flutter and Dart constraints of the apps of the matrix of the CLI, which the pipeline merges from the `PubspecContribution.environment`s of their modules, and takes the releases from the lists that Flutter publishes for Linux, macOS and Windows. The jobs on Linux run with each of them, and the jobs on macOS and Windows with the oldest and with the latest patch of each minor version. With the latest release, the jobs of the matrices check every combination of the providers, or a 3-wise covering of more than 100 (the input `every_combination`), in more shards, while the apps that CI builds and starts stay the pairwise coverings. The job of the broken providers runs only with the latest release: whether the tests of the roles fail on the bugs hardly depends on the release, but for how flutter_test reports a failure, which a new release may change. The nightly run skips the jobs without Flutter, and the comparison of the brick of `flutter_core` with `flutter create`, since the brick follows the template of the pinned Flutter. It also checks what users install: the job `CLI from pub.dev` of each version activates `smf_flutter_cli` from pub.dev with `dart pub global activate`, which resolves its dependencies from pub.dev rather than from the workspace, generates with it the apps with every module of that release, one for each combination of the providers of the roles that take one, with the full `dart fix`, and runs `flutter analyze`, `flutter test` and `flutter build apk --debug` in each. The CLI on pub.dev has the modules of its release, which may differ from those of the workspace, so `packages/smf_flutter_cli/tool/every_module_apps.dart`, run in a package of its own that depends on the active version, prints the arguments of `smf create` of those apps from `matrixOf` of the release, and the workflow names no module there either. A release without the plan of CI cannot cover them, so this job alone checks its apps one after another. A failure there affects the users of the published version, and its fix needs a release. Maven Central answers 403 to a runner that downloads too much, so what Gradle downloads for the Android builds goes into a cache, and so does what Swift Package Manager downloads for the iOS builds (`~/Library/Caches/org.swift.swiftpm`). Each cache serves every version of Flutter and is keyed by what the app of a job builds with and by the week. Once the app is generated and configured, `tools/native_build.dart` writes into a file of the workspace, whose hash is in the key, the plugins of the app with native code for the platform, with the versions that pub resolved (the plugins of the Flutter SDK left out), plus its Gradle files without the ids of the app for Android, or the Swift packages that its Xcode project refers to itself for iOS. For apps with none of these for the platform, such as an app without plugins with iOS code, it writes no file, and the job neither restores nor saves a cache. The tool lists every plugin with native code, whether its build downloads anything or not. The apps that CI starts on iOS without Firebase have plugins with iOS code, but none whose Swift package names a remote package. So their jobs have a key under which nothing is ever saved, and each restores the newest cache of any app without using it. Every job that builds for Android or iOS, `CLI from pub.dev` included, restores the cache of its app, or else the newest one of its app from an earlier week, or else the newest one of its platform. When it did not find the cache of its app, it saves that cache after a successful build, but only if the build added more than `NATIVE_CACHE_SAVE_ABOVE_MB` (100 MB) to what it restored. `apps.yml` sets that threshold in its `env` with the reason: a cache is saved whole, over 1 GB for Gradle, so an app that needs only a few MB more than the cache of another app downloads them in each run instead of storing a near copy, while an app that builds with another version of Gradle or of its plugins gets a cache of its own. Only the runs on main save, because the runs of every branch find the caches of main: `build.yml` passes `save_gradle_cache` and `save_swiftpm_cache` for its runs on main, and the nightly run passes them for its latest Flutter on main. Both are false by default. When jobs save the same key at once, the first one wins. A job still downloads what the cache that it restored lacks, such as what its app needs beyond the cache of another app. So every job that builds for Android puts `.github/gradle/maven_central_mirror.gradle` into `~/.gradle/init.d`, and every build of Gradle there takes what it would download from Maven Central from the mirror of Maven Central that Google keeps. A build that declares no repository of plugins, such as the included build of the Gradle plugin of Flutter, gets the mirror before the Gradle Plugin Portal, which would send it on to Maven Central for the Kotlin Gradle plugin. `tools/workflow_apps_test.dart` fails on a job on Linux that runs Gradle for Android without a step before that puts the script there (`mavenCentralProblemsOf`). Gradle also installs the packages of the Android SDK that an app needs and the runner lacks, such as the NDK of Flutter, in every build for Android. The SDK manager downloads them without retries, and a download that breaks off leaves an archive that it cannot open, so the build fails. So every job builds for Android with `.github/scripts/build_apk.sh`, which runs `flutter build apk` and builds the app again when the build failed that way, three times in all, and `start_app.sh` builds with it too. `tools/workflow_apps_test.dart` fails on a step that runs `flutter build apk` itself (`apkBuildProblemsOf`), and `tools/build_apk_test.dart` tests the script with a command that stands in for `flutter`.

The job `CI` of `build.yml` sums up the other jobs of the workflow: it needs all of them and passes only when each of them succeeded. So it fails on a job that failed or was cancelled, and on any other result too, such as `abandoned`, which the jobs of `apps.yml` have when no runner took one of them. A skipped job counts as passed only in a pull request into a branch other than main, which skips the jobs with Flutter. Every other run runs every job, so there `CI` fails on a skipped job too, and a mistake in the condition of the jobs with Flutter cannot let a pull request into main pass without them. The ruleset of main requires the checks `CI` and `PR title`, so the ruleset does not have to change when jobs come and go. A job added to `build.yml` goes into the `needs` of `CI` too. `tools/build_workflow_test.dart` runs the step of `CI` that sums up the results, and fails when a job is missing in the `needs`, and when `CI` lacks `if: ${{ !cancelled() }}`, without which a failed job would skip `CI` and a ruleset would take the skipped check as passed. A new run of `build.yml` cancels the run of its concurrency group that is still in progress: `build-<number of the pull request>` for a pull request, and `build-<ref>` otherwise. `.github/workflows/cancel.yml` runs when a pull request is closed and joins the group of the pull request with `cancel-in-progress`, so the run of Build of a merged or closed pull request stops; `tools/build_workflow_test.dart` fails when no workflow does so.

When a test of a package or of `tools/` fails in CI, the page of the run lists it at the top as an annotation, with the name of the test, its message, and its file and line. Every `dart test` in the workflows writes a JSON report with `--file-reporter json:build/test-results/<name>.json` in the directory it runs in, under a name that no other run in its job uses. `.github/scripts/each_app.sh` gives the report of the command it runs for each app the name of the app, `<name>.<app>.json`, so that the run for the next app does not replace it. The last step of each job with tests runs `dart tools/test_annotations.dart` whenever Dart is set up, even after a failed step or in a cancelled job. It turns each test in those reports that failed, or that started and never finished, into an annotation. `tools/test_annotations_test.dart` fails when a run of tests in a workflow writes no report or the same report as another run in its job, and when a job with tests does not run the tool after them.

Run the CLI from source. It finds the Flutter SDK through `flutter` on the `PATH` before it generates anything, and runs `flutter pub get`, `dart fix` and `dart format` in the new app:

```bash
cd packages/smf_flutter_cli
dart run bin/smf_flutter.dart create my_app -o /tmp/out --org com.example --no-input --on-conflict replace
```

Modules are chosen with `-m`, and every option of `create` comes from the command line with `--no-input`. `--explain` prints what would be generated and whether the machine is ready, without changing anything.

## Generated files and templates

- `lib/bundles/*_bundle.dart` are generated from `bricks/` by `tools/bundle_bricks.dart`, which `melos bootstrap` runs. Never edit them by hand. Change the brick, re-bundle and commit the result. CI fails if a committed bundle differs from what the bricks produce.
- `bricks/**/__brick__/**` holds mason templates, not Dart. They are excluded from analysis and formatting. They use mason syntax: `{{app_name.snakeCase()}}`.
- Bricks have no mason hooks. The pipeline rejects a brick with hooks and runs none: modules check the machine and run tools through `Preflight` and `PostGenStep` contributions.
- A brick has the same files in every app. A file whose path depends on the data of a role or on its choice, such as one file for each item that the modules give the role, comes from a render hook instead. The hook of the template of the role, or of its provider, returns the text of the file by its path in the app (`RoleOutput.files`). The pipeline takes the file as it is. It renders no mustache in it, fills no tag and adds no import, and `dart fix` and `dart format` of the new app go over such a Dart file as over the rest of the app. In every other way it is a file of the app like those of the bricks. Its path is inside the app, where the kind of the module of a provider may generate files, and no brick or other hook generates the same file. The path comes from data, so it must also be one that every machine can write. It has no control character, no character that Windows forbids in the name of a file, and no segment that ends with a dot or a space. It is not a directory of another file of the app, and it is not inside what is a file of the app, whatever the case of the letters. The owner of the file is the owner of the hook, and the contract harness, the snapshots and the matrix see it like any other file. A Dart file from the hook of a provider may import what the fragments of that hook may. The harness also reports a file of the app, from a brick or from a hook, at a path where code generation or the localizations of Flutter write theirs. The provider of the clock in the fixture package `fake_roles` generates a file for each time zone this way.
- Code of a template that depends on whether a role is in the app is a variable of its brick with a `RoleVar` in `BrickContribution.vars`. A `RoleVar` has the code for an app with the role and the code for one without it, each a `Fragment` with the imports it needs or a string of code that needs none. The pipeline takes the value by the presence of the role, as it applies a contribution by its `when`. So one line of a template serves both apps, where two mustache sections under `has_<role>` would hold the code and its import twice. The role is one that the contributor provides, requires or uses. The variable is a fragment variable in every app, whichever value the app gets, so a template reads it rightly in every app or in none. A template reads it as it is, `{{{name}}}`, never in a path, and only in a Dart library when either value has imports. The pipeline adds the imports of the value that the app gets to the Dart files of the brick that read the variable. A template reads the variable outside every mustache section, also outside that of the presence flag of another role: code that needs a second role goes into a brick of its own, contributed with `when` of that role. A `RoleVar` holds no plain data for mustache, such as a list or a boolean. The variables of a render hook take none, because a hook asks itself for the presence of the roles that its role requires or uses (`RoleHookInput.has`). The module `fake_clock_user` of the fixture package `fake_roles` reads the time zones of the clock this way.
- A brick or role data that only some apps need, by what a role chose rather than by the roles of the app, has conditions on that choice (`Contribution.whenChosen`). Each is a `ChoiceCondition` that the role publishes as a constant. `RouterRole.noStartRoute`, for example, holds in an app that no route starts, and only such an app has the fallback start screen of the app entry. Only `BrickContribution` and `RoleData` take them, because the pipeline needs the other kinds before any role chooses. Validation, `--explain` and lenient mode treat such a contribution as one that applies, so its problems are reported in every app that may have it. Validation also reports four errors: a condition of a role that the contributor does not provide, require or use, as for `when`; data of a role with a condition of that same role, which chooses from its data; conditions on the data of roles that form a cycle; and a tag of a socket in a brick with conditions, because an app that leaves the brick out would lose what the socket gets. The `choose` hook of a role whose data depends on what another role chose runs after the hook of that role, and it gets only the data whose conditions hold. The other roles keep their order (`choiceOrder` of the pipeline). Once every role has chosen, the pipeline decides the collection (`Collection.decide`). Rendering, the render hooks and the checks of the rendered app see only the contributions whose conditions hold, and `ContractResult.hook` and `ContractResult.collection` are built from them. A symbol of the interface of a role can depend on a choice too (`RequiredSymbol.whenChosen`). `RoleInterface.checkSymbols` checks it only in an app where its conditions hold, and an app where one does not must have no file at its path. So such a symbol has a file of its own, which every provider contributes under the same conditions. The registry refuses a role whose symbols at one path have different conditions, and a role with a symbol that has a condition of a role it neither requires nor uses. The contract harness answers the questions of a role as a user who presses Enter, so it checks both sides of a condition only when the data of the modules or a mode option drives the choice.
- A role may have command line options (`Role.options`), such as `--start` of the router role. The `choose` hook of the template of the role reads them, and what it chooses reaches only the render hooks of that template and of the providers of the role (`RoleHookInput.choice`): the contributions of a module are the same whatever the role chose. A mode option, `RoleOption.mode(name, help, values)`, takes one of a closed list of values, and a role declares it when each value makes another app. With it the role states that the code of the app depends on the value, that the first value is the default, and that every value gets apps in the tests. The default is the value of an app that got none. The `choose` hook chooses it when the option is not given and the run has no terminal, and a user who presses Enter at its question gets it too. `optionsOf()` of the template gives the option with its value for every choice, also for one that the template made without asking. The choices of such a role compare by value, and with the same options the role makes the same choice in a terminal and in a run without one. So no run needs the option, and a script written before the role had it generates the same app. A module that is no provider has no hook, so the template of the role writes the value into a file of the role as a constant, and the code of such a module branches on it when the app runs. The registry refuses a mode option with fewer than two values, with a value twice, or with a value that is not of lower-case letters and digits with single hyphens between them, since the values name the apps of the tests. In the fixtures, the clock role of `fake_roles` has such an option, `--clock-hours` with the values 24 and 12: its template writes the constant `clockHours`, the render hook of its provider renders the code of the hours of the app, and `fake_clock_user` reads the constant when the app runs.
- A warning about what the app is made of, such as a destination that no main navigation leads to, has a code: `SmfIssue.warning(message, code: …)`. The code is the id of the role that reports the warning, a dot and a name in lower snake_case, such as `router.no_start`, and the role publishes it as a constant (`RouterRole.noStartWarning`). The `validate` hooks and the module rules of a role return such warnings. A `choose` hook reports a warning that depends on its choice with `RoleChoiceContext.warn`, never through the logger. A warning with a code of another role or of another form is an error of the hook or the rule that reports it. So is a warning about the machine (`SmfIssue.machineWarning`), which only the preflight checks of the pipeline report. Such an error works like any other: lenient mode leaves out the module at fault, and an error of the template of a role stops the run. The warnings of the pipeline itself have codes that start with `pipeline.`, such as `pipeline.unused_option` for an option of a role that the app lacks, so the registry refuses a role with the id `pipeline`. The validation reports `pipeline.unused_option`, before the machine is checked. A run prints such a warning after its origin and without its code. The origin is `[role:router]` for the template of a role and the module for a provider or a module rule, as for `router.ambiguous_routes`. `pipeline.unused_option` has none. `ContractResult.warnings` of the contract harness has the warnings about the app of a case: those of the validation, and those of the choices in a terminal that the app is rendered with. The harness makes the choices of every app again without a terminal, as the matrices generate it, and reports a role that warns of other codes there. It also reports as an error a `choose` hook that warns through the logger, and a warning of a structural rule, since `smf create` runs no structural rule. `smf create --strict` stops on such a warning as it does on an error, and never on a warning about the machine. It stops after the stage that found the warning, so it writes nothing: a warning of the validation stops it before the machine is checked, and a warning of a choice before the app is rendered. `--explain` makes no choices, so `--explain --strict` stops on a warning of the validation but not on a warning of a choice; the same run without `--explain` stops on both. It then prints each warning that stopped it with its code, as `warning [role:router] router.no_start: …`. The hidden option `--allow-warning=<code>` lets a strict run go on after the warnings with that code. It may be given more than once, and a value that is not a code is a usage error. The matrices give each app `--allow-warning` for each code of `MatrixApp.warnings`, which are the codes of the `ContractResult.warnings` of its case. Tests declare by hand which apps warn, and of what. `_warningApps` in `packages/smf_flutter_cli/test/matrix_test.dart` declares them for the CLI, and the test also expects that no app with every module warns: CI builds and starts those apps, and a user gets one with every module. `fixture_registry/test/matrix_app_tests_test.dart` declares them for the apps of the fixtures and the app of several providers, and `fixture_registry/test/broken_providers_test.dart` for the apps whose tests must fail. Such a test prints the actual warnings when they differ, and no variable updates the declaration, since a new warning of an app is a decision: change the app, or declare the warning. A change that adds a warning to an app updates the declarations in the same pull request. A warning that the harness misses stops `smf create --strict` in the jobs with Flutter.
- The pipeline checks the machine for a module after the modules it depends on, directly or not. It does not matter where the user named those modules, or whether the pipeline added them. The checks of a module that comes after one that depends on it run right before those of the first such module. The checks of the other modules keep the order of the modules of the app, and those of the templates of the roles come last. After an installation, the pipeline runs again only the checks after it that have not passed. So a check of a module may need a tool that a check of a module it depends on installs, as `FirebaseCliVersionCheck` of `smf_firebase_core` needs the Firebase CLI. It cannot count on a check of any other module, whose place depends on the order in which the user named the modules.
- A post-generation step may continue another step, such as with a fix of a file that the tool of that step writes: it names that step by its id in `PostGenStep.followUpOf`, runs right after it once that step succeeded, and is left for later with it when that step does not run or fails. It is part of that step, so a run asks the user only about the step that it continues, unless it has a notice of its own. A step that others may continue has an id (`PostGenStepId`: the module that contributes the step and a name), which the module publishes as a constant of its module class. A module continues only its own steps and those of the modules it depends on directly, so a module knows nothing of the modules that continue its steps. The pipeline reports a step with the id of another module, two steps with one id, a step that the module may not continue or that the app does not have, a `when` on a step that continues another, and steps that continue each other in a cycle.
- A step with a notice (`PostGenStep.notice`) runs only once the user agreed to it. The notice is what the user has to know before the step runs and cannot learn from its description, such as a side effect of the tool that it runs. A run in a terminal asks about the step when the step can run, with the notice in the question, even when the step continues another. That question comes once the step that it continues succeeded, and Enter answers yes, as for every step. The run does not ask about a step that cannot run: one that needs external setup in a run that skips it, one that needs a check which has not passed, or one whose tool is missing. Such a step is left for later like any other. A run that cannot ask leaves the step for later, although it runs a step without a notice unasked. When the user declines a step, the steps that continue it are left for later after it, without a question. The notice follows the command of a step that is left for later, whatever the reason, and `--explain` shows it under the command. So it is one line that reads on its own in each of these places, and the pipeline reports a notice that is blank or has a line break. The user may decline the step, so it has to be skippable, and the pipeline reports a step with a notice that is not.
- When a run ends, it tells of the steps that are not done, in two ways. A step that could not run or failed is a warning, before the line that the app is created (`SkippedStep.failed`): a check that it needs has not passed, its tool is missing, or its command failed. A step that was left for later is no warning, since nothing went wrong: the user or the options of the run left it, or it continues a step that is not done. The run lists those steps after that line with `logger.info`, in the order in which they run. Each has what it does, the reason in parentheses, its command on a line of its own and its notice below the command. The pipeline never wraps a command, because the user copies it. Several steps are numbered, and a step that was left with a step of the list gives the number of that step as its reason, which the pipeline finds through `SkippedStep.after`. A step that continues a step that failed names it by its description. A step that the run would leave for later anyway stays one when a check that it needs has not passed either, and its reason names the check too. After the list, an app with steps by hand (see `ManualStep` below) gets one more message with `logger.info`, when the front end names their guide: `Finish the setup by hand in 2 steps:`, or `in one step:`, with the link on a line of its own below it, indented like a command and never wrapped. The run asks nothing about those steps, so a run with `--no-input` or `--skip-external-setup`, or without a terminal, prints the same message. Then come the lines on running the app, as `Then run the app:`. They only tell the order, because the pipeline does not know which step an app needs to start. A run that left no step for later ends with `Run it:`, whether the message of the steps by hand comes before it or not. A test of what a run prints of such a step checks the level of the message too.

## Tests

- Tests live in each package's `test/`. Sonar counts coverage only within the package that runs the tests, so a module's code needs tests in that module.
- Keep coverage at 100% of the lines and branches of `lib/` with tests that pin behavior someone relies on, never with tests that only touch a line. Remove code that cannot run instead of covering it. Code that no automated test can run, such as the terminal of a user, goes between `// coverage:ignore-start` and `// coverage:ignore-end`, with the reason in a comment next to it. Don't use `coverage:ignore-file`, which the banlist fails on: the file then drops out of `lcov.info` and Sonar counts all of it as uncovered. `melos run test:coverage` measures branches as well as lines, and `melos run coverage:check` after it fails on any line or branch of `lib/` that the tests do not cover, with its `path:line`. CI runs both.
- The contract harness of `package:smf_pipeline/testing.dart` checks a module against the rules of the roles it declares and renders every app it can be part of. `packages/smf_flutter_cli/test/modules_test.dart` runs it over every module the CLI offers, and a module package runs it over itself in its own tests. New modules must pass it.
- For a module, the harness builds a case for each subset of the roles it only uses and each combination of providers of the role of its variants, of each role it requires and of each role of the subset. It leaves out a combination of providers that would give an app two providers of a role that takes one, such as another router next to a module that depends on go_router, unless no combination of the subset can be in an app with the module; then it keeps them all, and their cases report why. A case names the provider of each of its roles that has several in the registry, such as `fake_analytics (get_it) with di`, so the names change when a role gets a second provider. For each package of a provider of a role that a module adds, the harness also builds a case of the module with that provider, `<module> with <provider>` or `<module> (<provider of its variant>) with <provider>`, when they can be in one app. So the registry of a module's tests holds the providers of the roles it requires or uses, the providers it has variants for, and the providers whose packages it adds, and the harness builds an app of the module with each. `ContractHarness.uncheckedProviders()` lists each provider of a role that a module requires or uses which can be in an app with the module but provides the role in no app of the cases of the module; `packages/smf_flutter_cli/test/modules_test.dart` and `packages/smf_pipeline/fixture_registry/test/fixture_registry_test.dart` expect none.
- For a role with a mode option (`RoleOption.mode`), the harness builds one more case of each provider of the role for each value of the option after the first. It is the first case of the provider, which has every role that the role uses, with the value among the options of the case (`ContractCase.roleOptions`), and its name ends with `--<option>=<value>`, as in `clock by fake_clock_badge --clock-hours=12`. The other cases leave the option out, so their apps have its first value. `ContractResult.appKey` has the options of a case, so `checkAll()` keeps such a case next to the case of the same modules, and the matrices generate its app with the option. `ContractHarness.casesOfModes()` has the cases of the apps with every module (`casesOfAll()`) once more for each other combination of the values of the mode options of the roles of each app. An option that the harness gives every case (`ContractHarness.roleOptions`) has no cases of its own. In every app with such a role that it renders, the harness makes the choices twice: in a terminal, where it answers as a user who presses Enter, and without one, as the matrices generate every app. In both runs it holds the choice of the role to the option, by the value that `optionsOf()` of the template gives for the choice: with a value of the option the choice has that value, and without one it has the first value. No role may fail or ask in the run without a terminal, and the harness names the role that does. The two choices of the role must be equal, so its choices compare by value. The harness also reports a value that a case gives an option which does not take it (`RoleOption.allowed`), since the command line would refuse it. So the package of a provider of such a role renders its hook for every value in its own `checkAll()`, and a second provider gets these cases without a change of the tests. The harness reads the options from the roles of its registry and names no role itself.
- A change of the steps by hand of a module of the CLI (`ManualStep`) needs `dart run tool/setup_steps.dart` in `packages/smf_flutter_cli`, which writes `setup_steps.json`, and the new file on the site of SMF with a guide for each new step: `test/setup_steps_test.dart` fails until the file is written.
- Generator tests check generated code for real: they parse it or type-check it with the analyzer, not just string-match.
- Tests are hermetic: no network, no Flutter SDK, temp dirs cleaned up. The few that need more skip themselves unless CI provides it: an app from `flutter create` (`SMF_FLUTTER_CREATE_APP`), an app with Crashlytics to archive on macOS (`SMF_CRASHLYTICS_APP`), an app with Crashlytics that flutterfire configured for iOS, to fix its build phase for Crashlytics on macOS (`SMF_CONFIGURED_APP`), an app with Firebase to configure with flutterfire for a platform in a Firebase project, with the key of a service account of the project (`SMF_FIREBASE_APP`, `SMF_FIREBASE_PLATFORM`, `SMF_FIREBASE_PROJECT`, `SMF_FIREBASE_SERVICE_ACCOUNT`, and `SMF_FIREBASE_REGISTER=1` to let flutterfire register the app in the project when the project has none with its id), an app with firebase_auth that flutterfire configured, to ask its Firebase project for its sign-in methods (`SMF_CONFIGURED_APP` and `SMF_FIREBASE_PROJECT`, and to enable them there first `SMF_FIREBASE_ENABLE_SIGN_IN=1` with the key in `SMF_FIREBASE_SERVICE_ACCOUNT`), the request of an app that CI started, with the address of its device, to send a push message to in its Firebase project with the key of a service account (`SMF_START_REQUEST`, `SMF_FIREBASE_PROJECT`, `SMF_FIREBASE_SERVICE_ACCOUNT`), or a machine where the Firebase CLI may be installed (`SMF_INSTALL_FIREBASE_CLI=1`).
- A bug found but not fixed gets a test for the *correct* behavior, marked `skip: 'Bug: <description>'`. Never write a test that locks buggy behavior in. The fix removes the `skip`.

## Git and PRs

- Use [Conventional Commits](https://www.conventionalcommits.org/) with the package's short name as scope: `fix(go_router): ...`, `feat(contracts): ...`, `test(cli): ...`, `chore(ci): ...`. `melos version` derives version bumps and CHANGELOGs from them.
- Name branches `fix/<topic>`, `feat/<topic>`, `chore/<topic>`, `docs/<topic>`, `test/<topic>`.
- A PR is squash-merged: the squash commit takes the title of the PR as its only line, so the title must be a Conventional Commit too, and CI checks the title of every PR (`.github/workflows/pr-title.yml`). A breaking change needs `!` in the title, such as `feat(contracts)!: ...`: a `BREAKING CHANGE:` footer in a commit of the branch does not reach main.
- A larger change may collect its PRs in a branch of its own. The PR of that branch into main is merged with a merge commit rather than squashed, so that each commit of the branch, such as the squash commit of each of its PRs, reaches main as it is, and `melos version` reads each on its own. So the `!` of a breaking change goes into the title of the PR into that branch that makes the change.
- Once a branch is pushed, add new commits on top. Don't force-push or rewrite pushed history unless a maintainer asks.
- Don't bump package versions or edit CHANGELOGs by hand. `melos version` does both, and its preCommit hook syncs `packages/smf_flutter_cli/lib/version.dart`.
- Keep PRs focused: one concern per PR, one logical change per commit.
