# AGENTS.md

Guidance for AI coding agents working in this repository. Human contributors: see [CONTRIBUTING.md](CONTRIBUTING.md) and [README.md](README.md). The documentation for users and module authors is at [doc.saymyframe.com](https://doc.saymyframe.com).

SMF (Say My Frame) is a Flutter CLI (`smf create`) that generates apps from independent modules (routing, DI, Firebase, features, ...). It is a Dart pub workspace managed by Melos. Every package is versioned and published to pub.dev on its own.

## The module model

- A module declares the roles it provides, requires or uses (router, DI, state management, ...) instead of depending on the modules that implement them. It puts code into typed sockets instead of patching files, and never learns which provider of a role was selected. The model is `package:smf_contracts/smf_contracts.dart`; `package:smf_contracts/core.dart` is its core without concrete roles.
- `packages/smf_pipeline/` is the generation pipeline of `smf create`. It imports only `core.dart` and knows no concrete module or role; `test/architecture_test.dart` checks this.
- The CLI offers the modules listed in `packages/smf_flutter_cli/lib/src/modules.dart`:

  | Package | Module (`-m`) | What it is |
  | --- | --- | --- |
  | `smf_flutter_core` | `flutter_core` | Provides the app entry, which every app has exactly one of (`FlutterCoreModule`, brick `bricks/flutter_core`). Its fallback start screen, which an app without a route to start on shows, names the app and tells its developer where the first screen goes. The module uses the localization role for the two texts of that screen. |
  | `smf_go_router` | `go_router` | Provides the router role. |
  | `smf_bloc`, `smf_riverpod` | `bloc`, `riverpod` | Provide the state management role; an app has at most one. |
  | `smf_home_flutter` | `home` | The feature `home` (`HomeModule`), the start screen at `/home`: a welcome to the developer of the app, with the name of the app, a greeting by the time of the day, a card in the colours of Say My Frame and three next steps, each with a path that a tap copies. It requires the router role, and uses the localization role for the texts of its screen and the label of its destination. The module takes the symbol and the number of the cell on the card from the name of the app with `SmfNames.elementSymbolOf` and `SmfNames.elementNumberOf` of the contracts, as every module that shows the app as such a cell does, so that the screens of an app show the same ones, and keeps the image of the mark that the screen shows in the folder of the feature, `lib/features/home/assets/`, which it declares in the pubspec of the app. |
  | `smf_settings` | `settings` | The feature `settings` (`SettingsModule`), the settings screen at `/settings`; provides the settings screen role, whose entries the modules of the app and the templates of its roles contribute, requires the router role, and uses the localization role for the title of its screen, which is the label of its destination too. The screen shows the entries in one group, and in an app whose modules have no setting a note for the developer of the app instead, in English: its provider renders the one or the other by the entries of the role. |
  | `smf_bottom_tabs` | `bottom_tabs` | Provides the layout role: tabs in a bar at the bottom for the destinations of the features, which the router builds its main navigation around. The layout requires the router role. |
  | `smf_material_theme` | `material_theme` | Provides the theme role: a light and a dark Material 3 theme in `lib/core/theme/app_theme.dart`, the file that a developer edits for another look, with a palette, text styles and the look of the components. Its brick has the files of the font of the themes with their licence, in `assets/fonts/geist/` of the app, and the module declares the family in the pubspec: an app loads no font from the network and gets no package for it. The theme mode that the user selects is the role's, with every provider: its template remembers the mode in the preferences, which the role requires, and adds its entry to the settings screen. |
  | `smf_gen_l10n` | `gen_l10n` | Provides the localization role with gen-l10n of Flutter: it writes the texts of the modules into ARB files, one for each language of the app, and `flutter pub get` generates the class through which code reads them. |
  | `smf_get_it` | `get_it` | Provides the dependency injection (DI) role and registers in get_it the services that the modules of the app declare. |
  | `smf_event_bus` | `event_bus` | Provides the events role: a service on the event_bus package through which parts of the app that do not know each other exchange events. |
  | `smf_shared_preferences` | `shared_preferences` | Provides the preferences role with the shared_preferences package: the settings of the app that are no secret, such as the theme mode, which the app remembers between its launches. |
  | `smf_onboarding` | `onboarding` | The feature `onboarding` (`OnboardingModule`), the onboarding at `/onboarding`, which a new user goes through on the first launch: its guard of the routes keeps the user there until it is finished, and the app remembers that. `onboardingStatus.restart()` shows it again. It requires the router role and the preferences role, and uses the localization role for its texts. |
  | `smf_firebase_core` | `firebase_core` | Infrastructure without a role that sets up Firebase; a run in a terminal offers it among the modules of its kind. |

- Within `smf_contracts`, `test/architecture_test.dart` keeps the core free of concrete roles. A module package checks in its own `test/architecture_test.dart`, with `ModulePackage` of `package:smf_pipeline/testing.dart`, that its code uses only the module model and the modules it depends on, and what the package depends on. `roleClassNameProblems` of the same library checks that the code in `lib/` of a package and of the module packages it depends on takes the name of each class that a role requires from the role, such as `LayoutRole.appShell.name`, rather than spelling it out in a string; `test/role_class_names_test.dart` of `smf_flutter_cli` and of `fixture_registry` runs it. A module package other than `smf_flutter_core` renders the apps of its tests with `smf_flutter_core` as a dev dependency, for their app entry; its `lib/` imports no other module but those it depends on. Nor does a module package name the modules that depend on it: `packages/smf_flutter_cli/test/modules_test.dart` fails when the `lib/` of a module package, but its bundles, or its `bricks/`, `example/` or `README.md` has a word of the id of such a module that the id of the module of the package lacks, whatever its case and also inside a camelCase name, such as `crashlytics` in `smf_firebase_core`. Dev dependencies between module packages must not form a cycle, because pub.dev resolves them when it analyzes a package: `smf_flutter_core` has none on modules, and of two modules whose tests need each other's role, one tests with a provider of its own in `test/`. `tools/package_graph_test.dart` checks the packages of the workspace for a cycle.

## Layout

```
packages/
  smf_contracts/              # the module model: modules, roles, sockets, contributions
  smf_pipeline/               # the generation pipeline of `smf create` and the contract test harness
    fixture_registry/         # the apps of the fixtures: snapshots, their Flutter matrix with its app tests, the app of several providers, and the apps of the broken providers
    test/fixtures/            # fake modules for the features of the model that no real module uses yet, and providers of roles with a known bug
  smf_modules/
    smf_contribution_engine/  # a standalone engine that patches Dart files; no module uses it
    smf_<module>/             # first-party modules: go_router, get_it, firebase_*, event_bus, shared_preferences, home, settings, onboarding, flutter_core, bloc, riverpod, bottom_tabs, gen_l10n, material_theme
  smf_flutter_cli/            # the `smf` binary: the modules it offers, and the terminal, files and processes of the machine
tools/                        # bundle_bricks.dart and sync_cli_version.dart; banlist.dart, coverage_check.dart, native_build.dart, test_annotations.dart and workspace_members.dart with their tests; package_graph_test.dart, build_workflow_test.dart, workflow_apps_test.dart, each_app_test.dart, start_app_test.dart, firebase_registration_test.dart, flutterfire_version_test.dart, sonar_lcov_test.dart, matrix_plan_test.dart, app_tests_test.dart, app_test_imports_test.dart and workspace.dart, which the last two share; the tools read the members of the workspace with workspace_members.dart, the only file that reads them from the root pubspec, as banlist.dart checks
```

Dependencies point one way only: `smf_contracts` ← `smf_pipeline` and modules ← `smf_flutter_cli`. Contracts never depend on modules, the pipeline or the CLI; the pipeline never depends on a module. Modules use `smf_pipeline` only in their tests, for the contract harness.

## The core principle: modules are independent

Module independence is the foundation of the project. Never break it, not even to fix a bug quickly.

- A module knows **only** the modules it lists in `ModuleDescriptor.dependsOn`, and only in one direction. For example, `firebase_analytics` depends on `firebase_core`, but `firebase_core` knows nothing about its dependents.
- A module never references another module's generated artifacts (classes, files, packages) unless it declares that dependency, and it should avoid needing to.
- Nothing is hardcoded for a particular combination. Any selection of modules and variants (e.g. state manager `bloc` / `riverpod`) must generate an app that compiles.
- Modules describe *what* they need through the DSLs in `smf_contracts`: routes, and the guards that keep the user from them until a condition holds (`RoutesData` of the router role), DI (`DiRegistration` of the DI role), the entries of the settings screen (`SettingsEntry` of the settings screen role), the texts that a user sees (`TextsData` of the localization role), code for sockets (`SocketContribution`s) and bricks. The providers of those roles turn the descriptions into code, and the contract harness checks that the files of the provider of the DI role call or tear off the factory of every registration and its dispose function (the rule `di.registrations_rendered` of the role), and that the files of the provider of the settings screen role create the widget of every entry, through an import of its file with a prefix that no import of another file has (the rule `settings_screen.entries_rendered`). It also checks that the files of the provider of the router role create the `GuardedNavigation` that the role generates in an app with guards and read `guardChanges` (the rule `router.guards_asked`). Only the tests of the role in a running app show whether the provider asks the guards as the role says. In an app with a layout and destinations, it checks that those files read `appDestinations`, the list of the destinations that the layout role generates (the rule `router.destinations_shown`). A feature module must not assume a specific router or DI container, and neither do its tests. They check what the module gives a role through the data of the role, which the role reads from `ContractResult.hook`, the hook request of the app of a case of the harness, with functions such as `diRole.graphOf(diRole.hookInput(result.hook!))`, `routerRole.startIn`, `layoutRole.destinationsIn`, `settingsScreenRole.entriesIn` and `localizationRole.textsIn`, and through what each socket got, in the order the pipeline rendered it, with the fragments of the render hooks of the roles (`RenderedApp.socketOrders`). They tell the files that a provider changed by their owner, and never read `RouterRole.appRouterFactoryFile`, `DiRole.dependenciesFile`, `LayoutRole.appShellFile` or `LocalizationRole.textsFile`, in which the providers of those roles render what the modules give them, nor `AppEntryRole.bootstrapFile`, `AppEntryRole.mainFile` and `lib/app.dart`, into which the provider of the app entry renders the start-up and the root of the app. Only the package of the provider tests those files. `tools/banlist.dart` bans their constants and paths in the tests of the module packages, except as the key of a map, for the files of a provider that a test defines, and in the tests of the package that provides each. Nor do they read the screen in which the provider of the settings screen role shows the entries: it is a file of that provider, which no role names, so the banlist does not know it. `packages/smf_flutter_cli/test/modules_test.dart` fails when a test of a module package takes more of the class of a module of another package than its `id`, such as the directory in which a provider writes its files, unless its module depends on that module.
- Generated UI talks only to its state-management layer (a Cubit via `context.read`, a Riverpod provider via `ref`), never directly to a DI container or infrastructure service.
- The preferences role keeps the settings of the app that are no secret, such as the theme mode. A token, a password, an API key or an encryption key never goes there. A module, or the template of a role, that remembers a setting gives the role a restorer (`PreferencesRole.restorers`), a function that gets the preferences in the platform phase of `bootstrap()`, reads its keys and keeps the preferences for its writes. A restorer is synchronous and awaits nothing: the role does not wait for an asynchronous one and does not catch what it throws. A key is `<owner id>.<setting>`, such as `theme.mode`, where the owner is the module or the role whose code keeps the setting. No module and no template of another role calls `createAppPreferences()`, and only `bootstrap()` calls `initPreferences()` (the rule `preferences.factory_calls` of the role). A restorer keeps the current value when nothing is saved under its key, and may run more than once, since `initPreferences()` runs again in a test of the next launch of the app. An app test shows that a setting is remembered by writing its key through `AppPreferences`, running `initPreferences()` again and reading the state, and that it is saved by reading the key after a choice; running `initPreferences()` again right after a choice proves nothing, since memory has the value already. Nor does it stand for the next launch once a key was removed: the restorer then keeps the value that the state has. A test of code that takes `AppPreferences` from a DI container also runs `resetDependencies()` and `registerDependencies()` once `initPreferences()` ran again, since the container keeps the object of the earlier open.
- A text that a user sees is a `LocalizedText` of the module that shows it, with its English text and its translations by the code of their language. The module gives its texts to the localization role as `TextsData` and only uses the role, so it works in an app without it too. Its bricks read each text through a variable of `localizationRole.varsOf`, as in `Text({{{text_title}}})`: `context.l10n.<getter>` in an app with the role, where the getter starts with the id of the module (`settingsTitle`), and the English text as a literal in an app without it. A template reads the variable where a `BuildContext context` below the root of the app is in scope, and not inside a `const` expression, since the code of an app with the role is no constant. The rule `localization.texts` of the role reports a variable whose text the module did not give the role, or whose English text differs from that of the text. The template of a role gives its texts the same way and reads them in its render hook with `localizationRole.expressionOf`. The data that a module gives another role can have texts too, such as the label of a destination in its routes (`Destination.label`), and such data implements `DataWithTexts`. The template of the role that shows them requires or uses the localization role and reads each with `localizationRole.expressionOf` too, as a text of the module. For a text of a module, the code is `context.l10n.<getter>` only when the module gave the localization role that text, and the English text otherwise, so the app never reads a text that it lacks. A module that lists the localization role gives it each such text among its `TextsData`, and the rule `localization.texts` reports one that it did not give, and one that differs from the text of that name that it gave. It also reports two texts of one name that differ in the data of a role: the app reads a text of a module by its name, so it would show the same text for both. A module that does not list the role shows such a text in English in every app, so the text takes no translations: the module rule of the role of the data reports a translation there, with `localizationRole.dataTextProblems`, as `router.routes` does for a label. The provider of the role renders a getter for each text in the languages of the app: those that the texts are in, English first, or those of `--locales`. An app can be only in a language in which Flutter has the texts of its own widgets, one of `LocalizationRole.supportedLanguages`, the set of the oldest Flutter that the apps allow. The role leaves any other language of a text out of the app with a warning that names the module and the text, and `--locales` refuses it. A module brings no delegate for texts of its own and adds no language to the root of the app, because every delegate of the root has to support each language that the role chose. The `supportedLocales` of the root take the items of one contributor (`ArgShape.listOfOneContributor`), and in an app with the role that contributor is its template. So the pipeline reports a module that gives the root a locale of its own there as a conflict, and reports it to the module. The rule `localization.text_access` of the role keeps the code of a module to its own texts and to those of the modules it depends on; it sees a text that code reads from `context.l10n` or from a variable called `l10n`. The template of another role reads its own texts. Of the texts of the modules, it reads those that the modules give, in data with texts, to its role or to a role that its role requires or uses, since it shows them. The rule takes that data from `StructuralRuleInput.inputOf`. It gives a rule what the hooks of a role get, but only for a role of the app that requires or uses the role of the rule. It cannot tell a read that the template of a brick has in its own code from one that a render hook wrote for the data. So a template that names such a text of a module passes in an app with the module. In an app without the module, the app lacks the text and the rule reports the read. The rule `localization.texts_rendered` checks that a file of the provider names the getter of every text. The template of the role writes the section `LocalizationRole.readmeHeading` of the README of the app from its render hook: where the languages of the app are, how the app comes to be in another of them, and each place that a new language goes into, which in an app with a settings screen includes the setting of the language. So a provider tells in a section of its own only where its texts are, how to add one and what its texts need for a new language. In the fixtures, `fake_second` of `fake_feature` has texts, and `fake_l10n` of `fake_infra` provides the role with the texts of the app in one Dart file. In the CLI, `gen_l10n` provides it: its render hook writes an ARB file for each language of the app (`RoleOutput.files`), with a text under the name of its getter, and leaves a text out of the file of a language that it has no translation into, so that gen-l10n takes the English one. SMF writes no code that reads the ARB files: `flutter pub get`, which `smf create` runs in the new app, generates it as `l10n.yaml` says. So the tests of `smf_gen_l10n` parse the ARB files and `l10n.yaml`, and type-check the code of the app against a stand-in of the class that gen-l10n would generate from them.
- The localization role remembers the language that the user chose, so it requires the preferences role. `appLocale.choose()` of `lib/core/l10n/app_locale.dart` takes one of `appLocales`. It also takes a locale of the language of one of them, such as `Locale('uk', 'UA')`, which then is the choice, and it refuses a locale of another language with an `ArgumentError`. The file tells the languages of the app apart by their codes alone, so `appLocales` has one locale for each language: of two locales of one language, `choose()` takes the first. It changes the language and then saves its code under `LocalizationRole.localeKey` (`localization.locale`). With `null` the app follows the device again, and the key is removed. When the preferences fail to save a choice, the future of `choose()` completes with their error: the app stays in the new language while it runs, and its next launch starts with what was saved before. The file keeps the constructor of `AppLocaleController` and the key to itself, so other code reads `appLocale.value` and calls `choose()`, and a test takes the key from the role. The template of the role gives the preferences the restorer `restoreAppLocale()`, which takes a saved code only when it is one of the languages of the app. The role also uses the settings screen role. In an app with a settings screen, its template adds `LanguageSetting` (`LocalizationRole.languageSettingFile`), an entry of that screen that lists the languages of the app and the choice to follow the device. The entry reads the choice from `AppLocaleScope` and changes it with `appLocale.choose()`. It names the languages of `LocalizationRole.languageNames`, English and Ukrainian, each in its own language, and shows any other language by its code. In an app with a settings screen, the choice of the languages warns of each such language and tells the developer of the app to add its name to `_names` in the file of the entry. Its hook asks whether the app has a settings screen with `RoleChoiceContext.has()`. The entry has two texts, `LocalizationRole.languageSettingTitle` and `languageOfDevice`, which are texts of the template of the role. The template gives them to the role only in an app with a settings screen (`when: {settingsScreenRole}`), and the same goes for the brick of the entry.
- The layout role is the main navigation of the app. A feature makes a top-level route a destination with `Destination(label:, icon:)` in its routes, and the template of the role generates `lib/core/layout/destination.dart` (`LayoutRole.destinationFile`) with the class `Destination` and with `appDestinations` (`LayoutRole.appDestinations`), the destinations of the app in the order of the features. The label of a `Destination` of the app is a function that takes a `BuildContext` and returns the text. For each destination the file has a top-level function, which reads the text of the module from the texts of the app or returns its English text, so the list is a constant and a release build can tree-shake the icon fonts. The router gives `AppShell` of the provider that list and has a branch for each destination in the same order, so no router renders a label or an icon. A layout shows a label with `destination.label(context)` in the `build` of the widget that shows it and keeps nothing of what it returned, so the label follows the language of the app. The file imports what the icons of the features need, and an icon may come from a file of its feature. So the contract harness lets the code that a render hook gives import the files of the modules that give data to the role of the hook, or to a role which that role requires or uses. This holds for the template of a role and for its providers, and for two kinds of import: one that the pipeline adds for a fragment of the hook (one of `RoleOutput.fragments`, or a fragment variable), and one in a file that the hook generates. The pipeline tells the harness which fragments a render hook gave (`AddedImport.fromHook`). No other import reaches a file through the data. The template of a brick gets none for an import that it has itself, and a contribution gets none for a fragment of its own, such as a socket contribution or the code of a `RoleVar`, because a contribution is the same whatever the modules give the role. The harness reports such an import with a hint. A render hook that names a file of a module itself still passes in an app with that module; the cases of its owner without the module report it.
- The theme role is the look of the app in a light and in a dark theme, and the theme mode that the user selects: light, dark, or the one of the device. An app has at most one provider of the role. The provider generates `lib/core/theme/app_theme.dart` (`ThemeRole.appThemeFile`) with `createLightTheme(context)` and `createDarkTheme(context)`. Each takes the `BuildContext` of the root of the app and returns a `ThemeData`. That context is below the root wrappers and above the root `MaterialApp`, so it has neither the theme nor the localizations of the app. A provider whose look depends on state of its own, such as a colour that the user picks, puts an inherited widget with that state among the root wrappers and reads it from the context, and the root rebuilds when the widget notifies. The template of the role does the rest, whichever module provides the role. It generates `lib/core/theme/theme_mode.dart` with `appThemeMode` and `AppThemeModeScope`. The `value` of `appThemeMode` is the `ThemeMode` of the app, and its `choose(mode)` changes the mode at once and saves it. `AppThemeModeScope.of(context)` returns the mode and rebuilds the widget of that context when the mode changes. So a widget reads the mode from the scope, and code changes it on `appThemeMode`. The language of the localization role has the same shape, with `appLocale` and `AppLocaleScope.of(context)`. The template puts the scope around the root of the app and gives the root `MaterialApp` its `theme`, its `darkTheme` and its `themeMode`. The `themeMode` reads the scope from the context of the root, so the root rebuilds in the mode that the user selects. Each of the three arguments takes one value, so the pipeline refuses an app with the role and a module that sets one of them. The role requires the preferences role: the mode is saved under `ThemeRole.modeKey` (`theme.mode`) as the name of the `ThemeMode`, and the restorer of the template takes it from there when the app starts. In an app with the settings screen role, the template also generates `lib/core/theme/theme_mode_setting.dart` with `ThemeModeSetting`, the entry of the settings screen in which the user selects the mode. The texts of the entry are texts of the template, in English and in Ukrainian, and the template gives them to the localization role only in an app with a settings screen. The mode and its entry belong to the role: a provider adds no entry for the mode, and a provider with a setting of its own for its look contributes an entry of its own. A screen of a module reads the theme with `Theme.of(context)`, in an app with the role and in one without it. A test selects a mode with `appThemeMode.choose(mode)` and reads it from `appThemeMode.value`. The app has one controller, and two things about it outlive a test and reach the next test of the same file: its mode, and the preferences of the last start. From the first start on, `choose` saves through those preferences, also before the next start. So a test that selects a mode chooses `ThemeMode.system` again when it ends. That choice saves `system`, so a test that needs nothing saved removes `ThemeRole.modeKey` from the preferences. In the fixtures, `fake_theme` of `fake_infra` provides the role with themes of a colour that it keeps and that a test changes, and `fake_sockets` gives the root no theme.
- State-manager variants: a module whose code depends on the state manager declares `Variants` of the state management role in its descriptor, keyed by the id of each provider (`bloc`, `riverpod`), and each variant adds the package of its state manager with the constraint `any`, leaving the version to the provider (see the fixture `fake_feature` in `packages/smf_pipeline/test/fixtures/`).
- The package of a provider of a role, such as `flutter_riverpod` of `riverpod`, goes into another module only through its variant for the provider, with the constraint `any`, or through its `dependsOn` on the provider: the pipeline rejects any other module that adds it in an app with the provider. A module that imports or exports such a package adds it itself, even when it depends on the provider; a provider of a role may import, for a fragment or in a file that its render hook generates, the package that a module which gives the role data adds.

## Commands

Dart 3.12.2 is pinned in CI (`.github/workflows/build.yml`). The formatter output depends on the SDK version.

```bash
melos bootstrap             # resolve the workspace and re-bundle every brick (needs the Mason CLI: dart pub global activate mason_cli)
melos run format            # format lib/test/bin/tool/app_tests/example of every package, and tools/
melos run analyze           # dart analyze --fatal-infos --fatal-warnings, every package and tools/
melos run banlist           # no file uses a name that the repository bans, such as one the module model replaced (tools/banlist.dart)
melos run test              # dart test in every package with a test/ dir, and in tools/
melos run check             # format:check + analyze + banlist + test
melos run test:coverage     # test, and write coverage/lcov.info and a report of the tests in build/test-results/ of each package (needs dart pub global activate coverage)
melos run coverage:check    # after test:coverage: the tests cover every line and branch of lib/ (tools/coverage_check.dart)
```

CI has a job that runs these checks, with coverage for SonarCloud, and jobs with Flutter that generate apps with `smf create --no-input --skip-external-setup --no-dart-fix --strict` and run `flutter analyze` on each: `packages/smf_flutter_cli/tool/matrix.dart` for the modules of the CLI and `packages/smf_pipeline/fixture_registry/tool/matrix.dart` for the fixture modules. Each takes a directory for the apps and needs `flutter` on the `PATH`. Then it copies into each app the tests that apply to it (`MatrixAppTest`), from the `app_tests/` directories of the packages, such as the start-up of Firebase with its platform side mocked, adds the dev dependencies of those tests with `flutter pub add dev:…`, and runs `flutter analyze` and `flutter test`: tests of what only a running app shows, which are not part of the generated apps. A library of the package of each tool registers its tests: `smfAppTests()` of `packages/smf_flutter_cli/lib/matrix_app_tests.dart`, which no other library of the CLI imports, and `fixtureAppTests()` of `packages/smf_pipeline/fixture_registry/lib/matrix_app_tests.dart`. The fixture registry keeps most tests of the router role. `router_screens` checks that the router calls the listeners of the screen once for each screen the user sees, its error screen included, gives each navigator observers of its own, closes the route on top with the back button of the system and creates its configuration once (`router_config_test.dart`). `router_listeners` checks, in the apps with the listeners of the screen of the fixture analytics and of the fixture screen log, that the router calls each listener on its own, as `RouterRole.screenListeners` asks, so that one that throws keeps no other from hearing the screen and what it throws reaches no handler of the errors of the app. `router_fallback` checks the fallback screen of the app entry, which the router shows when no route starts the app. `router_guards` checks what the role says of the guards of the routes (`RouterRole.guardedNavigation`), in the apps with every fixture that have the fixture gates, whose guards a test closes and opens. The router shows the target of the first guard that does not allow in place of the location that the app starts on. It does the same for each location outside the flow of that guard that `go()`, `push()` or `replace()` is asked to show, from the target and from another page of the flow: the target is then the only page, and such a `push()` completes with `null`. When a guard starts or stops allowing, the router shows what the role answers. That is the target, in place of the pages that the guard keeps the user from. Once the guards allow it, it is the latest location that was asked for, with its query, or the location below the pages that pushes showed. And when a flow is over with no location to come back to, it is the screen that the app starts on. The user also comes there when the code of the app called `go()` to the target of a guard and then closed the guard, in one handler, as a sign-out does: the guard took the user from no location, so the next user does not come to the page that the last one was on. A pull request into another branch, such as one that collects the pull requests of a larger change, runs only the job of the checks; the jobs with Flutter run later, in the pull request of that branch into main. `nightly.yml` runs them every night, and when someone starts it by hand, with every stable release of Flutter that the generated apps allow. `packages/smf_flutter_cli/tool/flutter_versions.dart` finds those releases: it intersects the Flutter and Dart constraints of the apps of the matrix of the CLI, which the pipeline merges from the `PubspecContribution.environment`s of their modules, and takes the releases from the lists that Flutter publishes for Linux, macOS and Windows. The jobs on Linux run with each of them, and the jobs on macOS and Windows with the oldest and with the latest patch of each minor version. With the latest release, the jobs of the matrices check every combination of the providers, or a 3-wise covering of more than 100 (the input `every_combination`), in more shards, while the apps that CI builds and starts stay the pairwise coverings. The job of the broken providers runs only with the latest release: whether the tests of the roles fail on the bugs hardly depends on the release, but for how flutter_test reports a failure, which a new release may change. The nightly run skips the jobs without Flutter, and the comparison of the brick of `flutter_core` with `flutter create`, since the brick follows the template of the pinned Flutter. It also checks what users install: the job `CLI from pub.dev` of each version activates `smf_flutter_cli` from pub.dev with `dart pub global activate`, which resolves its dependencies from pub.dev rather than from the workspace, generates with it the apps with every module of that release, one for each combination of the providers of the roles that take one, with the full `dart fix`, and runs `flutter analyze`, `flutter test` and `flutter build apk --debug` in each. The CLI on pub.dev has the modules of its release, which may differ from those of the workspace, so `packages/smf_flutter_cli/tool/every_module_apps.dart`, run in a package of its own that depends on the active version, prints the arguments of `smf create` of those apps from `matrixOf` of the release, and the workflow names no module there either. A release without the plan of CI cannot cover them, so this job alone checks its apps one after another. A failure there affects the users of the published version, and its fix needs a release. Maven Central answers 403 to a runner that downloads too much, so what Gradle downloads for the Android builds goes into a cache, and so does what Swift Package Manager downloads for the iOS builds (`~/Library/Caches/org.swift.swiftpm`). Each cache serves every version of Flutter and is keyed by what the app of a job builds with and by the week. Once the app is generated and configured, `tools/native_build.dart` writes into a file of the workspace, whose hash is in the key, the plugins of the app with native code for the platform, with the versions that pub resolved (the plugins of the Flutter SDK left out), plus its Gradle files without the ids of the app for Android, or the Swift packages that its Xcode project refers to itself for iOS. For apps with none of these for the platform, such as an app without plugins with iOS code, it writes no file, and the job neither restores nor saves a cache. The tool lists every plugin with native code, whether its build downloads anything or not. The apps that CI starts on iOS without Firebase have plugins with iOS code, but none whose Swift package names a remote package. So their jobs have a key under which nothing is ever saved, and each restores the newest cache of any app without using it. Every job that builds for Android or iOS, `CLI from pub.dev` included, restores the cache of its app, or else the newest one of its app from an earlier week, or else the newest one of its platform. When it did not find the cache of its app, it saves that cache after a successful build, but only if the build added more than `NATIVE_CACHE_SAVE_ABOVE_MB` (100 MB) to what it restored. `apps.yml` sets that threshold in its `env` with the reason: a cache is saved whole, over 1 GB for Gradle, so an app that needs only a few MB more than the cache of another app downloads them in each run instead of storing a near copy, while an app that builds with another version of Gradle or of its plugins gets a cache of its own. Only the runs on main save, because the runs of every branch find the caches of main: `build.yml` passes `save_gradle_cache` and `save_swiftpm_cache` for its runs on main, and the nightly run passes them for its latest Flutter on main. Both are false by default. When jobs save the same key at once, the first one wins. A job still downloads what the cache that it restored lacks, such as what its app needs beyond the cache of another app. So every job that builds for Android puts `.github/gradle/maven_central_mirror.gradle` into `~/.gradle/init.d`, and every build of Gradle there takes what it would download from Maven Central from the mirror of Maven Central that Google keeps. A build that declares no repository of plugins, such as the included build of the Gradle plugin of Flutter, gets the mirror before the Gradle Plugin Portal, which would send it on to Maven Central for the Kotlin Gradle plugin. `tools/workflow_apps_test.dart` fails on a job on Linux that runs Gradle for Android without a step before that puts the script there (`mavenCentralProblemsOf`).

The job `CI` of `build.yml` sums up the other jobs of the workflow: it needs all of them and fails when one of them failed or was cancelled. A skipped job counts as passed only in a pull request into a branch other than main, which skips the jobs with Flutter. Every other run runs every job, so there `CI` fails on a skipped job too, and a mistake in the condition of the jobs with Flutter cannot let a pull request into main pass without them. The ruleset of main requires the checks `CI` and `PR title`, so the ruleset does not have to change when jobs come and go. A job added to `build.yml` goes into the `needs` of `CI` too. `tools/build_workflow_test.dart` fails when one is missing there, and when `CI` lacks `if: ${{ !cancelled() }}`, without which a failed job would skip `CI` and a ruleset would take the skipped check as passed. A new run of `build.yml` cancels the run of its concurrency group that is still in progress: `build-<number of the pull request>` for a pull request, and `build-<ref>` otherwise. `.github/workflows/cancel.yml` runs when a pull request is closed and joins the group of the pull request with `cancel-in-progress`, so the run of Build of a merged or closed pull request stops; `tools/build_workflow_test.dart` fails when no workflow does so.

When a test of a package or of `tools/` fails in CI, the page of the run lists it at the top as an annotation, with the name of the test, its message, and its file and line. Every `dart test` in the workflows writes a JSON report with `--file-reporter json:build/test-results/<name>.json` in the directory it runs in, under a name that no other run in its job uses. `.github/scripts/each_app.sh` gives the report of the command it runs for each app the name of the app, `<name>.<app>.json`, so that the run for the next app does not replace it. The last step of each job with tests runs `dart tools/test_annotations.dart` whenever Dart is set up, even after a failed step or in a cancelled job. It turns each test in those reports that failed, or that started and never finished, into an annotation. `tools/test_annotations_test.dart` fails when a run of tests in a workflow writes no report or the same report as another run in its job, and when a job with tests does not run the tool after them.

Run the CLI from source. It finds the Flutter SDK through `flutter` on the `PATH` before it generates anything, and runs `flutter pub get`, `dart fix` and `dart format` in the new app:

```bash
cd packages/smf_flutter_cli
dart run bin/smf_flutter.dart create my_app -o /tmp/out --org com.example --no-input --on-conflict replace
```

Modules are chosen with `-m`, and every option of `create` comes from the command line with `--no-input`. `--explain` prints what would be generated and whether the machine is ready, without changing anything.

## Generated files and templates

- `lib/bundles/*_bundle.dart` are generated from `bricks/` by `tools/bundle_bricks.dart`, which `melos bootstrap` runs. Never edit them by hand. Change the brick, re-bundle and commit the result. CI fails if a committed bundle differs from what the bricks produce.
- `bricks/**/__brick__/**` holds mason templates, not Dart. They are excluded from analysis and formatting. They use mason syntax: `{{app_name.snakeCase()}}`.
- Bricks have no mason hooks. The pipeline rejects a brick with hooks and runs none: modules check the machine and run tools through `Preflight` and `PostGenStep` contributions.
- A brick has the same files in every app. A file whose path depends on the data of a role or on its choice, such as one file for each item that the modules give the role, comes from a render hook instead. The hook of the template of the role, or of its provider, returns the text of the file by its path in the app (`RoleOutput.files`). The pipeline takes the file as it is. It renders no mustache in it, fills no tag and adds no import, and `dart fix` and `dart format` of the new app go over such a Dart file as over the rest of the app. In every other way it is a file of the app like those of the bricks. Its path is inside the app, where the kind of the module of a provider may generate files, and no brick or other hook generates the same file. The path comes from data, so it must also be one that every machine can write. It has no control character, no character that Windows forbids in the name of a file, and no segment that ends with a dot or a space. It is not a directory of another file of the app, and it is not inside what is a file of the app, whatever the case of the letters. The owner of the file is the owner of the hook, and the contract harness, the snapshots and the matrix see it like any other file. A Dart file from the hook of a provider may import what the fragments of that hook may. The harness also reports a file of the app, from a brick or from a hook, at a path where code generation or the localizations of Flutter write theirs. The provider of the clock in the fixture package `fake_roles` generates a file for each time zone this way.
- Code of a template that depends on whether a role is in the app is a variable of its brick with a `RoleVar` in `BrickContribution.vars`. A `RoleVar` has the code for an app with the role and the code for one without it, each a `Fragment` with the imports it needs or a string of code that needs none. The pipeline takes the value by the presence of the role, as it applies a contribution by its `when`. So one line of a template serves both apps, where two mustache sections under `has_<role>` would hold the code and its import twice. The role is one that the contributor provides, requires or uses. The variable is a fragment variable in every app, whichever value the app gets, so a template reads it rightly in every app or in none. A template reads it as it is, `{{{name}}}`, never in a path, and only in a Dart library when either value has imports. The pipeline adds the imports of the value that the app gets to the Dart files of the brick that read the variable. A template reads the variable outside every mustache section, also outside that of the presence flag of another role: code that needs a second role goes into a brick of its own, contributed with `when` of that role. A `RoleVar` holds no plain data for mustache, such as a list or a boolean. The variables of a render hook take none, because a hook asks itself for the presence of the roles that its role requires or uses (`RoleHookInput.has`). The module `fake_clock_user` of the fixture package `fake_roles` reads the time zones of the clock this way.
- A role may have command line options (`Role.options`), such as `--start` of the router role. The `choose` hook of the template of the role reads them, and what it chooses reaches only the render hooks of that template and of the providers of the role (`RoleHookInput.choice`): the contributions of a module are the same whatever the role chose. A mode option, `RoleOption.mode(name, help, values)`, takes one of a closed list of values, and a role declares it when each value makes another app. With it the role states that the code of the app depends on the value, that the first value is the default, and that every value gets apps in the tests. The default is the value of an app that got none. The `choose` hook chooses it when the option is not given and the run has no terminal, and a user who presses Enter at its question gets it too. `optionsOf()` of the template gives the option with its value for every choice, also for one that the template made without asking. So no run needs the option, and a script written before the role had it generates the same app. A module that is no provider has no hook, so the template of the role writes the value into a file of the role as a constant, and the code of such a module branches on it when the app runs. The registry refuses a mode option with fewer than two values, with a value twice, or with a value that is not of lower-case letters and digits with single hyphens between them, since the values name the apps of the tests. In the fixtures, the clock role of `fake_roles` has such an option, `--clock-hours` with the values 24 and 12: its template writes the constant `clockHours`, the render hook of its provider renders the code of the hours of the app, and `fake_clock_user` reads the constant when the app runs.
- A post-generation step may continue another step, such as with a fix of a file that the tool of that step writes: it names that step by its id in `PostGenStep.followUpOf`, runs right after it once that step succeeded, and is left for later with it when that step does not run or fails. A step that others may continue has an id (`PostGenStepId`: the module that contributes the step and a name), which the module publishes as a constant of its module class. A module continues only its own steps and those of the modules it depends on directly, so a module knows nothing of the modules that continue its steps. The pipeline reports a step with the id of another module, two steps with one id, a step that the module may not continue or that the app does not have, a `when` on a step that continues another, and steps that continue each other in a cycle.
- The snapshots in `packages/smf_flutter_cli/test/snapshots/` and `packages/smf_pipeline/fixture_registry/test/snapshots/` hold the files of the apps the CLI and the fixtures render. When a change alters them, update them with `SMF_UPDATE_SNAPSHOTS=1 dart test test/snapshot_test.dart` in the package and review the diff. The snapshot test of the CLI parses the YAML, XML and plist files of an app, and its ARB files as JSON, so a file that does not parse fails it.
- `smf_firebase_core` generates `lib/firebase_options.dart` as a placeholder in the form that `flutterfire configure` writes, which throws an `UnsupportedError` until the FlutterFire CLI fills it in, and initializes Firebase with it in `bootstrap()`. Its preflight checks look for the Firebase CLI, a Firebase login, the FlutterFire CLI and, on macOS, the Ruby gem xcodeproj; elsewhere a check tells that the Xcode project is set up on a Mac. They only warn: a run in a terminal offers to set up what it can, asking first. After generation it runs `flutterfire configure` in the terminal with the ids of the app; that needs a Firebase account, so a run with `--no-input` or `--skip-external-setup` generates the app with the placeholder and prints the command to run later. The id of that step is `FirebaseCoreModule.configureStep`, and `smf_firebase_crashlytics` continues it with a step that runs only on macOS and points the build phase for Crashlytics that flutterfire adds at the upload script in `build/ios/SourcePackages`, which `flutter build ipa` needs. The section `Crashlytics` that `smf_firebase_crashlytics` adds to the README of the app gives the command of that fix, to run after `flutterfire configure` by hand on macOS.
- Every app gets `AGENTS.md`, a guide for coding agents that work on the app, and `CLAUDE.md`, whose whole content is `@AGENTS.md`. The template of the app entry role generates both, whichever module provides the role, and `AppEntryRole.agentSections` is the socket of the sections of the guide. The template of a role contributes `AgentNote.ofRole(text)` under the description of the role, such as `routerRole.description`: where its files are, how code uses it and what code must not do. Such a note never names a provider or its package. A provider adds `AgentNote(text)` under the same heading, and a module without a role under a heading of its own. A module keeps the texts of its notes in `lib/src/agents.dart`. A provider that wraps a package opens its note with the line ``With `<package>`:``, such as ``With `go_router`:``, and then tells where it writes what the role describes and how to add one more by hand. One that wraps a tool of Flutter names the tool there instead, as `gen_l10n` does with ``With `gen-l10n` of Flutter:``. A note is true in every app that has it. A note tells only what the code of the app does not show, and names a file in backticks by its path from the root of the app. In every app that the contract harness renders, the structural rule `app_entry.agent_guide_paths` reads the paths that the guide names below a top-level directory of a Flutter project, such as `lib/`, `test/` or `android/`, and its paths to Dart files, and reports one that the app does not have. It does not read the name of a file at the root of the app, such as `pubspec.yaml`. So a note about a file of a role that the app may lack is a contribution of its own with `when:`, as the note of the localization role on the setting of the language is, and a note that depends on the data of a role comes from a render hook. The template of the router role does so for the guards of the routes: its render hook adds a second `AgentNote.ofRole` after the note of the role, so only the guide of an app with guards tells of them. The section of the app entry comes first and the others in the order of their headings, and a section has the notes of the roles first, then the others in the order of the ids of their contributors. So replacing the provider of a role changes only its own note. The socket does not follow the order edges of its contributors (`SocketKind.followsOrderEdges`), so a note under `when:` cannot make an app impossible to generate. Only the template of a role contributes `AgentNote.ofRole`: the socket refuses one from a module. The tests of a module read its notes with `RenderedApp.entriesOf(AppEntryRole.agentSections)`, each with its contributor and its heading. For the names of code that a test lists, they check that the note gives the name in inline code and that a file of one app of the module declares or uses it (`DartFileIndexer`). They check neither a name that the test does not list nor what a sentence says about the code, which only a test of that code can pin. The tests of `smf_contracts` do the same for the notes of the roles, with `agentNoteOf` and `expectNamesOfCode` of `test/role_support.dart`, which looks each name up in the file that the test names for it. `agentNoteOf` takes the roles of the `when:` of a note that only some apps have, and `test/roles_test.dart` checks the paths of such a note against the files that the template generates in an app with those roles. Every module that the CLI offers has a note, and so does every role with a template. `test/agent_notes_test.dart` of `smf_flutter_cli` fails on a module or a role without a note in the guide of an app with it, and `test/roles_test.dart` of `smf_contracts` fails on a role whose template has no note for every app with the role. A module or a role with nothing to tell a coding agent goes into `_withoutNote` of the first test, and a role also into `withoutNote` of the second, each with the reason. A module whose only note is for the apps with another role, as that of `firebase_analytics` is for the apps with a router, goes into `_onlyWith` of the first test with that role and the reason. `roleNoteProblems` of `package:smf_pipeline/testing.dart` checks the notes of the roles in the apps of a registry. It holds every note against the providers of every role and the modules that they depend on. A note has none of their ids and none of the packages that they add, in its text or in its code, also with `-` for `_`, in camel case or inside a longer name, such as `GoRouterState` for `go_router`. An id whose words are all words of the roles, such as `settings`, counts only as it is, in code. In code, a note has no name that only their files declare at the top level or as the prefix of an import. Nor has it a name in upper camel case that only code with one of their packages has, or with a file that they import and no module generates: the check takes it for a name of that package or file. In inline code, it has no file or directory that only they generate. What a role guarantees is free: the symbols of its interface, their files, and the names that the descriptions of its rules give as code. The names of `dart:core` and `dart:async` are free too, and so is what every app has at its root, such as `pubspec.yaml` and `test/`. The check has limits. It reads the text of a note only for ids and packages, and it knows a module only from the files of the apps. So it misses a method of a package, a class that no generated file uses, and one word of an id of several words, such as the brand of a package. It also errs the other way: a name of Flutter that only files with one package have is taken for a name of that package. For that case `roleNoteProblems` takes `allowed`, what a note may have after all, as the note gives it and with the reason, and it reports an entry that excuses nothing. `test/agent_notes_test.dart` of `smf_flutter_cli` runs the check over the modules of the CLI, and the test of the same name in `fixture_registry` runs it over the two registries of the fixtures, which have a provider of their own for most roles. A registry holds a note only against the modules that it has, so a line about a fixture, such as `fake_router`, comes only from the second test. Both tests pin sentences that a note may have and sentences that the check refuses, and both fail when none of their apps has the note that the router role adds for an app with guards. The test of the CLI fails as well when the template of a role contributes a note under `when:` that no app has, because then no test reads that note.

## Tests

- Tests live in each package's `test/`. Sonar counts coverage only within the package that runs the tests, so a module's code needs tests in that module.
- Keep coverage at 100% of the lines and branches of `lib/` with tests that pin behavior someone relies on, never with tests that only touch a line. Remove code that cannot run instead of covering it. Code that no automated test can run, such as the terminal of a user, goes between `// coverage:ignore-start` and `// coverage:ignore-end`, with the reason in a comment next to it. Don't use `coverage:ignore-file`, which the banlist fails on: the file then drops out of `lcov.info` and Sonar counts all of it as uncovered. `melos run test:coverage` measures branches as well as lines, and `melos run coverage:check` after it fails on any line or branch of `lib/` that the tests do not cover, with its `path:line`. CI runs both.
- The contract harness of `package:smf_pipeline/testing.dart` checks a module against the rules of the roles it declares and renders every app it can be part of. `packages/smf_flutter_cli/test/modules_test.dart` runs it over every module the CLI offers, and a module package runs it over itself in its own tests. New modules must pass it.
- For a module, the harness builds a case for each subset of the roles it only uses and each combination of providers of the role of its variants, of each role it requires and of each role of the subset. It leaves out a combination of providers that would give an app two providers of a role that takes one, such as another router next to a module that depends on go_router, unless no combination of the subset can be in an app with the module; then it keeps them all, and their cases report why. A case names the provider of each of its roles that has several in the registry, such as `fake_analytics (get_it) with di`, so the names change when a role gets a second provider. For each package of a provider of a role that a module adds, the harness also builds a case of the module with that provider, `<module> with <provider>` or `<module> (<provider of its variant>) with <provider>`, when they can be in one app. So the registry of a module's tests holds the providers of the roles it requires or uses, the providers it has variants for, and the providers whose packages it adds, and the harness builds an app of the module with each. `ContractHarness.uncheckedProviders()` lists each provider of a role that a module requires or uses which can be in an app with the module but provides the role in no app of the cases of the module; `packages/smf_flutter_cli/test/modules_test.dart` and `packages/smf_pipeline/fixture_registry/test/fixture_registry_test.dart` expect none.
- For a role with a mode option (`RoleOption.mode`), the harness builds one more case of each provider of the role for each value of the option after the first. It is the first case of the provider, which has every role that the role uses, with the value among the options of the case (`ContractCase.roleOptions`), and its name ends with `--<option>=<value>`, as in `clock by fake_clock_badge --clock-hours=12`. The other cases leave the option out, so their apps have its first value. `ContractResult.appKey` has the options of a case, so `checkAll()` keeps such a case next to the case of the same modules, and the matrices generate its app with the option. `ContractHarness.casesOfModes()` has the cases of the apps with every module (`casesOfAll()`) once more for each other combination of the values of the mode options of the roles of each app. An option that the harness gives every case (`ContractHarness.roleOptions`) has no cases of its own. In every app that it renders, the harness holds the choice of a role with a mode option to the values of the option, by the value that `optionsOf()` of the template gives for the choice. With a value of the option, the choice has that value. Without one, it has the first value: in a terminal, where the harness answers as a user who presses Enter, and in a run without a terminal, where the role must not fail for the lack of the option. So the package of a provider of such a role renders its hook for every value in its own `checkAll()`, and a second provider gets these cases without a change of the tests. The harness reads the options from the roles of its registry and names no role itself.
- Generator tests check generated code for real: they parse it or type-check it with the analyzer, not just string-match.
- Tests are hermetic: no network, no Flutter SDK, temp dirs cleaned up. The few that need more skip themselves unless CI provides it: an app from `flutter create` (`SMF_FLUTTER_CREATE_APP`), an app with Crashlytics to archive on macOS (`SMF_CRASHLYTICS_APP`), an app with Crashlytics that flutterfire configured for iOS, to fix its build phase for Crashlytics on macOS (`SMF_CONFIGURED_APP`), an app with Firebase to configure with flutterfire for a platform in a Firebase project, with the key of a service account of the project (`SMF_FIREBASE_APP`, `SMF_FIREBASE_PLATFORM`, `SMF_FIREBASE_PROJECT`, `SMF_FIREBASE_SERVICE_ACCOUNT`, and `SMF_FIREBASE_REGISTER=1` to let flutterfire register the app in the project when the project has none with its id), or a machine where the Firebase CLI may be installed (`SMF_INSTALL_FIREBASE_CLI=1`).
- A bug found but not fixed gets a test for the *correct* behavior, marked `skip: 'Bug: <description>'`. Never write a test that locks buggy behavior in. The fix removes the `skip`.

## Git and PRs

- Use [Conventional Commits](https://www.conventionalcommits.org/) with the package's short name as scope: `fix(go_router): ...`, `feat(contracts): ...`, `test(cli): ...`, `chore(ci): ...`. `melos version` derives version bumps and CHANGELOGs from them.
- Name branches `fix/<topic>`, `feat/<topic>`, `chore/<topic>`, `docs/<topic>`, `test/<topic>`.
- A PR is squash-merged: the squash commit takes the title of the PR as its only line, so the title must be a Conventional Commit too, and CI checks the title of every PR (`.github/workflows/pr-title.yml`). A breaking change needs `!` in the title, such as `feat(contracts)!: ...`: a `BREAKING CHANGE:` footer in a commit of the branch does not reach main.
- A larger change may collect its PRs in a branch of its own. The PR of that branch into main is merged with a merge commit rather than squashed, so that each commit of the branch, such as the squash commit of each of its PRs, reaches main as it is, and `melos version` reads each on its own. So the `!` of a breaking change goes into the title of the PR into that branch that makes the change.
- Once a branch is pushed, add new commits on top. Don't force-push or rewrite pushed history unless a maintainer asks.
- Don't bump package versions or edit CHANGELOGs by hand. `melos version` does both, and its preCommit hook syncs `packages/smf_flutter_cli/lib/version.dart`.
- Keep PRs focused: one concern per PR, one logical change per commit.
