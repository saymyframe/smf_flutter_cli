# AGENTS.md

This guide tells coding agents what the code of this Flutter app does not show. Setup that needs a person or an account is in [README.md](README.md). When you change what a section describes, change the section too.

## App entry

The app is plain Flutter code that nothing regenerates. Change it by hand, unless a section below says what writes a file.

- `main()` in `lib/main.dart` initializes the binding, awaits `bootstrap()` and calls `runApp()`, in this order. When `bootstrap()` throws, `main()` calls `showFailedStart()` of `lib/core/app/failed_start.dart` and returns: the app shows `FailedStartApp`, with the error in a debug build, and the error reaches `FlutterError.onError`. Keep the `try` around `await bootstrap()` in `main()`. Start-up code goes into `bootstrap()`. Do not catch an error there just to let the app start: fix what the error names, such as a step of the setup that has not run.
- `bootstrap()` in `lib/bootstrap.dart` runs before the first frame, in four phases: what must come before anything else, then the platform services, then the services of the app, then what needs them. Put a new statement into its phase, and import neither `package:flutter/material.dart` nor `package:flutter/cupertino.dart` there.
- Put code that features share into `lib/core/<concern>/`, one directory for each concern. Put a feature, with its screens and their state, into `lib/features/<feature>/`.
- The root of the app asks the system for the icons of the status bar that suit the theme, around every screen, with `StatusBarIcons` of `lib/core/app/status_bar_icons.dart`: dark icons on a light theme, light ones on a dark theme. A screen without an app bar needs no `AnnotatedRegion` for them. Add one only to a screen whose top has another brightness than the theme, such as a picture behind the status bar.
- The app has the flavors `dev`, `staging` and `prod`. A `flutter` command without `--flavor` builds `dev`, in release mode too, so a build for a store takes `--flavor prod`. Code reads the flavor from `appFlavor` of `package:flutter/services.dart`. The app has one entry: add no `main_<flavor>.dart`.

- The section "Finish the setup" of the README lists the steps of the setup that no command can do, such as a step in the web console of a service that the app uses. Only the developer of the app does them: when a task depends on one of them, point the developer to that section, and do not try to do the step yourself.

After a change, run:

```bash
dart format lib test
flutter analyze
flutter test
```

Format only `lib/` and `test/`: `dart format .` also formats what Flutter writes into `build/`. The app as generated is formatted, `flutter analyze` finds no issue in it and `flutter test` passes.

- `App` in `lib/app.dart` is the root widget of the app and creates its one `MaterialApp`. Every screen is below it, so create no other `MaterialApp` in `lib/`. The only other one is in `FailedStartApp`, which `main()` runs in its place when the start-up fails.
- The `theme`, `darkTheme`, `themeMode`, `locale` and localizations of the app go into the arguments of that `MaterialApp`.
- Tests mirror `lib/`: the test of `lib/<path>.dart` is `test/<path>_test.dart`.
- The app has only an Android and an iOS project, in `android/` and `ios/`.
- The entitlements of the iOS app, such as Push Notifications or Sign in with Apple, are in `ios/Runner/Runner.entitlements`. Every build configuration of the Runner target signs with this file, even while it is empty. The Signing & Capabilities tab of Xcode edits the same file.
- Each flavor is in `productFlavors` of `android/app/build.gradle.kts`, and on iOS in `ios/Runner.xcodeproj/xcshareddata/xcschemes/<flavor>.xcscheme` and in the build configurations `Debug-<flavor>`, `Profile-<flavor>` and `Release-<flavor>` of `ios/Runner.xcodeproj/project.pbxproj`. Change both places together. A new setting of the Runner target goes into each of its twelve build configurations.

## Firebase

- `bootstrap()` initializes Firebase with `firebaseOptionsOfFlavor` of `lib/firebase_options_of_flavor.dart`, by the flavor of the build. `lib/firebase_options_dev.dart`, `lib/firebase_options_staging.dart` and `lib/firebase_options_prod.dart` are placeholders until `tool/configure_firebase.dart` writes them, and a build of such a flavor stops at start-up with an `UnsupportedError`. Do not write them by hand.
- `tool/configure_firebase.dart` needs a Firebase account and a project: run it only when asked, with the command of the section Firebase of `README.md`. Do not run `flutterfire configure`, which writes one configuration that every flavor then shares.
- A test that runs `main()` or `bootstrap()` starts Firebase with the options of the flavor of the test, `dev`, which needs a mock of its platform side. Prefer a test of a widget, which needs neither.

## Preferences

- `AppPreferences` in `lib/core/preferences/app_preferences.dart` remembers the settings of the app between its launches, such as the theme mode. It is not encrypted: never save a token, a password, an API key or an encryption key in it.
- To remember a setting, write a function that takes the `AppPreferences` and add it to `_restorers` in that file. In it, read the setting, put it into the state that the widgets listen to, and keep the preferences in that state for its writes. The function awaits nothing, and keeps the current value when nothing is saved.
- Name a key `<owner id>.<setting>`, such as `theme.mode`, where the owner is the feature or the concern whose code keeps the setting.
- In the code of the app, do not call `createAppPreferences()` or `initPreferences()`. `bootstrap()` opens the preferences, and code gets them as the argument of its function in `_restorers`, or, with a DI container in the app, from the container. Widgets use the state and do not touch the preferences. A test may call both: `initPreferences()` opens the preferences again, as the next launch of the app does, and `createAppPreferences()` returns them.

With `shared_preferences`:

- In `lib/`, only `lib/core/preferences/shared_app_preferences.dart` imports the package. Other code uses `AppPreferences`.
- A number is read only as the type that it was saved as: `getDouble()` returns `null` for a key with an `int`, and `getInt()` for a key with a `double`.
- In a test that runs `bootstrap()`, first set `SharedPreferencesAsyncPlatform.instance = InMemorySharedPreferencesAsync.empty()`. Without it, opening the preferences throws. Both names are from the package `shared_preferences_platform_interface`: add it as a dev dependency.
- `pubspec.yaml` keeps `shared_preferences_android` at 2.5.2 or later. With 2.5.0 and 2.5.1, a release build fails to open the preferences on Android, because R8 renames Kotlin classes that the package looks up by name. Before you change the constraint, check that a release build of the app starts on Android.

## Remote config

- `appRemoteConfig` in `lib/core/remote_config/app_remote_config.dart` holds the values of remote config, which a backend changes without a new version of the app. Its `value` is a `RemoteValues` with a getter for each parameter of the app, which returns the value that the backend gave or the default of the parameter. It is a `ValueListenable`: a widget that follows a value reads it in `build` under a `ValueListenableBuilder`, and code that must not change on the screen reads it once, such as in `initState`. The app has one controller, so create no other `AppRemoteConfigController`.
- The values never hold the start. The start makes active what the device kept from the last fetch, and an app with parameters fetches new values in the background, also each time the user comes back to it, which take effect at once. While the app has no parameter, it asks the backend nothing.
- A parameter has a default in `RemoteValues.defaults` and a getter in `lib/core/remote_config/remote_values.dart`, and the same name and type in the backend of the provider. The code of a module reads only its own parameters.
- Every value reaches every installation that fetches it, where anyone can read it: never put a secret into remote config, such as a key or a password.
- A new provider implements `RemoteConfigService` of `lib/core/remote_config/remote_config_service.dart`, and only the files of that implementation import it. The code of the app imports `lib/core/remote_config/app_remote_config.dart`, which exports `RemoteValues`, and calls neither `initRemoteConfig()` nor `createRemoteConfigService()` nor `appRemoteConfig.start()`. A test gives `appRemoteConfig.start()` a service of its own.

With `firebase_remote_config`:

- `FirebaseRemoteConfigService` in `lib/core/remote_config/firebase_remote_config_service.dart` implements `RemoteConfigService` on `FirebaseRemoteConfig`. In `lib/`, only that file imports the package: other code reads the values through `appRemoteConfig`.
- A parameter that the app reads is created in Firebase Remote Config of the Firebase project of each flavor, with the name and the type of `RemoteValues.defaults`. The section Firebase Remote Config of the README tells how, and which two APIs of Google the project needs.
- `values` of the service has only the values whose `source` is `ValueSource.valueRemote`: `getAll()` of Firebase has the defaults of the app too. Keep that filter, or a parameter that the project lacks reads a value of Firebase in place of its default.
- `updates` passes on `onConfigUpdated` of Firebase, after which `appRemoteConfig` calls `activate()`. Do not call `activate()`, `fetch()` or `fetchAndActivate()` of the package elsewhere: values that change in the middle of a screen come only through `appRemoteConfig`.
- The package has no platform side for tests. A test that runs `bootstrap()` answers its messages to the platform itself, with `setMockMessageHandler` of `TestDefaultBinaryMessengerBinding.instance.defaultBinaryMessenger`, on the channels `dev.flutter.pigeon.firebase_remote_config_platform_interface.FirebaseRemoteConfigHostApi.<method>` in the codec of the package, and on the event channel `plugins.flutter.io/firebase_remote_config_updated`. A test of the values alone gives `appRemoteConfig.start()` a service of its own.

## Router

- Navigate with `context.nav.<feature>.<route>(...)`, never with the package of the router. It returns a `NavLink`, whose `go()`, `push<T>()` and `replace()` show the location. In `context.nav` both names are in lowerCamelCase; elsewhere `<feature>` is the id of the feature.
- A route is in three places, which agree on its name, `<feature>.<route>`, and on its path, which starts with `/<feature>`:
  1. its screen, a widget in `lib/features/<feature>/` whose `const` constructor takes each value of the route as a named parameter;
  2. `lib/core/router/navigation.dart`: its location class, which extends the sealed `AppLocation` with its `routeName`, its `path` and, below another route, its `parent`, and a method that returns its `NavLink` in the class of the routes of its feature. `AppNav` returns that class from a getter with the name of the feature, and both classes pass on the `BuildContext` that `NavLink` takes;
  3. the route itself, where the provider of the router declares its routes.
- A value of a route is a `String`, an `int`, a `double` or a `bool`, from a `:<name>` segment of its path or from the query.
- `appRouter` of `lib/core/router/app_router.dart` is the one router of the app: create no other.
- `NotFoundScreen` in `lib/core/router/not_found_screen.dart` is the page that the router shows for a location that it cannot show, such as a link to a page that the app does not have. Change its look there, and keep its `const` constructor without arguments. `appRouter.navigatorOf(context).goToStart()` shows the screen that the app starts on, as `go()` shows a location.

- `routeGuards` in `lib/core/router/app_router.dart` lists the guards of the routes, each a `RouteGuard`, in the order the router asks them. A guard without `routes` is a gate over the whole app. The gates come first, and the first one whose `allows` is `false` decides: the router asks no guard after it. A guard with `routes` keeps the user only from the routes that it names there, each as `<feature>.<route>`, and comes after the gates.
- To keep the user from the rest of the app, add a gate to that list, never a redirect to the files of the router. Put it at the place among the gates where its screen comes on a first launch: a guard of the first launch goes before one that asks who the user is. Make its `redirectTo` a top-level route outside the main navigation. To keep the user from some routes only, add their names to the `routes` of the guard that stands for what they need, or add such a guard after the gates. Add the name of each route below such a route too: a route does not ask because the route above it does. The `routes` are outside the main navigation and outside every `flow`, and the screen that the app starts on is none of them.
- A feature changes the value of `allows` of its guard, and the router navigates when it does. While the `allows` of a gate is `false`, the router shows its `redirectTo` in place of the whole stack, whichever location was asked for. Once the gates allow, the router shows the location that was asked for in the meantime, such as a link, or else brings the user back to where they were. A gate with `resumes: false` does not bring the user back. When the `allows` of a guard with `resumes: false` turns `false`, the router forgets where the user was and what was asked for before, even while the `redirectTo` of another guard is shown. Once the gates allow, the user comes to a location that was asked for since then, or else to the screen that the app starts on. So after a sign-out the next user does not come to the screen of the last one.
- While the `allows` of a guard with `routes` is `false`, `go()`, `push()` or `replace()` of one of those routes opens its `redirectTo` over the page that the user is on, and the request waits. Back returns to that page, and a `push()` that waited completes with `null`. Once the value is `true`, the router closes the pages of the `flow` and does what was asked: `push()` shows the route over the page that the user was on and completes with the value of its page, `go()` shows it in place of the stack, and `replace()` in place of that page. When the value turns `false`, the router closes the pages of the `routes` with the pages over them. The user is then on the page below them, or on the screen that the app starts on when no page is below, as after `go()` to one of the `routes`.
- A screen neither closes itself nor navigates after it changed the value of `allows` of a guard: the router has done both by then. This goes for a screen of a `flow` that turned the value `true`, as after a sign-in, and for a screen of the `routes` that turned it `false`, as a screen with a sign-out button. A `pop()` after the change closes the page that is on top by then: the page that the user asked for, or the page below the one that the router closed, which may be the main navigation of the app.
- The `flow` of a guard is its `redirectTo` and the routes below it. These routes show only while a guard with that `flow` does not allow. At any other time the router shows the screen that the app starts on in their place, or the `redirectTo` of a gate whose `allows` is `false`. So no code navigates into the `flow` of a gate, and no screen of a `flow` navigates out of it once its guard allows: the router does. The first does not hold for a guard with `routes`. While it does not allow and every gate does, its `redirectTo` shows like any route, so a screen may open it with `push()`. `go()` to it from a screen takes the place of the stack, with no way back. A link to a route of its `flow` opens that route over the screen that the app starts on, so back leads into the app. Such a link is lost while a gate with another `flow` does not allow: once the gate allows, the user is on the screen that the app starts on. Inside a `flow`, navigate with `push()` or `replace()`. `go()` takes the place of the pages below the `flow`, and the request that waits is lost with them.

With `go_router`:

- `lib/core/router/app_router_factory.dart` has the one `GoRouter` of the app. A route is a `GoRoute` in its `routes`, or in the `routes` of its parent: `path` is the full path of a top-level route and the path from its parent otherwise, and `name` is `<feature>.<route>`. The values of a route come from `state.pathParameters` and `state.uri.queryParameters`. Parse one that is not a `String` with `tryParse`, and throw a `GoException` in the `redirect` of the route when a required value is missing or does not parse, so that the router shows its error screen.
- The app opens at `initialLocation`, and the route `/` leads to the same screen: change both together.
- To follow the screen that the user sees, add a function to `_screenListeners`.

## Store reviews

- `appReview` in `lib/core/review/app_review.dart` asks for the review dialog of the App Store or Google Play only where the code of the app calls `appReview.requestIfDue()`. Call it at a natural break, such as after the user has finished a task: `unawaited(appReview.requestIfDue());`. It asks only when `ReviewPolicy` says that a review is due: never on the first launch, in the flow of a guard of the routes, twice in a version or twice in 14 days. It returns nothing, since the store tells nothing.
- Never call it from a button or after a question of your own, and show nothing around the dialog. Nothing in the app may depend on whether the app asked.
- `appReview.openStorePage()` opens the page of the app in its store, and `appReview.openStorePage(review: true)` the page for a review. `appReview.hasStorePage` tells whether there is one: on iOS only once `REVIEW_APP_STORE_ID` in `.env` has the App Store ID. The Google Play page is that of `googlePlayId`, the id of the flavor for a release, also from a build of another flavor.
- A new provider implements `ReviewService` of `lib/core/review/review_service.dart`, and only the files of that implementation import it. The code of the app calls neither `initReview()`, `createReviewService()` nor `appReview.start()`, and writes nothing under the keys `review.*`.

With `in_app_review`:

- `InAppReviewService` in `lib/core/review/in_app_review_service.dart` implements `ReviewService` of `lib/core/review/review_service.dart`: it asks for the review dialog with `InAppReview.instance.requestReview()`, opens the page of the app in its store with `launchUrl` of url_launcher, and reads the version of the app with `PackageInfo.fromPlatform()` of package_info_plus. In `lib/`, only that file imports in_app_review.
- Keep `openStoreListing()` of in_app_review out of the app: on Android it opens the page for the id of the running build, such as that of the flavor `dev`, which has no page in Google Play. `appReview.openStorePage()` opens the right page.
- The app asks for the dialog only where its code calls `appReview.requestIfDue()`. Google Play shows the dialog only in an app that it installed, such as from an internal test track, and the README of the app tells how to see it there. Never send a review while testing: Google Play shows no dialog to an account that has reviewed the app.
- Through the dialog, Google Play collects the rating and the text of a review. Both stores require a link to a privacy policy in the listing of the app and inside the app.

## Update required

- While the version of the app is below `updateRequiredMinimumVersion` of `appRemoteConfig.value`, the parameter `update_required_minimum_version` of remote config, the guard `update_required.supported` of `routeGuards` shows `UpdateRequiredScreen` of `lib/features/update_required/update_required_screen.dart`, the route `update_required.updateRequired` at `/update_required`, in place of every other screen. So no code navigates to it or away from it.
- `updateStatus` in `lib/features/update_required/update_status.dart` has what the guard reads, `supported`, and starts in `bootstrap()`. It reads the version of the app with `PackageInfo.fromPlatform()`, without the build number, and compares it with `versionBelow()` of `lib/features/update_required/version_compare.dart`: number by number, a missing number is 0, and a version that is not numbers between dots keeps the app running.
- The screen shows only where `appReview.hasStorePage` holds, so on iOS only with the App Store ID in `.env`. Its button calls `updateStatus.openStore()`, which opens the store page through `appReview.openStorePage()` and waits for it at most 10 seconds. Once the store opened, did not open or did not answer, the screen also shows "Not now", `updateStatus.continueForNow()`, which lets the user in for this launch below that lowest version.
- A test of another screen needs nothing: the default of the parameter is empty, so the app runs. A test of the screen gives `appRemoteConfig.start()` and `appReview.start()` services of its own, and `updateStatus.start(review: ...)` an `AppReviewController` of its own, such as one with an App Store ID that it scripts. It runs `updateStatus.start()` again for the next launch.

## Values in .env

- Read a value of `.env` only through a static getter of `AppEnv` in `lib/core/env/app_env.dart`. The getter is the key in lowerCamelCase: `AppEnv.myServiceKey` for the key `MY_SERVICE_KEY`. It returns a `String?` that is `null` while the value is empty or missing, so handle `null`. Never read `.env` or `.env.example` from code.
- Every value ends up in the app, where anyone can read it. Never put a secret into `.env`, such as the secret key of a server, a password or a private key.
- `.env` stays out of git. A new key goes into both `.env.example` and `.env`, in UPPER_SNAKE_CASE with a comment line above it, and `AppEnv` gets a getter for it.
- A release build of an app with keys stops with an error unless its command gives the app the values of `.env`; the note of the provider names the arguments. Never remove or work around the check in `lib/core/env/env_check.dart`, which `bootstrap()` calls in its first phase: give the build the arguments. `AppEnv.supplied` tells whether a build has the values.
- `.vscode/launch.json` and `.run/<flavor>.run.xml` are the run configurations of VS Code and Android Studio, one for each flavor. Each passes the flavor and the arguments that the values need. In VS Code, F5 starts the selected configuration, while the links above `main()` and above a test and the Testing view always use `dev`, whose configuration alone has `templateFor`. In Android Studio, a test gets none of these arguments.

With `--dart-define-from-file`:

- Every command of the `flutter` tool that builds, runs or tests the app takes `--dart-define-from-file=.env`, such as `flutter run --dart-define-from-file=.env`, `flutter test` and `flutter build`. Without it, every getter of `AppEnv` is `null`, and a release build stops with an error.
- A command reads `.env` only when it starts. After a change of `.env`, stop `flutter run` and start it again: hot reload and hot restart keep the values that the app was built with.
- The getter of a new key in `lib/core/env/app_env.dart` reads `const String.fromEnvironment('MY_SERVICE_KEY')`, with the key in place of `MY_SERVICE_KEY`, and returns `null` for an empty value, as the other getters do.
- `AppEnv.supplied` is `true` once `--dart-define-from-file=.env` declared one of the keys that it names, so a new key needs no change there. An app without keys has `true` there: with its first key, make it `bool.hasEnvironment('MY_SERVICE_KEY')` with that key.

| `staging` | `com.example.my_app.staging` | `com.example.my-app.staging` |
| `prod` | `com.example.my_app` | `com.example.my-app` |

A `flutter` command without `--flavor` builds `dev`, because `default-flavor` in `pubspec.yaml` says so. That holds in release mode too: `flutter build appbundle` and `flutter build ipa` build a release of `dev`, under its id. For a store, name the flavor:

```bash
flutter run --flavor staging
flutter build appbundle --flavor prod
flutter build ipa --flavor prod
```

Code reads the flavor from `appFlavor` of `package:flutter/services.dart`. A service that knows your app by its id, such as a store or a push provider, knows each flavor as an app of its own, so you repeat a step of its setup for each flavor that needs it.

## Flavors in the native projects

Each flavor is in two places, so change both when you rename, add or remove one:

- Android: `productFlavors` in `android/app/build.gradle.kts`, with its id suffix and its name on the device.
- iOS: `ios/Runner.xcodeproj/xcshareddata/xcschemes/<flavor>.xcscheme`, and the build configurations `Debug-<flavor>`, `Profile-<flavor>` and `Release-<flavor>` in each configuration list of `ios/Runner.xcodeproj/project.pbxproj`. The name of a flavor has no hyphen, since Flutter splits the name of a configuration on it.

In Xcode, select the scheme of a flavor, not `Runner`. The scheme of a flavor builds that flavor, with its id, its name and its `appFlavor`. `Runner` builds the id and the name of `prod`, and takes `appFlavor` from `ios/Flutter/Generated.xcconfig`, which has one only after a `flutter` command that builds or runs the iOS app with a flavor. `flutter build ios --config-only --flavor <flavor>` gives that file a flavor.

On Android, a release build is signed with the debug key until `android/app/build.gradle.kts` has a signing config of yours, and a store refuses such a build. [Sign the app](https://docs.flutter.dev/deployment/android#sign-the-app) tells how.

## When the start-up fails

`bootstrap()` in `lib/bootstrap.dart` runs before the first frame. When it throws, `main()` shows `FailedStartApp` of `lib/core/app/failed_start.dart` in place of the splash screen, which would otherwise stay. A debug build shows the error and its stack trace there and prints them to the console. Any other build only says that the app could not start.

The error also reaches `FlutterError.onError`, so crash reporting that the start-up set up before the error reports it. An error before that reaches no crash reporter, so reproduce it in a debug build. The error usually says what to do, such as a command to run.

The texts of the screen are in English, since the texts of the app need the start-up that failed. Change them in that file.

## Run, test and build with .env

`AppEnv` in `lib/core/env/app_env.dart` reads each value of `.env` with `String.fromEnvironment`. The `flutter` tool reads `.env` when a command that builds, runs or tests the app starts, given `--dart-define-from-file=.env`, and compiles each value into the app. Without the argument, a debug or profile build has every getter of `AppEnv` `null` and says so, and a release build stops with an error that names the argument, so give it to each such command:

```bash
flutter run --dart-define-from-file=.env
flutter test --dart-define-from-file=.env
flutter build apk --flavor prod --dart-define-from-file=.env
flutter build appbundle --flavor prod --dart-define-from-file=.env
flutter build ipa --flavor prod --dart-define-from-file=.env
```

A build without `--flavor` is a release of `dev`, under its id, so a build for a store names its flavor. The section "Flavors" tells more.

Xcode takes the values from `ios/Flutter/Generated.xcconfig`. Only a `flutter` command that builds or runs the iOS app writes them there, and in a fresh app the file has no values. So before Product > Archive, run `flutter build ios --config-only --flavor prod --dart-define-from-file=.env`, or archive with `flutter build ipa` as above.

A command reads the values only when it starts: after you change `.env`, stop `flutter run` and start it again. Hot reload and hot restart keep the values that the app was built with.

`AppEnv.supplied` is `true` once the command declared one of the keys that it names, so a key of your own needs no change there. An app without keys has `true` there, since nothing can tell. With the first key of your own, make it `bool.hasEnvironment('MY_SERVICE_KEY')` with that key, so that a release build without the argument stops.

To read a key of your own, give `AppEnv` a getter for it, as for the other keys:

```dart
static String? get myServiceKey {
  const value = String.fromEnvironment('MY_SERVICE_KEY');
  return value.isEmpty ? null : value;
}
```

The section "Values in .env" tells what goes into `.env`, lists the keys of the app and names the run configurations that pass the argument.

## Firebase

The app uses [Firebase](https://firebase.google.com/docs/flutter/setup) through `firebase_core`: `bootstrap()` initializes it with `firebaseOptionsOfFlavor` of `lib/firebase_options_of_flavor.dart`, which takes the options of the flavor of the build from `lib/firebase_options_<flavor>.dart`. A flavor may have a Firebase project of its own or share one. Until a flavor is configured, its options are a placeholder, and a build of it stops at start-up with an `UnsupportedError` that gives the command below. A debug build shows that error on the screen of a failed start.

`smf create` offers to configure `dev`, and otherwise leaves the command for later. To configure a flavor, or to configure it again, such as for another project or on another machine, run in the directory of the app:

```bash
dart pub global activate flutterfire_cli 1.4.1
firebase login
dart tool/configure_firebase.dart staging --project=<id>
```

Use this script rather than `flutterfire configure`, which writes one configuration that every flavor then shares: `ios/Runner/GoogleService-Info.plist` goes into the resources of every flavor, and `android/app/google-services.json` is what the Google services plugin takes for any variant without a file of its own. It registers the Android and iOS apps of the flavor in the project and writes its options, `android/app/src/<flavor>/google-services.json`, `firebase.json` and, on macOS, `ios/flavors/<flavor>/GoogleService-Info.plist`. Commit them. Elsewhere the script leaves the Xcode project and that file as they were, so run it again on a Mac for iOS. In a terminal you may leave `--project` out, and flutterfire then asks. Other arguments, such as `--account=<email>`, go to flutterfire. The ids of each flavor are at the top of the script: if you change them in the projects, change them there too.

Once one flavor is configured, a build of a flavor that is not fails on Android, with `File google-services.json is missing`. On iOS it builds and stops at start-up, unless a build phase that flutterfire adds for a Firebase package fails the build there first.

In Xcode, select the scheme of a flavor. It builds that flavor, whatever `ios/Flutter/Generated.xcconfig` says. The scheme `Runner` takes the flavor from that file, which has none after a fresh `flutter pub get`, so `appFlavor` is `null` there and `firebaseOptionsOfFlavor` throws an `UnsupportedError`. `flutter build ios --config-only --flavor <flavor>` gives the file a flavor.

The script changes the Xcode project only on macOS, and adds a build phase that runs `flutterfire` from `~/.pub-cache/bin`. So every Mac that builds the app for iOS needs the FlutterFire CLI activated, flutterfire_cli 1.4.1 or a later 1.x; if `dart pub global list` shows one already, skip its activation above. flutterfire needs the [Firebase CLI](https://firebase.google.com/docs/cli).

## Firebase Remote Config

The app reads its values of remote config from [Firebase Remote Config](https://firebase.google.com/docs/remote-config) with [firebase_remote_config](https://pub.dev/packages/firebase_remote_config): `lib/core/remote_config/firebase_remote_config_service.dart` implements the remote config service of the app on it (see the section Remote config, which lists the parameters of the app).

Create each parameter of the app in the Firebase console of the project of each flavor: open Remote Config, add the parameter with the name, the type and the default that the section Remote config lists, and publish the changes. A value that differs by platform, such as one for Android and one for iOS, gets a condition of the platform in the console. The section Finish the setup lists this among the steps that you do by hand once the app has a parameter. A value that you publish reaches an app that runs through the real-time updates of Firebase, and an app that starts later with its next fetch.

The app needs two APIs of Google in the project: the Firebase Remote Config API (`firebaseremoteconfig.googleapis.com`) for its fetches, and the Firebase Remote Config Realtime API (`firebaseremoteconfigrealtime.googleapis.com`) for the values that you publish while it runs, which answers 403 while it is disabled. If the API keys of the Android and iOS apps of the project have API restrictions, in the Google Cloud console under APIs & Services, Credentials, each key must allow both APIs, or the fetches and the real-time updates of the app fail.

A release build fetches at most every 12 hours, and a debug build at each start and each time you come back to the app, so a value that you change shows at once while you develop. The real-time updates do not wait for that interval. Firebase gives a project 100,000 fetches a day for free; beyond them, a project on the Spark plan is throttled and one on the Blaze plan is billed for each fetch (see the [prices of Remote Config](https://firebase.google.com/docs/remote-config/pricing)). An app without parameters fetches nothing.

Each fetch sends the Firebase installation ID of the app on the device, an identifier of the installation. Declare it in the App Privacy details of App Store Connect and in the Data safety form of Google Play. Both stores also ask for a link to the privacy policy of the app, in the listing of the app and inside the app: name Firebase Remote Config there among the services that the app sends data to.

## Values in .env

`.env` at the root of the app holds the values you fill in after generating the app, such as the public key of a service. Code reads each value as a static getter of `AppEnv` in `lib/core/env/app_env.dart`. The getter is `null` while the value is empty or missing, so the app builds and starts before you fill anything in.

A release build needs `.env`: `flutter build` of a release, and an archive in Xcode, stop with an error unless the command has `--dart-define-from-file=.env` and `.env` has a line of a key of the app, also with an empty value. So a build for a store never goes out by mistake from a command that did not give it `.env`. A debug or profile build without it starts with every getter `null` and says so in the console. `lib/core/env/env_check.dart` holds the check, which `bootstrap()` calls in its first phase, and `AppEnv.supplied` tells whether a build has the values.

`.gitignore` lists `.env`, so it stays out of git. `.env.example` is in git and has the same keys without values: after a clone, run `cp .env.example .env` and fill in `.env`. Every value ends up in the app, where anyone can read it, so never put a secret there, such as the secret key of a server, a password or a private key.

`.env` is not tied to a flavor: a build of any flavor takes what `.env` has when its command runs. Keep one file and change its values by hand, or have CI write the file for its job.

The keys of the app:

- `REVIEW_APP_STORE_ID`, read as `AppEnv.reviewAppStoreId`, from the store reviews role: The App Store ID of the app, its Apple ID in App Store Connect, such as 1234567890

To add a key of your own, put it into `.env.example` and `.env` and give `AppEnv` a getter for it. The section of the module that provides the values tells how they get into the app.

Each flavor has a run configuration, which passes the flavor and the arguments that the values need:

- In VS Code, they are in `.vscode/launch.json`. Run and Debug (F5) starts the one that you select in the Run and Debug view. The Run and Debug links above `main()` and above a test, and the Testing view, always use the configuration of `dev`, the only one that is a template of those launches (`templateFor`).
- In Android Studio, each is a file of its own, `.run/<flavor>.run.xml`. A test that you run there gets none of these arguments.

## in_app_review

The app asks for the review dialog of its store with [in_app_review](https://pub.dev/packages/in_app_review): `lib/core/review/in_app_review_service.dart` implements the reviews of the app on it, as the section "Store reviews" tells. On iOS the dialog is that of StoreKit, and on Android that of the In-App Review API of Google Play. The page of the app in its store opens with [url_launcher](https://pub.dev/packages/url_launcher), and the version of the app, in which the app asks at most once, comes from [package_info_plus](https://pub.dev/packages/package_info_plus).

The app asks only where its code calls `appReview.requestIfDue()`, and nothing asks on its own.

Google Play shows the dialog only in an app that it installed. To see it before the app is published ([Test in-app reviews](https://developer.android.com/guide/playcore/in-app-review/test)):

1. Upload a build of the flavor `prod` to the internal test track in Play Console.
2. Add a Gmail account to the testers of that track. It is the primary account of the Play Store on the device: an account of Google Workspace does not work.
3. Install the app once from the internal test track with that account. From then on, local builds of the flavor `prod` may show the dialog on that device: uninstall the copy from Google Play first, since a local build has another signature. Google Play does not limit how often it shows the dialog to an app from the internal test track.
4. Never send the review of a test, or delete it in the Play Store: Google Play shows no dialog to an account that has reviewed the app.

An app from internal app sharing shows the dialog too, but its review cannot be sent. On a device without the review service of Google Play, such as an emulator without the Play Store, the store cannot take the request, the app records nothing, and the next call of `appReview.requestIfDue()` asks again. On a device with the Play Store, for a build that Google Play did not install, such as a local build of the flavor `dev`, the request completes and shows nothing, and the app counts it as a request, so it does not ask again in that version of the app.

Through the dialog, Google Play collects the rating and the text of the review, which become a public review on Google Play, or which only you see for an app on a closed test track: see the section "Data Safety" of [the In-App Review API](https://developer.android.com/guide/playcore/in-app-review). The privacy manifest of in_app_review on iOS declares no data that it collects.

Both stores require a link to a privacy policy in the listing of the app and inside the app.

## Remote config

The app reads values of remote config through `appRemoteConfig` in `lib/core/remote_config/app_remote_config.dart`. A backend of the provider changes them without a new version of the app. `appRemoteConfig.value` is a `RemoteValues` with a getter for each parameter of the app, which returns the value that the backend gave the parameter, or its default while the backend gives none or gives a value that the type of the parameter does not take.

The values never hold the start of the app. The start makes active what the last fetch got, which the device keeps, also without the network, and waits for that at most a second. In an app with parameters, the app then asks the backend for new values in the background, at the start and each time the user comes back to the app, and makes them active at once, also while a screen shows. Where the provider tells of values that the backend publishes while the app runs, they come the same way. While the app has no parameter, it asks the backend nothing: it starts asking with its first parameter. A widget that follows a value reads it in `build` under a `ValueListenableBuilder` of `appRemoteConfig`, and code that must not change on the screen reads it once, such as in `initState`.

The parameters of the app:

- `update_required_minimum_version`, a text read as `updateRequiredMinimumVersion`, by default empty, from the module `update_required`: The lowest version of the app that may run, such as 1.4.0; empty for none

To add a parameter of your own, give it a default in `RemoteValues.defaults` and a getter in `lib/core/remote_config/remote_values.dart`, and create it in the backend of the provider with the same name and type. The section of the module that provides remote config tells where its backend is.

Every value reaches every installation of the app that fetches it, where anyone can read it. So never put a secret into remote config, such as a key or a password.

## Store reviews

The app asks for a review only where its code calls `appReview.requestIfDue()` of `lib/core/review/app_review.dart`. Call it at a natural break, such as when the user has finished a task:

```dart
await saveNote(note);
unawaited(appReview.requestIfDue());
```

When a review is due, the call asks the App Store or Google Play for its own review dialog, and the app shows nothing around it. It returns nothing: the store tells no app whether the dialog showed or what the user did, so nothing in the app may depend on it. Never call it from a button, and never after a question of your own, such as "Do you like the app?": Google Play forbids both, and the App Store allows no prompt but its own.

A review is due as `ReviewPolicy` in that file says: from the third launch of the app (`ReviewPolicy.launches`), three days after its first launch (`ReviewPolicy.sinceFirstLaunch`), and at most once a version of the app and once in 14 days (`ReviewPolicy.between`). Change the numbers there. It is never due in the flow of a guard of the routes, such as the onboarding or a sign-in. The app counts its launches and remembers its last request in the preferences, under the keys `review.*`, so write nothing there.

The store decides whether the dialog shows. iOS shows it in a debug build each time, never in TestFlight, and at most three times in 365 days. Google Play shows it only in an app that it installed, such as from an internal test track. On a device without the review service of Google Play, such as an emulator without the Play Store, the store cannot take the request and the app records nothing, so the next call of `appReview.requestIfDue()` asks again, also in the same launch. On a device with the Play Store, for an app that Google Play did not install, such as a local build, the request completes and shows nothing, and the app counts it as a request, so it does not ask again in that version of the app.

`appReview.openStorePage()` opens the page of the app in its store, and `appReview.openStorePage(review: true)` the page where the user writes a review. On Android that is the Google Play page of `com.example.my_app` (`googlePlayId`), the id of the flavor for a release, also from a build of another flavor. On iOS it is the App Store page of `REVIEW_APP_STORE_ID` in `.env`, the Apple ID of the app in App Store Connect. While that key is empty, the app has no App Store page, and `appReview.hasStorePage` is `false` on iOS.

## Update required

While the version of the app is below the lowest version that may run, the screen "Update required" takes the place of the app, and its button "Update" opens the page of the app in its store. The lowest version is `update_required_minimum_version`, a parameter of remote config (see the section Remote config), whose default is empty, which is no lowest version. Raise it in the backend of remote config, and the screen shows without a new version of the app: at the next start, or while the app runs once the new value comes. Lower it or empty it, and the user is back where they were.

The version of the app is its version name, such as `1.4.0` of `version: 1.4.0+12` in `pubspec.yaml`, without the build number. The two compare number by number, and a missing number is 0, so `1.2` equals `1.2.0` and `1.10.0` is above `1.9.2`. A lowest version that is not one to four numbers between dots, such as `2.0.0-beta`, keeps the app running, and a debug build prints why. The comparison is in `lib/features/update_required/version_compare.dart`.

The screen is hard until the user taps "Update". From then on, or at once when no app of the device opened the store page, which the screen says, it also offers "Not now", which lets the user in for this launch. A store page that does not answer within 10 seconds counts as opened. So a lowest version above the version that the store has, set before the review of a release or during a staged rollout, costs a user one trip to the store and never locks anyone out. The next launch, and another lowest version, show the screen again.

The store page is that of the section Store reviews: on Android the page of the app in Google Play, and on iOS its page in the App Store, which needs the App Store ID of the app in `REVIEW_APP_STORE_ID` of `.env`. Without it, the app has no store page on iOS, and the screen never shows there: a debug build says so. Before the app is in Google Play, "Update" leads to a page that says the item was not found.

The guard `update_required.supported` of `routeGuards` shows the screen, `lib/features/update_required/update_required_screen.dart`, in place of every other screen, and `updateStatus` of `lib/features/update_required/update_status.dart` has what it reads, so nothing navigates to the screen. Its texts are texts of the module. In an app with localization, they are texts of the app, which the screen reads from `context.l10n`: change them where the provider of the localization keeps the texts of the app, in each language. In an app without it, they are the English texts in that file. In an app with an onboarding, the order of the modules of the app decides which of the two comes first on a launch that needs both: the guard of the module that comes first in the app.

The stores have no forced update of their own: Apple has no API for it, and the app only shows this screen. Raise the lowest version only when the old versions really cannot work any more, such as after a change of your backend that they do not understand, and only once the new version is in both stores for every user. Never raise it above the last version that the oldest system that the app supports can install: a user on that system can update to nothing newer. Where the backend of remote config gives a parameter a value for each platform, give each platform its own lowest version when the stores differ.

An app that stays offline never learns a new lowest version, and a user may stay on an old version with "Not now", so only the backend of the app can really refuse an old version, such as by the version that each request names.

import 'package:my_app/core/preferences/shared_app_preferences.dart' as impl0;

/// The settings of the app that are no secret, which it remembers between
/// its launches: the theme mode, the language, whether the user has seen
/// the onboarding.
///
/// Nothing here is encrypted, and a backup of the device carries it: never
/// store a token, a password, an API key or an encryption key in the
/// preferences.
///
/// A key is `<owner id>.<setting>`, such as `theme.mode`, where the owner
/// is the module or the role whose code keeps the setting. A key has one
/// value: a write replaces what the key had, a value of another type too.
///
/// A read is synchronous, from memory, and never throws: it returns `null`
/// when the key has no value of the type it asks for. Whether a number
/// saved as an `int` is read as a `double`, or the other way round, is up
/// to the provider of the preferences. Once the future of a write
/// completes, reads return what it saved, in this run of the app and after
/// its next launch.
abstract interface class AppPreferences {
  /// The text saved under [key], or `null` if it has none.
  String? getString(String key);

  /// The flag saved under [key], or `null` if it has none.
  bool? getBool(String key);

  /// The whole number saved under [key], or `null` if it has none.
  int? getInt(String key);

  /// The number saved under [key], or `null` if it has none.
  double? getDouble(String key);

  /// A copy of the list of texts saved under [key], or `null` if it has
  /// none: a change of the list changes nothing that is saved.
  List<String>? getStringList(String key);

  /// Saves the text [value] under [key].
  Future<void> setString(String key, String value);

  /// Saves the flag [value] under [key].
  Future<void> setBool(String key, bool value);

  /// Saves the whole number [value] under [key].
  Future<void> setInt(String key, int value);

  /// Saves the number [value] under [key].
  Future<void> setDouble(String key, double value);

  /// Saves a copy of the list of texts [value] under [key]: a later change
  /// of [value] changes nothing that is saved.
  Future<void> setStringList(String key, List<String> value);

  /// Removes what is saved under [key], which puts its setting back to its
  /// default: the reads of [key] return `null` again.
  Future<void> remove(String key);
}

/// parts; `bootstrap()` awaits it before the first frame, and nothing else
/// in the app calls it.

/// preferences, such as the theme mode. [initPreferences] calls each with
/// the preferences once they are open, so that every part has its settings
/// before the first frame.
///
/// A restorer reads its settings, and keeps the preferences for the writes
/// of its part. It is synchronous and awaits nothing: nothing waits for an
/// asynchronous one, and what such a one throws is not caught. It may run
/// again, with preferences that were opened anew.
final List<void Function(AppPreferences preferences)> _restorers = [
  restoreReview,
];

/// Calls each of [_restorers] with [preferences] on its own: what one
/// throws, an error or an exception, keeps no other from restoring and does
/// not stop the start-up of the app, which goes on with the defaults of
/// that part. In debug mode it is printed, so that a restorer that fails

void _restore(AppPreferences preferences) {

      restore(preferences);
    } on Object catch (error) {

      }

/// package, which keeps them in DataStore on Android and in `UserDefaults`
/// on iOS.
///
/// Neither is encrypted, and a backup of the device carries them: never
/// store a token, a password, an API key or an encryption key in the
/// preferences.
///
/// A number is read only as the type that it was saved as: `getDouble`
/// returns `null` for a key with an `int`, and `getInt` for a key with a
/// `double`, a whole number too.
///
/// A write puts its value into memory before it saves it. If the platform
/// refuses the save, as Android does for a text that starts with the prefix
/// that shared_preferences marks a list with, the write fails, and the
/// reads of this run return the value all the same. The next launch reads
/// what was saved before the write, or nothing if the key had no value.
final class SharedAppPreferences implements AppPreferences {
  /// Creates the preferences on [SharedPreferencesWithCache], which has
  /// read what is saved.
  SharedAppPreferences(this._preferences);

  final SharedPreferencesWithCache _preferences;

  @override
  String? getString(String key) => _read<String>(key);

  @override
  bool? getBool(String key) => _read<bool>(key);

  @override
  int? getInt(String key) => _read<int>(key);

  @override
  double? getDouble(String key) => _read<double>(key);

  @override
  List<String>? getStringList(String key) => switch (_preferences.get(key)) {
    final List<Object?> list => _textsOf(list),
    _ => null,
  };

  @override
  Future<void> setString(String key, String value) =>
      _preferences.setString(key, value);

  @override
  Future<void> setBool(String key, bool value) =>
      _preferences.setBool(key, value);

  @override
  Future<void> setInt(String key, int value) => _preferences.setInt(key, value);

  @override
  Future<void> setDouble(String key, double value) =>
      _preferences.setDouble(key, value);

  /// shared_preferences keeps the list that it is given, so it gets a copy.
  @override
  Future<void> setStringList(String key, List<String> value) =>
      _preferences.setStringList(key, List.of(value));

  @override
  Future<void> remove(String key) => _preferences.remove(key);

  /// The value of [key] if it is a [T], or `null`. The reads of

  static const startWait = Duration(seconds: 1);

  /// which the device keeps, and takes those values. In an app with
  /// parameters, it then fetches new values in the background, in a later
  /// turn of the event loop, and follows those that the service tells of.
  ///

  /// [startWait]: values that come later still become [value], and the app
  /// starts without waiting for them.
  ///

  /// on: `initRemoteConfig()` does so in a test of the next launch of the
  /// app, and a test gives it a service of its own. The controller then drops
  /// the calls of the service before, and [value] has the defaults until the
  /// new service gives its values.
  Future<void> start(RemoteConfigService service) {
    unawaited(_run?.updates?.cancel());
    final run = _run = _Run(service);
    _set(RemoteValues.initial);
    if (_observer == null) {
      final observer = _observer = _ResumeObserver(_onResume);
      WidgetsBinding.instance.addObserver(observer);
    }
    final ready = _inTurn(run, () => _open(run));
    // In a later turn of the event loop, so that the code that runs right
    // after the start reads what the start made active, and the first frame
    // does not wait for the backend.
    if (_asks) unawaited(ready.then((_) => Timer.run(() => _follow(run))));
    return ready.timeout(startWait, onTimeout: () {});
  }

  /// Opens the service of [run], and makes active what the device kept.

    await run.service.open(

      fetchInterval: fetchInterval,
      fetchTimeout: fetchTimeout,
    );
    run.opened = true;
    await _activate(run);
  }

  /// Follows the backend with the service of [run], once it opened: listens
  /// to the values that the service tells of, if it tells of any, and
  /// fetches. It runs in a turn of the event loop of its own, where no call
  /// awaits it, so an error of the service that it meets is printed as any
  /// other, and the fetch still comes.
  void _follow(_Run run) {
    if (!identical(run, _run) || !run.opened) return;
    final service = run.service;
    try {
      if (service.liveUpdates) {
        run.updates = service.updates.listen(
          (_) => _activateLater(run),
          onError: (Object error) => _report(error),
        );
      }
    } on Object catch (error) {
      _report(error);
    }
    _fetchLater(run);
  }

  /// controller fetches again, which the provider throttles to
  /// [fetchInterval].
  void _onResume() {
    final run = _run;
    if (run != null && _asks && run.opened) _fetchLater(run);
  }

  /// Fetches with the service of [run] in its turn and makes what it got
  /// active, unless a fetch waits for its turn already.
  void _fetchLater(_Run run) {
    if (run.fetchWaits) return;
    run.fetchWaits = true;
    unawaited(
      _inTurn(run, () async {
        run.fetchWaits = false;
        await run.service.fetch().timeout(fetchTimeout + fetchGrace);
        await _activate(run);
      }),
    );
  }

  /// Makes active in its turn what the service of [run] told of, unless an
  /// activation waits for its turn already.
  void _activateLater(_Run run) {
    if (run.activationWaits) return;
    run.activationWaits = true;
    unawaited(
      _inTurn(run, () {
        run.activationWaits = false;
        return _activate(run);
      }),
    );
  }

  /// Makes active what the last fetch of the service of [run] got, and takes
  /// the active values, while the controller has that service.
  Future<void> _activate(_Run run) async {
    if (!identical(run, _run)) return;
    await run.service.activate();

      _set(RemoteValues.of(run.service.values, onInvalid: _printInvalid));
    }
  }

  /// Runs [job] once the calls of [run] made before it are over, unless the
  /// controller has another service by then. An error of [job] keeps the
  /// values.
  Future<void> _inTurn(_Run run, Future<void> Function() job) async {
    final earlier = run.last;
    final done = Completer<void>();
    final own = run.last = done.future;
    try {
      if (earlier != null) await earlier;
      if (identical(run, _run)) await job();
    } on Object catch (error) {
      _report(error);
    } finally {
      if (identical(run.last, own)) run.last = null;
      done.complete();
    }
  }

  /// Takes [values] as [value], and tells the listeners when that changes
  /// it.
  void _set(RemoteValues values) {
    if (values == _values) return;
    _values = values;
    notifyListeners();
  }

  /// Prints [error] of the service in a debug build, which no caller sees.
  void _report(Object error) {
    if (kDebugMode) {
      debugPrint('Remote config keeps its values; its service failed: $error');
    }
  }

  /// Prints once in a debug build that [text], the value that the backend

/// config implements: it keeps on the device what the last fetch got, and

/// each parameter of the app, which returns the value that the backend gave
/// the parameter, or its default while the backend gives none.
///
/// Add a parameter: give it a default in [defaults] and a getter, and create
/// it in the backend of the provider with the same name and type. Every value
/// reaches every installation that fetches it, where anyone can read it, so
/// never put a secret into remote config.
@immutable
final class RemoteValues {
  const RemoteValues._(this._values);

  /// Each parameter of the app by name, with the value that the app reads
  /// while the backend gives none, whose type is the type of the parameter:
  /// a `String`, a `bool`, an `int` or a `double`.
  static const Map<String, Object> defaults = {
    'update_required_minimum_version': '',
  };

  /// The values while the backend gives none: the [defaults].
  static const initial = RemoteValues._(defaults);

  /// The values of [texts], the active values that the backend gave, by
  /// parameter: each parameter of the app takes its text as the type of its
  /// default takes it, and its default when [texts] lacks it or when the type
  /// does not take the text, which [onInvalid] is told of.
  ///
  /// A `bool` takes `true` and `false`, in any case; an `int` what
  /// [int.tryParse] takes; a `double` a finite number that [double.tryParse]
  /// takes; and a `String` any text.
  factory RemoteValues.of(
    Map<String, String> texts, {
    void Function(String parameter, String text)? onInvalid,
  }) {
    final values = <String, Object>{};
    for (final MapEntry(key: parameter, value: fallback) in defaults.entries) {
      final text = texts[parameter];
      final value = text == null ? fallback : _parsed(text, fallback);
      if (text != null && value == null) onInvalid?.call(parameter, text);
      values[parameter] = value ?? fallback;
    }
    return RemoteValues._(values);
  }

  /// [text] as a value of the type of [fallback], or `null` if that type does
  /// not take it.
  static Object? _parsed(String text, Object fallback) => switch (fallback) {
    bool() => switch (text.toLowerCase()) {
      'true' => true,
      'false' => false,
      _ => null,
    },
    int() => int.tryParse(text),
    double() => switch (double.tryParse(text)) {
      final number? when number.isFinite => number,
      _ => null,
    },
    _ => text,
  };

  final Map<String, Object> _values;

  /// The lowest version of the app that may run, such as 1.4.0; empty for none
  String get updateRequiredMinimumVersion =>
      _values['update_required_minimum_version']! as String;

  @override
  bool operator ==(Object other) =>
      other is RemoteValues &&
      defaults.keys.every(
        (parameter) => _values[parameter] == other._values[parameter],
      );

  @override
  int get hashCode => Object.hashAll([
    for (final parameter in defaults.keys) _values[parameter],
  ]);

      try {

        await _preferences?.setString(_askedVersionKey, version);

      }
    } on Object catch (error) {
      _tell('The request for a review failed: $error');
    }
  }

  /// controller remembers. A request whose time is to come, as after the

    final now = _now();

      return false;
    }
    final askedAt = _askedAt;
    if (askedAt == null) return true;
    final since = now.difference(askedAt);
    return !since.isNegative && since >= ReviewPolicy.between;
  }

      _tell('The version of the app is unknown: $error');
    }

      _tell(
        'The version of the app is unknown, so the app asks for no review.',
      );
    }
    return null;
  }

  /// [service] tells: `false` if it fails to tell.
  Future<bool> _isAvailable(ReviewService service) async {
    try {

    } on Object {

    }
  }

/// A guard of the routes of the app. Without [routes] it is a gate: while
/// it does not allow, the router shows its target in place of every
/// location outside its flow. With [routes] it keeps the user only from
/// those routes, and the router shows every other route as it is.
///
/// While a gate does not allow, `go()`, `push()` and `replace()` of a
/// location that it keeps the user from show its target in place of the
/// whole stack, and `push()` completes with `null`. Once it allows, the
/// router shows the location that the user last asked for, or the one that
/// the gate took the user from if it [resumes], or else the screen that
/// the app starts on.

/// opens its target over the page that the user is on, and the request
/// waits. Back returns to that page and drops the request. Once the guard
/// allows, the router closes the pages of the flow and does what was asked:
/// `push()` shows the location over the page that the user was on, and
/// completes with the value of its page, `go()` shows it in place of the
/// stack, and `replace()` in place of that page. A further request for one
/// of the [routes] does nothing while the flow is open. A location from
/// the platform opens the target over the screen that the app starts on.
/// When the guard stops allowing, the router closes each page of its
/// [routes] and the pages over it.
///
/// The routes of its flow show only while it does not allow, or while
/// another guard with the same flow does not. At any other time the router
/// shows the screen that the app starts on in place of a location of the
/// flow (see [flowIsOver]), or the target of a gate while that one does
/// not allow. So the code of the app changes what [allows] reads. It
/// navigates into a flow only while a guard with [routes] and that flow
/// does not allow and every gate does, as to a sign-in that a guest opens.

  /// Whether the guard lets the user see the locations that it keeps them

  /// The target of the guard: the location that the router shows while the
  /// guard does not allow.
  final AppLocation redirectTo;

  /// The full names of the routes that the user may see while the guard
  /// does not allow: the route of [redirectTo] and the routes below it.
  /// Once every guard with this flow allows, the router shows none of them.
  final Set<String> flow;

  /// Whether the router brings the user back to the location that the
  /// guard takes them from when it stops allowing, once it allows again.
  ///

  /// stops allowing: where the user was, whichever gate took them from

  /// allow, the user comes to the screen that the app starts on, as the
  /// next user does after a sign-out, unless a location was asked for

  ///   into the app. The request that waits is the page itself: asked
  ///   about again once the flow closes, it is answered with [start],
  ///   where the user is then. A flow that a gate keeps open too is the
  ///   gate's, and takes the place of the stack.
  ///
  /// For a guard with routes the class remembers no location, only over
  /// how many pages its flow was opened, for [changed]. So the answer
  /// depends on [onTopOf] and not on what the class answered before. Asked
  /// again about a location that it answered [ShowOver] for, with a page of
  /// the flow among [onTopOf], it answers [ShowNothing] for a location that
  /// the guard keeps the user from and `null` for a page of the flow. With
  /// no pages it answers [ShowOver] again, so a router never asks with none
  /// about a location that it shows over a page.
  ///
  /// What a gate made the class remember is forgotten when no gate keeps
  /// the user from the location and it is outside every flow, or in one
  /// that is over: the user has moved on, as when the code of the app
  /// navigates right when a gate starts allowing. Before that, it is
  /// forgotten if a guard that does not bring the user back stopped
  /// allowing, as [changed] says.
  WhenAsked<L>? asked(
    String? route,
    L location, {
    required Iterable<String?> onTopOf,
  }) {
    _forgetAfterStop();
    final guard = _guardKeepingFrom(route);
    if (guard != null && guard.routes == null) {
      if (!_inAFlow(route)) _remembered = (route: route, location: location);
      return ShowInstead(locationOf(guard.redirectTo));
    }
    final over = flowIsOver(route);
    if (over || !_inAFlow(route)) _remembered = null;
    if (over) return ShowInstead(start);
    if (guard == null) {
      final flow = onTopOf.isEmpty ? _openFlowOf(route) : null;
      if (flow == null) return null;
      _below = 0;
      return ShowOver(location, flow: flow);
    }
    if (onTopOf.any(guard.flow.contains)) return const ShowNothing();
    _below = onTopOf.length;
    return ShowOver(locationOf(guard.redirectTo), flow: guard.flow);
  }

  /// What the router does now that a guard started or stopped allowing, or
  /// `null` to leave its pages as they are. With `null` the router changes
  /// nothing: its pages stay, and so do the routes without a page that code
  /// pushed over them, such as a dialog or the screen that the action of an
  /// onboarding step shows.
  ///
  /// [pages] are the pages that the user can get back to, the one on top
  /// first: those of the root navigator and of the selected branch of the
  /// main navigation, each with the full name of its route, its location,
  /// and whether the router can close it on its own and leave the pages
  /// below it as they are. That holds for a page that `push()` showed, and
  /// for one that `replace()` showed in place of such a page. There are
  /// none for a router that has no page yet.
  ///
  /// First, the remembered location is forgotten if a guard that does not
  /// bring the user back (see [RouteGuard.resumes]) stopped allowing: it
  /// allowed when the class was last asked or told, and does not now. That
  /// holds whichever guard decides and whatever the pages are, and for
  /// whichever gate the location was remembered, so that the next user
  /// does not come to a location of the last one. A guard that stops and
  /// allows again without the class being asked or told in between is not
  /// seen to stop.
  ///
  /// The answer is then the first of these:
  /// - [ShowInstead] of the target of the gate that keeps the user from one
  ///   of the pages. If that gate brings the user back, the location below
  ///   the pages that the router can close is then remembered, or [start]
  ///   if it can close them all, unless one is remembered already or it is
  ///   in the flow of a guard.
  /// - with a location remembered: `null` while a gate keeps the user from
  ///   it. Otherwise the location is forgotten, and the answer is
  ///   [ShowInstead] of it, or of [start] if a guard with
  ///   [RouteGuard.routes] keeps the user from it: the class cannot keep a
  ///   request waiting, so the user moves on to [start].
  /// - for the lowest page that has to leave, which is in a flow that is
  ///   over (see [flowIsOver]) or which a guard with [RouteGuard.routes] keeps
  ///   the user from: [ClosePages] of that page and the pages over it, if the
  ///   router can close each of them and a page stays below; and else
  ///   [ShowInstead] of [start]. The request that waits is dropped when the
  ///   pages that close reach below the flow that [asked] opened last: the
  ///   page that the request was made on closes then, as when it asks for
  ///   a condition that stopped holding while the flow of another one was
  ///   open over it.
  ///
  /// So the pages of a flow close once its guards allow, also below a page
  /// that was pushed from them, and a page that asks for a condition
  /// closes when the condition stops holding. A page that took the place
  /// of the stack, as after `go()` to it, has nothing below it: the user
  /// then comes to [start].
  ///
  /// A known limit of the second answer: a location that a guard with
  /// [RouteGuard.routes] keeps the user from, and that was asked for
  /// behind a gate, is lost once the gate allows. A link to such a route
  /// that opens the app on a first launch, behind an onboarding, leaves
  /// the user on [start], though [asked] opens the flow of the guard over
  /// [start] for the same link when no gate is in its way.
  WhenChanged<L>? changed(
    Iterable<({String? route, L location, bool pushed})> pages,
  ) {
    _forgetAfterStop();
    final all = pages.toList();
    for (final page in all) {
      final gate = _guardKeepingFrom(page.route);
      if (gate == null || gate.routes != null) continue;
      final below = all.where((other) => !other.pushed).firstOrNull;
      if (gate.resumes && _remembered == null && !_inAFlow(below?.route)) {
        _remembered = (
          route: below?.route,
          location: below == null ? start : below.location,
        );
      }
      return ShowInstead(locationOf(gate.redirectTo));
    }
    if (_remembered case final remembered?) {
      final guard = _guardKeepingFrom(remembered.route);
      // The pages are those of the flow of the gate, which is not over.
      if (guard != null && guard.routes == null) return null;
      _remembered = null;
      return ShowInstead(guard == null ? remembered.location : start);
    }
    // No gate keeps the user from a page, so a guard that does is one with
    // routes.
    final lowest = all.lastIndexWhere(
      (page) => flowIsOver(page.route) || _guardKeepingFrom(page.route) != null,
    );
    if (lowest < 0) return null;
    final closed = lowest + 1;
    return all.take(closed).every((page) => page.pushed) && closed < all.length
        ? ClosePages(closed, dropsRequest: all.length - closed < _below)
        : ShowInstead(start);
  }

  /// Forgets the remembered location if a guard that does not bring the
  /// user back stopped allowing since the class last looked at the guards,
  /// and notes which of those guards allow now.
  void _forgetAfterStop() {
    for (final guard in routeGuards) {
      if (guard.resumes) continue;
      if (guard.allows.value) {
        _allowed.add(guard);
      } else if (_allowed.remove(guard)) {
        _remembered = null;
      }
    }
  }

  /// Whether [route] is in the flow of a guard, of whichever guard.
  static bool _inAFlow(String? route) =>
      routeGuards.any((guard) => guard.flow.contains(route));

  /// The flow that [route] is a page of and that only guards with
  /// [RouteGuard.routes] keep open: that of the first guard that does not
  /// allow and has the route in its flow; or `null` if there is none, or if
  /// a gate that does not allow has the route in its flow too, since the
  /// flow of a gate takes the place of the stack.
  static Set<String>? _openFlowOf(String? route) {
    Set<String>? flow;
    for (final guard in routeGuards) {
      if (guard.allows.value || !guard.flow.contains(route)) continue;
      if (guard.routes == null) return null;
      flow ??= guard.flow;
    }
    return flow;
  }
}

  /// Drops the request that waits, if there is one.

  /// Closes the [count] pages on top, each of which a push showed. Then it
  /// drops the request that waits, with [dropsRequest], or else makes it
  /// again, if no page of its flow is left. The listeners of the screen
  /// hear of the page that the user ends on.
  ///

  /// `restore()` of its pages without them. `pop()` would close what the
  /// navigator shows on top, such as a dialog over the page, and it cannot
  /// close a page that a push of the same turn showed, which the navigator
  /// has not built yet.
  ///
  /// go_router does not complete the push of a page that leaves that way,
  /// so the router does, once the frame is over. Until its next build the
  /// navigator still has the routes of those pages. When one of them is
  /// popped in that time, by the code of its screen or by the back button
  /// of the system, go_router completes its push itself, and would throw
  /// on a push that is completed already.

    _waiting = null;

      final shown = config.routerDelegate.currentConfiguration;
      final closing = _pushedPages(
        shown.matches,

      }

  /// Whether a page of a route of [flow] is among the pages of the router.
  bool _shows(Set<String> flow) =>

  /// the router can close on its own, and, below them, the location that

    if (configuration.isEmpty && !configuration.isError) return const [];

    return [

  /// Tells the guards of the pages of the router when one of them starts
  /// or stops allowing, and does what they answer: goes to a location,
  /// which is the target of the gate that keeps the user from one of the
  /// pages, the location that the user comes back to once the gates allow
  /// it, or `/`; or closes the pages on top, those of a flow that is over
  /// or of routes whose condition stopped holding.
  ///
  /// The router listens to the guards itself rather than through the
  /// `refreshListenable` of go_router, whose refresh asks only about the
  /// location below the pushed pages. Before its first location, it has no
  /// page to tell the guards of, and no stack that an answer of theirs
  /// could take the place of: go_router asks them about that location when
  /// it shows it.
  void _guardsChanged() {
    final pages = _pages;
    if (pages.isEmpty) return;
    switch (_guards.changed(pages)) {
      case null:
        break;
      case ShowInstead(:final location):
        _own(() => config.go(location));
      case ClosePages(pages: final count, :final dropsRequest):
        _close(count, dropsRequest: dropsRequest);
    }
  }

  /// Follows the pages of go_router, whose delegate notifies its listeners
  /// of each change of them: keeps each push completing with the value of
  /// its page, and tells the listeners of the screen about the page on top.
  /// And it drops the request that waits for a flow once no page of the
  /// flow is among the pages, as when the user went back from it or another
  /// location took the place of the stack.
  void _pagesChanged() {
    _keepPushes();
    if (_waiting case final waiting? when !_shows(waiting.flow)) _drop();
    if (_muted) return;
    _showScreen();
  }

  /// Lets each push complete with the value that its page returns when it
  /// closes, whatever completer go_router gives the page.
  ///
  /// go_router completes a push with the completer that it gives the page
  /// it pushed, which the page completes when it closes. When go_router
  /// shows its pages anew from their encoded form, as on [GoRouter.refresh],
  /// such as when its `refreshListenable` notifies, it gives each pushed
  /// page a new completer, though the page keeps its key and its location,
  /// so the push would never complete
  /// (https://github.com/flutter/flutter/issues/128122). So when a page
  /// comes back at its location with another completer, the router passes
  /// on the value of that completer to that of the push. A branch of the
  /// main navigation that is not selected keeps its pages as they were, so
  /// a page that comes back with its branch passes on its value as before.
  /// Once go_router keeps the completers of its pages, this does nothing
  /// and can go.
  void _keepPushes() {
    final pushed = {
      for (final page in _pushedPages(
        config.routerDelegate.currentConfiguration.matches,
      ))
        page.pageKey: page,
    };
    for (final page in pushed.values) {
      final before = _pushed[page.pageKey];
      if (before == null ||
          before.completer == page.completer ||
          before.matches.uri != page.matches.uri) {
        continue;
      }
      final push = _pushes[before.completer] ?? before.completer;
      _pushes[page.completer] = push;
      unawaited(
        page.completer.future.then((value) {
          if (!push.isCompleted) push.complete(value);
        }),
      );
    }
    _pushed = pushed;
  }

  /// The pages that pushes showed among [matches], in the stacks of the
  /// main navigation too.
  static Iterable<ImperativeRouteMatch> _pushedPages(
    List<RouteMatchBase> matches,
  ) sync* {
    for (final match in matches) {
      if (match is ImperativeRouteMatch) yield match;
      if (match is ShellRouteMatch) yield* _pushedPages(match.matches);
    }
  }

  /// Tells the listeners of the screen about the page on top when another
  /// page comes on top, or the page on top shows another location.
  ///
  /// The delegate of go_router notifies its listeners once for each change
  /// of its configuration, a switch of branches included, and may do so
  /// again without a change of the page on top, which the listeners of the
  /// screen do not hear of twice. The location of a pushed page is its own,
  /// as that of the configuration leaves pushed pages out. The error screen
  /// of go_router has no route match, or, for a location pushed in error, a
  /// route without a name.
  void _showScreen() {
    final configuration = config.routerDelegate.currentConfiguration;
    final top = configuration.lastOrNull;
    final location = switch (top) {
      ImperativeRouteMatch(:final matches) => matches.uri.toString(),
      _ => configuration.uri.toString(),
    };
    final screen = (top?.pageKey, location);
    if (screen == _screen) return;
    _screen = screen;
    for (final listener in _screenListeners) {
      _callAlone(listener, top?.route.name, location);
    }
  }
}

/// Paints a dashed edge around the box that it is given, in [color].
class _DashedEdge extends CustomPainter {
  const _DashedEdge(this.color);

  final Color color;

  @override
  void paint(Canvas canvas, Size size) {
    const dash = 6.0;
    const gap = 4.0;
    final paint = Paint()
      ..color = color
      ..strokeWidth = 1.5;
    final edge = (Offset.zero & size).deflate(0.75);
    for (final (from, to) in [
      (edge.topLeft, edge.topRight),
      (edge.topRight, edge.bottomRight),
      (edge.bottomRight, edge.bottomLeft),
      (edge.bottomLeft, edge.topLeft),
    ]) {
      final length = (to - from).distance;
      final along = (to - from) / length;
      for (var start = 0.0; start < length; start += dash + gap) {
        canvas.drawLine(
          from + along * start,
          from + along * math.min(start + dash, length),
          paint,
        );
      }
    }
  }

  @override
  bool shouldRepaint(_DashedEdge oldDelegate) => oldDelegate.color != color;
}

    // and bold for a user who asks for bold text.
    var style = DefaultTextStyle.of(context).style.merge(this.style);
    if (MediaQuery.boldTextOf(context)) {
      style = style.merge(const TextStyle(fontWeight: FontWeight.bold));
    }
    final scaler = MediaQuery.textScalerOf(
      context,
    ).clamp(maxScaleFactor: maxScaleFactor);
    return LayoutBuilder(
      builder: (context, constraints) {
        final room = constraints.maxWidth;
        final painter = TextPainter(
          textDirection: Directionality.of(context),
          textScaler: scaler,
          maxLines: 1,
        );
        // The words of the text, between its white spaces, where a line may
        // break: every one but a no-break space, which keeps the words
        // around it together.
        final words = text.split(RegExp(r'[^\S\u00A0\u2007\u202F]+'));
        // How wide the longest word is in a font of [size].
        double widestAt(double size) {
          var widest = 0.0;
          for (final word in words) {
            painter
              ..text = TextSpan(
                text: word,
                style: style.copyWith(fontSize: size),
              )
              ..layout();
            if (painter.width > widest) widest = painter.width;
          }
          return widest;
        }

        // The size of a text of Flutter whose style gives none.
        var size = style.fontSize ?? 14;
        var widest = widestAt(size);
        // In a few steps: the text size of a device may grow a small font
        // by more than a large one.
        for (var step = 0; step < 4 && widest > room && room > 0; step++) {
          // A little smaller than the width allows, so that the rounding of
          // the layout breaks no word.
          size *= room / widest * 0.98;
          widest = widestAt(size);
        }
        painter.dispose();
        return Text(
          text,
          style: style.copyWith(fontSize: size),
          textAlign: textAlign,
          textScaler: scaler,
        );
      },
    );
  }

    }

  /// does not answer within [storeWait] counts as opened. A tap while the

    _storeVisit.value = opened ? StoreVisit.opened : StoreVisit.failed;

  /// screen that the screen "Update required" took the place of.
  ///

  /// again, and so does the next launch.
  void continueForNow() {
    if (_storeVisit.value == StoreVisit.none) return;
    _waived = minimum;
    _update();
  }

  /// config.

    final minimum = this.minimum;
    final version = _version;
    var supported = true;
    if (version != null && minimum.isNotEmpty) {

          'not numbers between dots, such as 1.4.0, so the app runs.',
        );

        if (_review.hasStorePage) {

            'put the App Store ID of the app into REVIEW_APP_STORE_ID of '
            '.env.',
          );
        }
      }
    }
    // The screen is hard again each time it takes the place of the app.
    if (!supported && _supported.value) _storeVisit.value = StoreVisit.none;
    _supported.value = supported;
  }

  /// Prints [message] once in a debug build, for the developer of the app.
  void _tell(String message) {
    if (kDebugMode && _told.add(message)) debugPrint(message);
  }

// The versions of the app as the screen "Update required" compares them: the
// version of the app, such as 1.4.0 of `version: 1.4.0+12` in its pubspec,
// against the lowest version that may run. The file needs nothing but Dart.

/// A number of a version: digits alone.
final RegExp _number = RegExp(r'^[0-9]+$');

/// The numbers of [version], such as `[1, 4, 0]` for `1.4.0`, or `null` when
/// it is no version: one to four whole numbers between dots, such as `2`,
/// `1.4` or `1.4.0.2`. A build number after `+`, as in `1.4.0+12`, does not
/// count, nor do spaces around the version. A pre-release, such as
/// `2.0.0-beta`, is no version here.
List<int>? versionNumbers(String version) {
  final name = version.trim().split('+').first.trim();
  final parts = name.split('.');
  if (parts.length > 4) return null;
  final numbers = <int>[];
  for (final part in parts) {
    final number = _number.hasMatch(part) ? int.tryParse(part) : null;
    if (number == null) return null;
    numbers.add(number);
  }
  return numbers;
}

/// Whether [version], the version of the app, is below [minimum], the lowest
/// version that may run.
///
/// The two compare number by number, and a missing number is 0: `1.2` equals
/// `1.2.0`, and `1.10.0` is above `1.9.2`. An empty minimum, or one of
/// spaces, is none. A version or a minimum that is no version (see
/// [versionNumbers]) is below nothing, so the app runs.
bool versionBelow(String version, String minimum) {
  final numbers = versionNumbers(version);
  final lowest = versionNumbers(minimum);
  if (numbers == null || lowest == null) return false;
  for (var index = 0; index < 4; index++) {
    final number = index < numbers.length ? numbers[index] : 0;
    final least = index < lowest.length ? lowest[index] : 0;
    if (number != least) return number < least;
  }
  return false;
}

// Configures Firebase for one flavor of the app, with the FlutterFire CLI:
//
//     dart tool/configure_firebase.dart <flavor> --project=<id>
//
// In a terminal, without --project, flutterfire asks for the project. The
// other arguments go to flutterfire as they are, such as --account=<email>.
//
// flutterfire writes one iOS build configuration in a run, and the build of
// each needs its entry in firebase.json, so on macOS this script runs it once
// for each. Run it again at any time: it changes nothing but the ids of the
// build phases that flutterfire added, or moves the flavor to another project.
//
// Then it formats the options that flutterfire wrote, and runs each Dart file
// of tool/firebase_configured by the order of their names, for what has to
// follow every run of flutterfire.

import 'dart:convert';
import 'dart:io';

/// The Android application id and the iOS bundle id of a flavor, each `null`
/// for a platform that the app does not have, and its Xcode build
/// configurations.
typedef _Flavor = ({String? android, String? ios, List<String> configurations});

/// The flavors of the app. SMF wrote their ids from the ids of the app: if you
/// change them in the Android and Xcode projects, change them here too.
const Map<String, _Flavor> _flavors = {
  'dev': (
    android: 'com.example.my_app.dev',
    ios: 'com.example.my-app.dev',
    configurations: ['Debug-dev', 'Profile-dev', 'Release-dev'],
  ),
  'staging': (
    android: 'com.example.my_app.staging',
    ios: 'com.example.my-app.staging',
    configurations: ['Debug-staging', 'Profile-staging', 'Release-staging'],
  ),
  'prod': (
    android: 'com.example.my_app',
    ios: 'com.example.my-app',
    configurations: ['Debug-prod', 'Profile-prod', 'Release-prod'],
  ),
};

/// The platforms of the app.
const _platforms = 'android,ios';

/// The directory of what has to follow every run of flutterfire.
const _hooks = 'tool/firebase_configured';

/// What flutterfire_cli 1.4.1 takes with `--android-package-name`, as
/// `validateAndroidPackageName` of its `lib/src/common/utils.dart` checks it.
final _packageName = RegExp(
  r'^[a-zA-Z][a-zA-Z0-9]*(\.[a-zA-Z_][a-zA-Z0-9_]*)+$',
);

/// What flutterfire_cli 1.4.1 takes with `--ios-bundle-id`, as
/// `validateAppBundleId` of the same file checks it.
final _bundleId = RegExp(
  r'^([a-zA-Z0-9]([a-zA-Z0-9\-]{0,61}[a-zA-Z0-9])?|([a-zA-Z0-9]([a-zA-Z0-9\-]{0,61}[a-zA-Z0-9])?(\.[a-zA-Z0-9]([a-zA-Z0-9\-]{0,61}[a-zA-Z0-9])?)+))$',
);

Future<void> main(List<String> arguments) async {
  final script = File.fromUri(Platform.script).resolveSymbolicLinksSync();
  try {
    exitCode = await _configure(File(script).parent.parent, arguments);
  } on _Stop catch (stop) {
    stderr.writeln(stop.why);
    exitCode = 1;
  }
}

/// Why the script stops before flutterfire.
final class _Stop implements Exception {
  const _Stop(this.why);

  final String why;
}

/// Configures the flavor that [arguments] names in [app], and returns the exit
/// code of the script.
Future<int> _configure(Directory app, List<String> arguments) async {
  final (named, others) = _withoutProject(arguments);
  // The word that names a flavor, which may come after another option.
  final flavors = others.where(_flavors.containsKey).toList();
  if (flavors.length != 1) {
    throw _Stop(
      'Name a flavor: dart tool/configure_firebase.dart '
      '<${_flavors.keys.join('|')}> --project=<id>',
    );
  }
  final flavor = flavors.single;
  final ofFlavor = _flavors[flavor]!;
  final rest = [...others]..remove(flavor);
  var project = named;
  final terminal = _hasTerminal();
  if (project == null && !terminal) {
    throw _Stop(
      'Name the Firebase project: dart tool/configure_firebase.dart $flavor '
      '--project=<id>. Without a terminal, nobody can answer the question of '
      'flutterfire.',
    );
  }
  final platforms = _platformsIn(rest);
  final android = platforms.contains('android') ? ofFlavor.android : null;
  final ios = platforms.contains('ios') ? ofFlavor.ios : null;
  _checkIds(android, ios);

  // flutterfire changes the Xcode project only on macOS, so the runs differ
  // only there.
  final configurations = Platform.isMacOS && ios != null
      ? ofFlavor.configurations
      : ofFlavor.configurations.take(1);
  for (final configuration in configurations) {
    final process = await Process.start(
      Platform.resolvedExecutable,
      [
        'pub',
        'global',
        'run',
        'flutterfire_cli:flutterfire',
        'configure',
        if (project != null) '--project=$project',
        '--platforms=$_platforms',
        '--overwrite-firebase-options',
        '--out=lib/firebase_options_$flavor.dart',
        if (android != null) ...[
          '--android-package-name=$android',
          '--android-out=android/app/src/$flavor/google-services.json',
        ],
        if (ios != null) ...[
          '--ios-bundle-id=$ios',
          '--ios-out=ios/flavors/$flavor/GoogleService-Info.plist',
          '--ios-build-config=$configuration',
        ],
        ...rest,
      ],
      workingDirectory: app.path,
      // Without a terminal, flutterfire fails rather than wait for an answer.
      environment: terminal ? null : const {'CI': 'true'},
      mode: ProcessStartMode.inheritStdio,
    );
    final code = await process.exitCode;
    if (code != 0) {
      stderr.writeln(
        'flutterfire failed for the flavor $flavor (exit code $code). What it '
        'wrote stays, and running this script again does the rest. It needs '
        'the FlutterFire CLI, a login of the Firebase CLI and, on macOS, the '
        'Ruby gem xcodeproj: see the section Firebase of README.md.',
      );
      return code;
    }
    // The next runs need no answer.
    project ??= _projectOf(app, flavor);
  }

  await _format(app, flavor);
  for (final hook in _hooksOf(app)) {
    final process = await Process.start(
      Platform.resolvedExecutable,
      [hook.path],
      workingDirectory: app.path,
      mode: ProcessStartMode.inheritStdio,
    );
    final code = await process.exitCode;
    if (code != 0) {
      stderr.writeln(
        '${hook.path} failed (exit code $code). flutterfire configured the '
        'flavor $flavor, and running this script again runs it again.',
      );
      return code;
    }
  }
  stdout.writeln(
    'Configured the flavor $flavor for the Firebase project $project. Commit '
    'firebase.json and the files it names.',
  );
  if (ios != null && !Platform.isMacOS) {
    stdout.writeln(
      'flutterfire changes the Xcode project only on macOS, so this run left '
      'it and ios/flavors/$flavor/GoogleService-Info.plist as they were. Run '
      'dart tool/configure_firebase.dart $flavor again on a Mac for the iOS '
      'app.',
    );
  }
  return 0;
}

/// Whether someone can answer a question of flutterfire.
///
/// `stdin.hasTerminal` also holds for any other character device, such as the
/// `/dev/null` of cron, `nohup`, `ssh -n` or Docker without `-i`, where
/// flutterfire would wait forever. Only a terminal has an echo mode to read.
bool _hasTerminal() {
  try {
    stdin.echoMode;
    return true;
  } on StdinException {
    return false;
  }
}

/// The project that [arguments] name, as flutterfire reads it, with the last
/// one counting, and the other arguments.
(String?, List<String>) _withoutProject(List<String> arguments) {
  String? project;
  final rest = <String>[];
  for (var index = 0; index < arguments.length; index++) {
    final argument = arguments[index];
    if (argument == '--project' || argument == '-p') {
      // Another option is no id, and flutterfire would take it for one.
      if (++index == arguments.length || arguments[index].startsWith('-')) {
        throw _Stop('$argument needs the id of a Firebase project.');
      }
      project = arguments[index];
    } else if (argument.startsWith('--project=')) {
      project = argument.substring('--project='.length);
    } else if (argument.startsWith('-p')) {
      project = argument.substring('-p'.length);
    } else {
      rest.add(argument);
    }
  }
  if (project != null && project.isEmpty) {
    throw _Stop('--project needs the id of a Firebase project.');
  }
  return (project, rest);
}

/// The platforms of this run: those of the app, unless [rest] names others.
/// [rest] comes last on the command line of flutterfire, which takes the last
/// value of an option.
List<String> _platformsIn(List<String> rest) {
  var platforms = _platforms;
  for (var index = 0; index < rest.length; index++) {
    if (rest[index].startsWith('--platforms=')) {
      platforms = rest[index].substring('--platforms='.length);
    } else if (rest[index] == '--platforms' && index + 1 < rest.length) {
      platforms = rest[index + 1];
    }
  }
  return platforms.split(',');
}

/// Stops at an id that flutterfire would refuse, with what to do about it.
void _checkIds(String? android, String? ios) {
  if (android != null && !_packageName.hasMatch(android)) {
    throw _Stop(
      'flutterfire takes no application id like $android (it allows no '
      'underscore in its first part): use another org.',
    );
  }
  if (ios != null && !_bundleId.hasMatch(ios)) {
    throw _Stop(
      'flutterfire takes no bundle id like $ios (it allows no hyphen at either '
      'end of a part, and at most 63 characters in one): use another org.',
    );
  }
}

/// The project of the options of [flavor], which flutterfire wrote into
/// `firebase.json` of [app].
///
/// It reads the entry of the options: the keys of the Android apps in that
/// file depend on the path of the app.
String _projectOf(Directory app, String flavor) {
  final file = File('${app.path}/firebase.json');
  final json = file.existsSync() ? jsonDecode(file.readAsStringSync()) : null;
  Object? entry = json;
  for (final key in [
    'flutter',
    'platforms',
    'dart',
    'lib/firebase_options_$flavor.dart',
    'projectId',
  ]) {
    entry = entry is Map ? entry[key] : null;
  }
  if (entry is! String) {
    throw _Stop(
      '${file.path} names no Firebase project for the flavor $flavor, though '
      'flutterfire succeeded. Run this script again with --project=<id>.',
    );
  }
  return entry;
}

/// Formats the options of [flavor], which flutterfire writes in a format of
/// its own, so that the check of the format of the app passes. They work
/// without it, so a failure only warns.
Future<void> _format(Directory app, String flavor) async {
  final options = 'lib/firebase_options_$flavor.dart';
  final result = await Process.run(Platform.resolvedExecutable, [
    'format',
    options,
  ], workingDirectory: app.path);
  if (result.exitCode != 0) {
    stderr.writeln(
      'Warning: dart format left $options as flutterfire wrote it (exit code '
      '${result.exitCode}): ${result.stderr}',
    );
  }
}

/// The Dart files of the hooks directory of [app], by the order of their
/// names. An app whose modules have nothing to do after flutterfire has no
/// such directory.
List<File> _hooksOf(Directory app) {
  final directory = Directory('${app.path}/$_hooks');
  if (!directory.existsSync()) return const [];
  return [
    for (final entity in directory.listSync())
      if (entity is File && entity.path.endsWith('.dart')) entity,
  ]..sort((a, b) => a.path.compareTo(b.path));
}
