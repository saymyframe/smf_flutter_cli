# AGENTS.md

This guide tells coding agents what the code of this Flutter app does not show. Setup that needs a person or an account is in [README.md](README.md). When you change what a section describes, change the section too.

## App entry

The app is plain Flutter code that nothing regenerates. Change it by hand, unless a section below says what writes a file.

- `main()` in `lib/main.dart` initializes the binding, awaits `bootstrap()` and calls `runApp()`, in this order. Start-up code goes into `bootstrap()`.
- `bootstrap()` in `lib/bootstrap.dart` runs before the first frame, in four phases: what must come before anything else, then the platform services, then the services of the app, then what needs them. Put a new statement into its phase, and import neither `package:flutter/material.dart` nor `package:flutter/cupertino.dart` there.
- Put code that features share into `lib/core/<concern>/`, one directory for each concern. Put a feature, with its screens and their state, into `lib/features/<feature>/`.
- The root of the app asks the system for the icons of the status bar that suit the theme, around every screen, with `StatusBarIcons` of `lib/core/app/status_bar_icons.dart`: dark icons on a light theme, light ones on a dark theme. A screen without an app bar needs no `AnnotatedRegion` for them. Add one only to a screen whose top has another brightness than the theme, such as a picture behind the status bar.
- The app has the flavors `dev`, `staging` and `prod`. A `flutter` command without `--flavor` builds `dev`, in release mode too, so a build for a store takes `--flavor prod`. Code reads the flavor from `appFlavor` of `package:flutter/services.dart`. The app has one entry: add no `main_<flavor>.dart`.

After a change, run:

```bash
dart format lib test
flutter analyze
flutter test
```

Format only `lib/` and `test/`: `dart format .` also formats what Flutter writes into `build/`. The app as generated is formatted, `flutter analyze` finds no issue in it and `flutter test` passes.

- `App` in `lib/app.dart` is the root widget of the app and creates its one `MaterialApp`. Create no other in `lib/`: every screen is below it.
- The `theme`, `darkTheme`, `themeMode`, `locale` and localizations of the app go into the arguments of that `MaterialApp`.
- Tests mirror `lib/`: the test of `lib/<path>.dart` is `test/<path>_test.dart`.
- The app has only an Android and an iOS project, in `android/` and `ios/`.
- The entitlements of the iOS app, such as Push Notifications or Sign in with Apple, are in `ios/Runner/Runner.entitlements`. Every build configuration of the Runner target signs with this file, even while it is empty. The Signing & Capabilities tab of Xcode edits the same file.
- Each flavor is in `productFlavors` of `android/app/build.gradle.kts`, and on iOS in `ios/Runner.xcodeproj/xcshareddata/xcschemes/<flavor>.xcscheme` and in the build configurations `Debug-<flavor>`, `Profile-<flavor>` and `Release-<flavor>` of `ios/Runner.xcodeproj/project.pbxproj`. Change both places together. A new setting of the Runner target goes into each of its twelve build configurations.

## CI

- CI runs the commands of the section "Continuous integration" of `README.md`, in a fresh copy of the repository. Keep them passing, and run them before you finish a change.
- A generated file that the app needs stays in git, or comes from `flutter pub get`, since no other of these commands writes it.

- `tool/write_env.dart` writes `.env` for a build of CI, from the keys of `.env.example` and the variables of the process. A new key also needs its variable where CI runs. The script stops when `.env` has a value, and never replaces one.
- The first check copies `.env.example` only when `.env` is missing, so running it keeps the values on your machine.
- A value of `.env` ends up in the app, so never give a build of CI a secret through it.

With `GitHub Actions`:

- `.github/workflows/ci.yml` has the two jobs: `checks`, on each push, and `build`, which a developer starts for an environment.
- Never put `${{ … }}` in a `run:` line, which would make a value a part of the script. Pass the value through `env:` of the step, and read it as a variable of the shell.
- Each `uses:` line is pinned to a full commit, with its tag in a comment after it. To update an action, change the two together.

- A new key of `.env` needs a line under `env:` of the step of `build` that runs `tool/write_env.dart`, as in `MY_SERVICE_KEY: ${{ vars.MY_SERVICE_KEY }}`. Without it, a build leaves that value empty.

## Values in .env

- Read a value of `.env` only through a static getter of `AppEnv` in `lib/core/env/app_env.dart`. The getter is the key in lowerCamelCase: `AppEnv.myServiceKey` for the key `MY_SERVICE_KEY`. It returns a `String?` that is `null` while the value is empty or missing, so handle `null`. Never read `.env` or `.env.example` from code.
- Every value ends up in the app, where anyone can read it. Never put a secret into `.env`, such as the secret key of a server, a password or a private key.
- `.env` stays out of git. A new key goes into both `.env.example` and `.env`, in UPPER_SNAKE_CASE with a comment line above it, and `AppEnv` gets a getter for it.
- `.vscode/launch.json` and `.run/<flavor>.run.xml` are the run configurations of VS Code and Android Studio, one for each flavor. Each passes the flavor and the arguments that the values need. In VS Code, F5 starts the selected configuration, while the links above `main()` and above a test and the Testing view always use `dev`, whose configuration alone has `templateFor`. In Android Studio, a test gets none of these arguments.

With `--dart-define-from-file`:

- Every command of the `flutter` tool that builds, runs or tests the app takes `--dart-define-from-file=.env`, such as `flutter run --dart-define-from-file=.env`, `flutter test` and `flutter build`. Without it, every getter of `AppEnv` is `null`.
- A command reads `.env` only when it starts. After a change of `.env`, stop `flutter run` and start it again: hot reload and hot restart keep the values that the app was built with.
- The getter of a new key in `lib/core/env/app_env.dart` reads `const String.fromEnvironment('MY_SERVICE_KEY')`, with the key in place of `MY_SERVICE_KEY`, and returns `null` for an empty value, as the other getters do.

## Flavors

The app has three flavors, which install next to each other on a device, each under an id of its own:

| Flavor | Android application id | iOS bundle id |
| --- | --- | --- |
| `dev` | `com.example.my_app.dev` | `com.example.my-app.dev` |
| `staging` | `com.example.my_app.staging` | `com.example.my-app.staging` |
| `prod` | `com.example.my_app` | `com.example.my-app` |

A `flutter` command without `--flavor` builds `dev`, because `default-flavor` in `pubspec.yaml` says so. That holds in release mode too: `flutter build appbundle` and `flutter build ipa` build a release of `dev`, under its id. For a store, name the flavor:

```bash
flutter run --flavor staging
flutter build appbundle --flavor prod
flutter build ipa --flavor prod
```

Code reads the flavor from `appFlavor` of `package:flutter/services.dart`. A service that knows your app by its id, such as a store or a push provider, knows each flavor as an app of its own, so you repeat a step of its setup for each flavor that needs it.

## Flavors in the native projects

Each flavor is in two places, so change both when you rename, add or remove one:

- Android: `productFlavors` in `android/app/build.gradle.kts`, with its id suffix and its name on the device.
- iOS: `ios/Runner.xcodeproj/xcshareddata/xcschemes/<flavor>.xcscheme`, and the build configurations `Debug-<flavor>`, `Profile-<flavor>` and `Release-<flavor>` in each configuration list of `ios/Runner.xcodeproj/project.pbxproj`. The name of a flavor has no hyphen, since Flutter splits the name of a configuration on it.

In Xcode, select the scheme of a flavor, not `Runner`, which builds the id and the name of `prod`. A scheme sets only the id and the name. `appFlavor` comes from `ios/Flutter/Generated.xcconfig`, which the last `flutter` command wrote, so run `flutter build ios --config-only --flavor <flavor>` before you run the scheme from Xcode.

## Run, test and build with .env

`AppEnv` in `lib/core/env/app_env.dart` reads each value of `.env` with `String.fromEnvironment`. The `flutter` tool reads `.env` when a command that builds, runs or tests the app starts, given `--dart-define-from-file=.env`, and compiles each value into the app. Without the argument, every getter of `AppEnv` is `null`, so give it to each such command:

```bash
flutter run --dart-define-from-file=.env
flutter test --dart-define-from-file=.env
flutter build apk --flavor prod --dart-define-from-file=.env
flutter build appbundle --flavor prod --dart-define-from-file=.env
flutter build ipa --flavor prod --dart-define-from-file=.env
```

A build without `--flavor` is a release of `dev`, under its id, so a build for a store names its flavor. The section "Flavors" tells more.

A command reads the values only when it starts: after you change `.env`, stop `flutter run` and start it again. Hot reload and hot restart keep the values that the app was built with.

To read a key of your own, give `AppEnv` a getter for it, as for the other keys:

```dart
static String? get myServiceKey {
  const value = String.fromEnvironment('MY_SERVICE_KEY');
  return value.isEmpty ? null : value;
}
```

=== tool/write_env.dart (role:ci) ===
// Writes `.env` for a job of CI, from `.env.example` and the variables of the
// process. No value in the file is a secret: every value ends up in the app.
//
// A key whose variable has a value gets it, in one of the two forms of a value
// of `.env`: as it is, or in double quotes when it has white space, `#` or a
// quote. Any other line stays as `.env.example` has it. A value with a double
// quote, a control character or a line separator fits neither form, and could
// add a line of its own, so the script stops and writes nothing. It never prints
// a value.
//
// It never replaces a value. When `.env` has one, the script stops and leaves
// the file as it is, and a developer who wants it written again deletes it. A
// missing `.env`, or one without values such as a copy of `.env.example`, is
// what a job of CI starts from.
import 'dart:convert';
import 'dart:io';

final _key = RegExp(r'^\s*([A-Za-z_][A-Za-z0-9_]*)\s*=');
final _unsafe = RegExp(r'["\x00-\x1F\x7F\u2028\u2029]');
final _quoted = RegExp(r"[\s#'`]");
final _withoutValue = RegExp(
  r'^\s*(?:#.*|[A-Za-z_][A-Za-z0-9_]*\s*=\s*(?:""\s*)?(?:#.*)?)?$',
);

void main() {
  final example = File('.env.example');
  if (!example.existsSync()) {
    stderr.writeln('.env.example is missing.');
    exitCode = 1;
    return;
  }
  final env = File('.env');
  // In latin1, every file reads, so an error shows no part of a value.
  if (env.existsSync() &&
      !env.readAsLinesSync(encoding: latin1).every(_withoutValue.hasMatch)) {
    stderr.writeln(
      '.env has values, which this script would replace. Delete .env to write '
      'it again.',
    );
    exitCode = 1;
    return;
  }
  final lines = <String>[];
  final empty = <String>[];
  final refused = <String>[];
  for (final line in example.readAsLinesSync()) {
    final key = _key.firstMatch(line)?[1];
    if (key == null) {
      lines.add(line);
      continue;
    }
    final value = Platform.environment[key] ?? '';
    if (value.isEmpty) {
      if (_withoutValue.hasMatch(line)) empty.add(key);
      lines.add(line);
    } else if (_unsafe.hasMatch(value)) {
      refused.add(key);
    } else {
      lines.add('$key=${_quoted.hasMatch(value) ? '"$value"' : value}');
    }
  }
  if (refused.isNotEmpty) {
    stderr.writeln(
      'The values of ${refused.join(', ')} have a double quote, a control '
      'character or a line separator, which .env cannot hold.',
    );
    exitCode = 1;
    return;
  }
  env.writeAsStringSync('${lines.join('\n')}\n');
  stdout.writeln('Wrote .env.');
  if (empty.isNotEmpty) {
    stdout.writeln('No value for: ${empty.join(', ')}.');
  }
}
