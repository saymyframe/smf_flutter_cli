# AGENTS.md

This guide tells coding agents what the code of this Flutter app does not show. Setup that needs a person or an account is in [README.md](README.md). When you change what a section describes, change the section too.

## App entry

The app is plain Flutter code that nothing regenerates. Change it by hand, unless a section below says what writes a file.

- `main()` in `lib/main.dart` initializes the binding, awaits `bootstrap()` and calls `runApp()`, in this order. When `bootstrap()` throws, `main()` calls `showFailedStart()` of `lib/core/app/failed_start.dart` and returns: the app shows `FailedStartApp`, with the error in a debug build, and the error reaches `FlutterError.onError`. Keep the `try` around `await bootstrap()` in `main()`. Start-up code goes into `bootstrap()`. Do not catch an error there just to let the app start: fix what the error names, such as a step of the setup that has not run.
- `bootstrap()` in `lib/bootstrap.dart` runs before the first frame, in four phases: what must come before anything else, then the platform services, then the services of the app, then what needs them. Put a new statement into its phase, and import neither `package:flutter/material.dart` nor `package:flutter/cupertino.dart` there.
- Put code that features share into `lib/core/<concern>/`, one directory for each concern. Put a feature, with its screens and their state, into `lib/features/<feature>/`.
- The root of the app asks the system for the icons of the status bar that suit the theme, around every screen, with `StatusBarIcons` of `lib/core/app/status_bar_icons.dart`: dark icons on a light theme, light ones on a dark theme. A screen without an app bar needs no `AnnotatedRegion` for them. Add one only to a screen whose top has another brightness than the theme, such as a picture behind the status bar.
- The app has the flavors `dev`, `staging` and `prod`. A `flutter` command without `--flavor` builds `dev`, in release mode too, so a build for a store takes `--flavor prod`. Code reads the flavor from `appFlavor` of `package:flutter/services.dart`. The app has one entry: add no `main_<flavor>.dart`.

- The section "Finish the setup" of the README lists the steps of the setup that no command can do, such as a step in the web console of a service that the app uses. Only the developer of the app does them: when a task depends on one of them, point the developer to that section, and do not try to do the step yourself.

After a change, run:

```bash
dart format lib test
flutter analyze
flutter test
```

Format only `lib/` and `test/`: `dart format .` also formats what Flutter writes into `build/`. The app as generated is formatted, `flutter analyze` finds no issue in it and `flutter test` passes.

- `App` in `lib/app.dart` is the root widget of the app and creates its one `MaterialApp`. Every screen is below it, so create no other `MaterialApp` in `lib/`. The only other one is in `FailedStartApp`, which `main()` runs in its place when the start-up fails.

## Crash reporting

- `installCrashReporting()` of `lib/core/crash_reporting/crash_reporter.dart`, which `bootstrap()` calls, reports the errors of the main isolate that nothing handles, through `FlutterError.onError` and `PlatformDispatcher.instance.onError`. Set these two nowhere else.
- Report an error that the code catches with `recordError()` of `CrashReporter`. `createCrashReporter()` returns the one reporter of the app, which reports to every provider and never fails. Call it where the state of a screen is created, or, with a DI container in the app, take the reporter from the container instead.
- A new provider implements `CrashReporter`. The function that creates it gets an entry in `_crashReporters` in that file, `?_createAlone('<name>', <function>)`, or, if it starts asynchronously, one in `initCrashReporting()`, which the file has once a provider needs it.

With `sentry_flutter`:

- `initSentryCrashReporter()` in `lib/core/crash_reporting/sentry_crash_reporter.dart` starts Sentry with `SENTRY_DSN` of `.env`, and `bootstrap()` awaits it. Without a value of the key, the app starts without Sentry.
- Report through `CrashReporter`, not through `Sentry.captureException`. Never call `SentryFlutter.init` elsewhere: its start removes `OnErrorIntegration` and puts `FlutterError.onError` back, so that each error reaches Sentry once.
- The environment of an event is the flavor of the build (`appFlavor`), and a debug build sends its events too.
- `configureSentryForTests` changes the options of Sentry before it starts, for tests only: a test keeps the events in `beforeSend` and gives Sentry a `transport` that sends nothing. `SentryFlutter.init` never completes in the fake time of a widget test, so a test starts Sentry, or runs `bootstrap()`, in real time.

## Values in .env

- Read a value of `.env` only through a static getter of `AppEnv` in `lib/core/env/app_env.dart`. The getter is the key in lowerCamelCase: `AppEnv.myServiceKey` for the key `MY_SERVICE_KEY`. - The getter of a new key in `lib/core/env/app_env.dart` reads `const String.fromEnvironment('MY_SERVICE_KEY')`, with the key in place of `MY_SERVICE_KEY`, and returns `null` for an empty value, as the other getters do.

## Sentry

The app reports its errors to [Sentry](https://sentry.io) with [sentry_flutter](https://pub.dev/packages/sentry_flutter). `lib/core/crash_reporting/sentry_crash_reporter.dart` starts Sentry in `bootstrap()` with the DSN of `SENTRY_DSN` in `.env`, and implements the crash reporter of the app on it. While `SENTRY_DSN` has no value in a build, or one that is no DSN of Sentry, the app starts without Sentry and reports nothing to it, and a debug build prints why without the value.

Create a Flutter project in Sentry and copy its DSN into `SENTRY_DSN`. The section Finish the setup lists this among the steps that you do by hand. A DSN only lets an app send events to its project, and it goes into the app, where anyone can read it, so it is no secret. In the settings of the project, give the key of the DSN a rate limit, so that one app that fails in a loop does not use up the quota of the organization. Keep a second project for development: its DSN goes into your local `.env`, and the DSN of the project of the release goes into the values that a build for a store gets, such as those of the environment `prod` of your CI.

The environment of each event is the flavor of the build, such as `dev` or `prod`, so Sentry tells the events of a test build from those of the release. A debug build sends its events too. To keep debug builds out of Sentry, start `initSentryCrashReporter()` with this line:

```dart
if (kDebugMode) throw StateError('Sentry reports nothing from a debug build.');
```

What each start of the app sends to Sentry:

- the errors that the crash reporting of the app reports: those that nothing catches, as fatal, and those that the code reports with `recordError()`, each with the messages of `log()` before it as breadcrumbs and with the id of the user that `setUserId()` set. An error that comes before Sentry has started in `bootstrap()` is not reported;
- the native crashes of Android and iOS, which the SDKs of Sentry for the platforms record and send at the next start, and on Android an app that does not respond (ANR), on iOS an app that hangs;
- a session, from which Sentry counts the users and the starts without a crash.

Next to another crash reporter, both record the native crashes that each of them catches: an uncaught exception of Java or Kotlin reaches both, and a signal of native code on Android may reach Sentry alone. On iOS, another crash reporter may warn in the log that another handler of exceptions is installed, which does no harm. The free plan of Sentry has a monthly quota of errors, which the [pricing](https://sentry.io/pricing/) of Sentry tells.

Without `--obfuscate`, the Dart frames of an event have their functions, files and lines, also in a release build. The other cases need files that a release build writes, uploaded with an auth token of Sentry that may upload debug files, in `SENTRY_AUTH_TOKEN`:

1. The native frames of iOS need the dSYMs of the archive. After `flutter build ipa`, upload them with [sentry-cli](https://docs.sentry.io/cli/installation/):

   ```bash
   sentry-cli debug-files upload --org <org> --project <project> build/ios/archive/Runner.xcarchive/dSYMs
   ```

2. The Java and Kotlin frames of the plugins in an Android release, which R8 shrinks, need its mapping. The Gradle plugin of Sentry uploads it. Add `id("io.sentry.android.gradle") version "6.27.0"` to the `plugins` of `android/app/build.gradle.kts`, and this block below them, without which the plugin fails every release build without a token, sends telemetry of its own, and changes the bytecode of every plugin:

   ```kotlin
   sentry {
       autoUploadProguardMapping.set(providers.environmentVariable("SENTRY_AUTH_TOKEN").isPresent)
       uploadNativeSymbols.set(false)
       telemetry.set(false)
       autoInstallation { enabled.set(false) }
       tracingInstrumentation { enabled.set(false) }
   }
   ```

3. The Dart frames of a build with `--obfuscate` need its symbols. Build with `--obfuscate --split-debug-info=build/debug-info --extra-gen-snapshot-options=--save-obfuscation-map=build/app/obfuscation.map.json`, add [sentry_dart_plugin](https://pub.dev/packages/sentry_dart_plugin) `^3.5.0` to the `dev_dependencies`, give the `pubspec.yaml` of the app this block, and run `dart run sentry_dart_plugin`:

   ```yaml
   sentry:
     org: <org>
     project: <project>
     dart_symbol_map_path: build/app/obfuscation.map.json
   ```

For the privacy policy of the app, which the App Store and Google Play ask for in the listing of the app and inside the app: Sentry gets crash and diagnostic data, the id of the user once the code sets one, and the IP address of the device, which Sentry may store unless "Prevent Storing of IP Addresses" is on in the settings of the project. The SDK of Sentry for iOS declares what it collects in its privacy manifest.

/// Reports the errors of the app.
abstract interface class CrashReporter {
  /// Reports [error] with its [stackTrace]; a [fatal] error ended the app.
  Future<void> recordError(
    Object error,
    StackTrace? stackTrace, {
    bool fatal = false,
    String? reason,
  });

  /// Reports an error that Flutter caught, described by [details].
  Future<void> recordFlutterError(
    FlutterErrorDetails details, {
    bool fatal = false,
  });

  /// Adds [message] to the log sent with the next report.
  Future<void> log(String message);

  /// Sets the id of the signed-in user for the next reports, or clears it
  /// with `null`.
  Future<void> setUserId(String? userId);
}

/// Returns the crash reporter of the app, which forwards every call to the
/// crash reporters of all modules.
///
/// It calls each of them on its own, and its future completes once all of
/// them are done. A crash reporter that throws, or whose future fails,
/// keeps no other from the call, and its failure reaches neither the code
/// that called nor the handlers of [installCrashReporting], which would
/// report it to the same crash reporter again, without end. In debug mode
/// the failure is printed, so that a crash reporter that does not work,
/// such as one that is not set up, shows in the console. A crash reporter
/// whose factory throws, or that fails to start, is left out, and in debug
/// mode its error is printed.
CrashReporter createCrashReporter() => _crashReporter;

/// Reports the errors of the main isolate that nothing handles, each once.
///
/// `bootstrap()` calls it once the crash reporting services are ready. Two
/// handlers cover the main isolate:
/// - `FlutterError.onError` gets the errors that Flutter catches, such as in
///   a build or a layout, and still presents them as Flutter does by
///   default;
/// - `PlatformDispatcher.instance.onError` gets every other uncaught error,
///   such as in a `Future`, a `Timer` or the handler of a port, with its
///   type. In debug mode it leaves the error unhandled, so the engine prints
///   it.
///
/// Each report reaches every crash reporter, and the failure of a crash
/// reporter comes back to neither handler; see [createCrashReporter].
///
/// `compute()` and `Isolate.run()` throw the error of their isolate to the
/// code that awaits them, so it reaches the platform dispatcher unless that
/// code catches it. The uncaught errors of an isolate that the app spawns
/// itself go only to the error listener of that isolate, such as the
/// `onError` port of `Isolate.spawn`, so the app reports them there to its
/// crash reporter.
void installCrashReporting() {
  final reporter = createCrashReporter();
  final presentError = FlutterError.onError;
  FlutterError.onError = (details) {
    presentError?.call(details);
    unawaited(reporter.recordFlutterError(details, fatal: true));
  };
  PlatformDispatcher.instance.onError = (error, stackTrace) {
    unawaited(reporter.recordError(error, stackTrace, fatal: true));
    return !kDebugMode;
  };
}

final List<CrashReporter> _crashReporters = [];

/// Creates the implementations of CrashReporter that start
/// asynchronously; `bootstrap()` awaits it.
Future<void> initCrashReporting() async {
  final started = await Future.wait([
    _startAlone('initSentryCrashReporter', impl0.initSentryCrashReporter),
  ]);
  _crashReporters.addAll(started.nonNulls);
}

/// Calls [start], the function [name], on its own: returns what it starts,
/// or `null` if it throws or its future fails, so that the app starts and
/// works without it, and in debug mode prints the error.
Future<CrashReporter?> _startAlone(
  String name,
  Future<CrashReporter> Function() start,
) async {
  try {
    return await start();
  } on Object catch (error) {
    if (kDebugMode) {
      debugPrint('$name() failed, so the app works without it: $error');
    }
    return null;
  }
}

final class _CrashReporters implements CrashReporter {
  const _CrashReporters(this._reporters);

  final List<CrashReporter> _reporters;

  @override
  Future<void> recordError(
    Object error,
    StackTrace? stackTrace, {
    bool fatal = false,
    String? reason,
  }) => _forAll(
    (reporter) =>
        reporter.recordError(error, stackTrace, fatal: fatal, reason: reason),
  );

  @override
  Future<void> recordFlutterError(
    FlutterErrorDetails details, {
    bool fatal = false,
  }) =>
      _forAll((reporter) => reporter.recordFlutterError(details, fatal: fatal));

  @override
  Future<void> log(String message) =>
      _forAll((reporter) => reporter.log(message));

  @override
  Future<void> setUserId(String? userId) =>
      _forAll((reporter) => reporter.setUserId(userId));

  /// Calls [call] with each crash reporter on its own, and completes once
  /// all of them are done, whatever each does; see [createCrashReporter].
  Future<void> _forAll(
    Future<void> Function(CrashReporter reporter) call,
  ) async {
    await Future.wait([
      for (final reporter in _reporters) _callAlone(reporter, call),
    ]);
  }

  /// Calls [call] with [reporter], and keeps what it throws, or the error of
  /// its future, from the caller: in debug mode it prints it.
  static Future<void> _callAlone(
    CrashReporter reporter,
    Future<void> Function(CrashReporter reporter) call,
  ) async {
    try {
      await call(reporter);
    } on Object catch (error) {
      if (kDebugMode) {
        debugPrint('The crash reporter ${reporter.runtimeType} failed: $error');
      }
    }
  }
}

void Function(SentryFlutterOptions options)? configureSentryForTests;

/// Starts Sentry with the DSN of `.env` and returns a crash reporter that
/// reports to it. `bootstrap()` awaits it before it installs the handlers of
/// the crash reporting.
///
/// The handlers of the errors that nothing catches belong to the crash
/// reporting of the app, which reports each error to every crash reporter.
/// So Sentry gets no handler of its own: the start removes the integration
/// with which Sentry would take `PlatformDispatcher.instance.onError`, and
/// puts back the handler of `FlutterError.onError` that Sentry replaces, or
/// an error of Flutter would reach Sentry twice. Native crashes stay with
/// the SDKs of Sentry for Android and iOS.
///
/// The environment of the events is the flavor of the build. A debug build
/// sends its events too.
///
/// Throws a [StateError] when the build has no DSN, has a value that is no
/// DSN of Sentry, or when Sentry does not start with it: the app then reports
/// nothing to Sentry, and a debug build prints why, without the value.
Future<CrashReporter> initSentryCrashReporter() async {
  final dsn = AppEnv.sentryDsn;
  if (dsn == null) {
    throw StateError(
      'SENTRY_DSN has no value in this build, so the app reports nothing to '
      'Sentry. In .env, give it the DSN of your Sentry project, and build the '
      'app as the section "Values in .env" of its README says. The section '
      '"Sentry" tells more.',
    );
  }
  final flutterErrors = FlutterError.onError;
  try {
    await SentryFlutter.init((options) {
      options
        ..dsn = dsn
        ..environment = appFlavor ?? 'dev'
        // Sentry logs what it does in a debug build; the crash reporting of
        // the app shows the errors, and Sentry logs nothing.
        ..debug = false
        ..sendDefaultPii = false
        ..attachScreenshot = false
        ..attachViewHierarchy = false
        // An event of the app carries what it logged with log(), not what it
        // printed, which may hold what nobody meant to send.
        ..enablePrintBreadcrumbs = false;
      // By type, which a build with --obfuscate keeps, unlike a name.
      for (final integration
          in options.integrations.whereType<OnErrorIntegration>().toList()) {
        options.removeIntegration(integration);
      }
      configureSentryForTests?.call(options);
    });
  } on ArgumentError {
    // The errors of Sentry about a DSN that it does not take quote the DSN,
    // which a debug build would print.
    throw StateError(_noDsnOfSentry);
  } on FormatException {
    throw StateError(_noDsnOfSentry);
  } finally {
    FlutterError.onError = flutterErrors;
  }
  if (!Sentry.isEnabled) {
    throw StateError(
      'Sentry did not start with the SENTRY_DSN of this build, so the app '
      'reports nothing to Sentry: copy the DSN of your Sentry project into '
      '.env again.',
    );
  }
  return const SentryCrashReporter();
}

/// Why the app reports nothing to Sentry when Sentry does not take the
/// value of SENTRY_DSN, which it does not quote.
const _noDsnOfSentry =
    'SENTRY_DSN of this build is no DSN of Sentry, so the '
    'app reports nothing to Sentry: copy the DSN of your Sentry project into '
    '.env again, as the section "Sentry" of its README tells.';

/// Reports the errors of the app to Sentry.
///
/// It prints nothing. Of the errors that `installCrashReporting()` reports,
/// Flutter already presents those it catches, in every mode, and in debug
/// mode the engine prints the others.
final class SentryCrashReporter implements CrashReporter {
  /// Creates the reporter, which reports to the Sentry that
  /// [initSentryCrashReporter] started.
  const SentryCrashReporter();

  @override
  Future<void> recordError(
    Object error,
    StackTrace? stackTrace, {
    bool fatal = false,
    String? reason,
  }) async {
    await Sentry.captureException(
      ThrowableMechanism(
        Mechanism(type: 'CrashReporter.recordError', handled: !fatal),
        error,
      ),
      stackTrace: stackTrace,
      withScope: (scope) async {
        scope.level = fatal ? SentryLevel.fatal : SentryLevel.error;
        if (reason != null) {
          await scope.setContexts('reason', {'reason': reason});
        }
      },
    );
  }

  /// Reports what the integration of Sentry for the errors of Flutter
  /// reports, without presenting the error, which the crash reporting of the
  /// app does.
  @override
  Future<void> recordFlutterError(
    FlutterErrorDetails details, {
    bool fatal = false,
  }) async {
    final context = details.context?.toDescription();
    final information = details.informationCollector?.call() ?? const [];
    final library = details.library;
    await Sentry.captureException(
      ThrowableMechanism(
        Mechanism(type: 'CrashReporter.recordFlutterError', handled: !fatal),
        details.exception,
      ),
      stackTrace: details.stack,
      withScope: (scope) async {
        scope.level = fatal ? SentryLevel.fatal : SentryLevel.error;
        await scope.setContexts('flutter_error_details', {
          if (context != null) 'context': 'thrown $context',
          if (information.isNotEmpty) 'information': information.join('\n'),
          'library': ?library,
        });
      },
    );
  }

  @override
  Future<void> log(String message) =>
      Sentry.addBreadcrumb(Breadcrumb(message: message, category: 'log'));

  @override
  Future<void> setUserId(String? userId) async {
    await Sentry.configureScope(
      (scope) => scope.setUser(userId == null ? null : SentryUser(id: userId)),
    );
  }
}

/// The values of `.env`, each through a static getter that returns the
/// value, or `null` while it is empty or missing.
///
/// A command of the `flutter` tool that builds, runs or tests the app reads
/// `.env` when it starts, given `--dart-define-from-file=.env`, and compiles
/// each value into the app, where `String.fromEnvironment` reads it as a
/// constant. Without that argument every value is empty, so every getter
/// is `null`, and a release build of an app with keys stops, since
/// [supplied] is `false` then.
abstract final class AppEnv {
  /// Whether the command that built the app gave it the values of `.env`:
  /// `--dart-define-from-file=.env` declares each key that `.env` has a line
  /// of, also with an empty value, and this is `true` once it declared one
  /// of the keys below. A key of your own needs no change here.
  static const bool supplied = bool.hasEnvironment('SENTRY_DSN');

  /// The DSN of your Sentry project, which the crash reports go to.
  static String? get sentryDsn {
    const value = String.fromEnvironment('SENTRY_DSN');
    return value.isEmpty ? null : value;
  }
}
