# AGENTS.md

This guide tells coding agents what the code of this Flutter app does not show. Setup that needs a person or an account is in [README.md](README.md). When you change what a section describes, change the section too.

## App entry

The app is plain Flutter code that nothing regenerates. Change it by hand, unless a section below says what writes a file.

- `main()` in `lib/main.dart` initializes the binding, awaits `bootstrap()` and calls `runApp()`, in this order. Start-up code goes into `bootstrap()`.
- `bootstrap()` in `lib/bootstrap.dart` runs before the first frame, in four phases: what must come before anything else, then the platform services, then the services of the app, then what needs them. Put a new statement into its phase, and import neither `package:flutter/material.dart` nor `package:flutter/cupertino.dart` there.
- Put code that features share into `lib/core/<concern>/`, one directory for each concern. Put a feature, with its screens and their state, into `lib/features/<feature>/`.
- The root of the app asks the system for the icons of the status bar that suit the theme, around every screen, with `StatusBarIcons` of `lib/core/app/status_bar_icons.dart`: dark icons on a light theme, light ones on a dark theme. A screen without an app bar needs no `AnnotatedRegion` for them. Add one only to a screen whose top has another brightness than the theme, such as a picture behind the status bar.
- The app has the flavors `dev`, `staging` and `prod`. A `flutter` command without `--flavor` builds `dev`, in release mode too, so a build for a store takes `--flavor prod`. Code reads the flavor from `appFlavor` of `package:flutter/services.dart`. The app has one entry: add no `main_<flavor>.dart`.

- The section "Finish the setup" of the README lists the steps of the setup that no command can do, such as a step in the web console of a service that the app uses. Only the developer of the app does them: when a task depends on one of them, point the developer to that section, and do not try to do the step yourself.

After a change, run:

```bash
dart format lib test
flutter analyze
flutter test
```

Format only `lib/` and `test/`: `dart format .` also formats what Flutter writes into `build/`. The app as generated is formatted, `flutter analyze` finds no issue in it and `flutter test` passes.

- `App` in `lib/app.dart` is the root widget of the app and creates its one `MaterialApp`. Create no other in `lib/`: every screen is below it.
- The `theme`, `darkTheme`, `themeMode`, `locale` and localizations of the app go into the arguments of that `MaterialApp`.
- Tests mirror `lib/`: the test of `lib/<path>.dart` is `test/<path>_test.dart`.
- The app has only an Android and an iOS project, in `android/` and `ios/`.
- The entitlements of the iOS app, such as Push Notifications or Sign in with Apple, are in `ios/Runner/Runner.entitlements`. Every build configuration of the Runner target signs with this file, even while it is empty. The Signing & Capabilities tab of Xcode edits the same file.
- Each flavor is in `productFlavors` of `android/app/build.gradle.kts`, and on iOS in `ios/Runner.xcodeproj/xcshareddata/xcschemes/<flavor>.xcscheme` and in the build configurations `Debug-<flavor>`, `Profile-<flavor>` and `Release-<flavor>` of `ios/Runner.xcodeproj/project.pbxproj`. Change both places together. A new setting of the Runner target goes into each of its twelve build configurations.

## Analytics

- Record what users do through `AnalyticsService` of `lib/core/analytics/analytics_service.dart`, never through the SDK of a provider. `createAnalyticsService()` returns the one service of the app. Call it where the state of a screen is created, or, with a DI container in the app, take the service from the container instead.

## Authentication

- `appSession` in `lib/core/auth/app_session.dart` tells who uses the app, and knows it before the first frame. Its `value` is a `SignedOutSession`, an `AnonymousSession` or an `AccountSession`, and `appSession.value.uid` is the id of the user. Sign in, sign up, sign out and delete the account only through `appSession`. The app has one, so create no other `AppSessionController`.
- A call of `appSession` fails only with an `AuthFailure`. Catch it and show a text of the app for its `reason`. Show its `developerHint` in debug mode only. After `recentSignInRequired`, tell the user to sign out and sign in again.
- `authMode` in that file says who may use the app without an account. It gates nothing on its own. What keeps a user from a screen is a guard of the routes. One that reads `appSession.allowsApp` stands before the whole app, and one that reads `appSession.hasAccount` stands only before the routes that it lists, the screens that need an account. In an app without such a guard every screen is open, whatever the mode, and that includes a screen that needs an account. A screen does not redirect itself.
- When an anonymous user signs in to an account that exists already, `takeGuestData()` in `lib/core/auth/guest_data.dart` says what moves from that user to the account. As generated it moves nothing: write there what the app keeps under the id of a user. Call no method of `appSession` in it, since the sign-in that calls it would wait for that call.
- `appSignInMethods` in `lib/core/auth/sign_in_methods.dart` lists the ways to sign in with an identity provider that the modules of the app add, and is empty without them. A screen of sign-in shows a button for each `SignInMethod` whose `isAvailable` is true, with its `label(context)` and its `icon`.
- On a tap, the state of the screen awaits `credential()` of the way to sign in and gives the credential to `appSession.signInWith`. `credential()` returns `null` when the user closed the sheet of the identity provider, which is no failure: the screen goes back to how it was. Call `credential()` from the state of a screen, never within a call of `appSession`.
- `appSession.signInWith` gives an anonymous user the identity with the same id, or signs in to the account that has the identity already, and `takeGuestData()` moves what the anonymous user had. `appSession.deleteAccount()` asks a way to sign in with `revokesOnDeletion` for a credential again itself, and deletes nothing when the user closes its sheet.
- `AccountSession.issuers` lists the identity providers of an account, each the `issuer` of a `SignInMethod`.
- A new provider implements `AuthService` of `lib/core/auth/auth_service.dart`, and only the file of that implementation imports it. The code of the app imports `lib/core/auth/app_session.dart`, which exports `AuthFailure`, `AuthFailureReason`, `SignInCredential` and `IdTokenCredential`, and calls neither `initAuth()` nor `createAuthService()` nor `appSession.start()`.

## Notifications

- `appNotifications` in `lib/core/notifications/app_notifications.dart` shows the notifications of the app. `show()` shows one now, `schedule(notification, at: time)` at about that time, not to the minute, even if the app is closed by then. `cancel()` and `cancelAll()` remove them, and `scheduled()` lists those still to come, those of an owner too. A notification is an `AppNotification` with an `id`, a `title`, a `body` and `data`, and one with the id of a notification that is shown or scheduled takes its place. Give it an id from 0 up: a negative id is for a notification with an owner, which names it under `notificationOwnerKey` in its `data`, and whose taps go to `tapsOf(owner)` and `launchTapOf(owner)`.
- `appNotifications.permission` is `granted`, `denied` or `notAsked`. Ask with `appNotifications.request()` where the user turns on something that notifies, so that the question explains itself. Where the system has no question to show, as on Android before 13, the request opens its settings instead. After `denied` the system may not ask again (iOS asks only once, and Android stops after a second no), so open its settings with `appNotifications.openSettings()`. The app remembers that it asked under `notifications.asked`, so write nothing under that key.
- A tap on a notification reaches `appNotifications.taps` with the `data` of the notification, and the tap that launched the app is `appNotifications.launchTap`. Handle both once the first screen is shown, and navigate as the rest of the app does. A notification runs no code of the app when it shows.
- On Android a notification shows `android/app/src/main/res/drawable/ic_notification.xml` as its small icon. Change the drawing there and keep the name of the file.
- A new provider implements `NotificationsService` of `lib/core/notifications/notifications_service.dart`, and only the files of that implementation import it. The code of the app imports `lib/core/notifications/app_notifications.dart`, which exports `AppNotification` and `NotificationTap`, and calls neither `initNotifications()` nor `createNotificationsService()` nor `appNotifications.start()`.

- The onboarding asks for the permission on a page of its own, with the functions of `lib/core/notifications/notifications_step.dart`. A user who skips the onboarding does not see that page, so code that needs notifications calls `appNotifications.request()` too.

## Onboarding screen

- The onboarding shows the steps of `appOnboardingSteps` in `lib/core/onboarding/onboarding_steps.dart`, each on a page of its own, in the order of the list. A step is an `OnboardingStep`: an `icon`, a `title`, a `text`, the label of its `action` and the function `run` that the action calls. Its `later` is the label of a button that goes on without calling `run`, and the onboarding leaves the step out when its `showIf` returns `false` as the onboarding opens.
- To add a step, add an `OnboardingStep` to `appOnboardingSteps`. Its labels, `run` and `showIf` are top-level functions, so that the list stays `const`: a label takes a `BuildContext` and returns the text, `run` takes the `BuildContext` of the onboarding screen and returns a `Future`, and `showIf` returns a `bool` at once. The onboarding goes on once the future of `run` completes. A `run` that shows a screen of its own over the onboarding pushes it with `Navigator.of(context, rootNavigator: true)` and completes once that screen is closed. Show a label with `step.title(context)` in the `build` of the widget that shows it, and do not keep what it returned: the text follows the language of the app.
- Skipping the onboarding skips its steps. So the app does not rely on `run` alone for what a step does, such as asking for a permission: the code that needs it calls the same function too.

## Preferences

- `AppPreferences` in `lib/core/preferences/app_preferences.dart` remembers the settings of the app between its launches, such as the theme mode. It is not encrypted: never save a token, a password, an API key or an encryption key in it.
- To remember a setting, write a function that takes the `AppPreferences` and add it to `_restorers` in that file. In it, read the setting, put it into the state that the widgets listen to, and keep the preferences in that state for its writes. The function awaits nothing, and keeps the current value when nothing is saved.

- In the code of the app, do not call `createAppPreferences()` or `initPreferences()`. `bootstrap()` opens the preferences, and code gets them as the argument of its function in `_restorers`, or, with a DI container in the app, from the container. Widgets use the state and do not touch the preferences. A test may call both: `initPreferences()` opens the preferences again, as the next launch of the app does, and `createAppPreferences()` returns them.

## Purchases

- `appPurchases` in `lib/core/purchases/app_purchases.dart` tells whether the user has premium access, and knows it before the first frame. Its `value` is `NoAccess` or `PremiumAccess`, and `appPurchases.hasPremium` is the `ValueListenable<bool>` that widgets and guards of the routes read. Every plan gives the same premium access. The app has one controller, so create no other `AppPurchasesController`.
- `appPurchases.plans()` gives the plans to sell, each a `Plan` with its `price`, its `period` (`null` for a plan paid once) and its `introOffer`. `appPurchases.purchase(plan)` returns `false` when the user cancels, which is no failure, and `appPurchases.restore()` gives the user what the store account bought. A call fails only with a `PurchasesFailure`: show a text of the app for its `reason`, and its `developerHint` in debug mode only. After `pending`, the access arrives later without another call.
- A screen that sells shows the full price of each period most clearly, the length of a free trial and the price after it, that the plan renews until the user cancels, a way to restore purchases, links to the terms of use and the privacy policy, and a visible way to close it, as the App Store and Google Play ask.
- `PremiumAccess.manageUrl` is the page of the store where the user manages or cancels the plan. A screen only for users with premium access stands behind a guard of the routes that reads `appPurchases.hasPremium`. A screen does not redirect itself.

- A new provider implements `PurchasesService` of `lib/core/purchases/purchases_service.dart`, and only the files of that implementation import it. The code of the app imports `lib/core/purchases/app_purchases.dart`, which exports the types of the answers, and calls neither `initPurchases()` nor `createPurchasesService()` nor `appPurchases.start()`.

- The purchases belong to the user of `appSession`, by `appSession.value.uid`, and to the user of this device while nobody is signed in. A user who buys before signing up keeps the purchase in the new account, which takes it over from the user of this device. A user who signs in to an account that exists already leaves the purchases with the user of this device, and after a sign-out the user of this device is a new one, with nothing bought. A purchase then comes back only through a restore, which may also move purchases from another user, as the backend of the provider decides. The app does not restore on its own: call `appPurchases.restore()` where the user asks for it.

## Push messages

## Router

- Navigate with `context.nav.<feature>.<route>(...)`, never with the package of the router. It returns a `NavLink`, whose `go()`, `push<T>()` and `replace()` show the location. In `context.nav` both names are in lowerCamelCase; elsewhere `<feature>` is the id of the feature.
- A route is in three places, which agree on its name, `<feature>.<route>`, and on its path, which starts with `/<feature>`:
  1. its screen, a widget in `lib/features/<feature>/` whose `const` constructor takes each value of the route as a named parameter;
  2. `lib/core/router/navigation.dart`: its location class, which extends the sealed `AppLocation` with its `routeName`, its `path` and, below another route, its `parent`, and a method that returns its `NavLink` in the class of the routes of its feature. `AppNav` returns that class from a getter with the name of the feature, and both classes pass on the `BuildContext` that `NavLink` takes;
  3. the route itself, where the provider of the router declares its routes.
- A value of a route is a `String`, an `int`, a `double` or a `bool`, from a `:<name>` segment of its path or from the query.
- `appRouter` of `lib/core/router/app_router.dart` is the one router of the app: create no other.

- `routeGuards` in `lib/core/router/app_router.dart` lists the guards of the routes, each a `RouteGuard`, in the order the router asks them. A guard without `routes` is a gate over the whole app. The gates come first, and the first one whose `allows` is `false` decides: the router asks no guard after it. A guard with `routes` keeps the user only from the routes that it names there, each as `<feature>.<route>`, and comes after the gates.
- To keep the user from the rest of the app, add a gate to that list, never a redirect to the files of the router. Put it at the place among the gates where its screen comes on a first launch: a guard of the first launch goes before one that asks who the user is. Make its `redirectTo` a top-level route outside the main navigation. To keep the user from some routes only, add their names to the `routes` of the guard that stands for what they need, or add such a guard after the gates. Add the name of each route below such a route too: a route does not ask because the route above it does. The `routes` are outside the main navigation and outside every `flow`, and the screen that the app starts on is none of them.
- A feature changes the value of `allows` of its guard, and the router navigates when it does. While the `allows` of a gate is `false`, the router shows its `redirectTo` in place of the whole stack, whichever location was asked for. Once the gates allow, the router shows the location that was asked for in the meantime, such as a link, or else brings the user back to where they were. A gate with `resumes: false` does not bring the user back. When the `allows` of a guard with `resumes: false` turns `false`, the router forgets where the user was and what was asked for before, even while the `redirectTo` of another guard is shown. Once the gates allow, the user comes to a location that was asked for since then, or else to the screen that the app starts on. So after a sign-out the next user does not come to the screen of the last one.
- While the `allows` of a guard with `routes` is `false`, `go()`, `push()` or `replace()` of one of those routes opens its `redirectTo` over the page that the user is on, and the request waits. Back returns to that page, and a `push()` that waited completes with `null`. Once the value is `true`, the router closes the pages of the `flow` and does what was asked: `push()` shows the route over the page that the user was on and completes with the value of its page, `go()` shows it in place of the stack, and `replace()` in place of that page. When the value turns `false`, the router closes the pages of the `routes` with the pages over them. The user is then on the page below them, or on the screen that the app starts on when no page is below, as after `go()` to one of the `routes`.
- A screen neither closes itself nor navigates after it changed the value of `allows` of a guard: the router has done both by then. This goes for a screen of a `flow` that turned the value `true`, as after a sign-in, and for a screen of the `routes` that turned it `false`, as a screen with a sign-out button. A `pop()` after the change closes the page that is on top by then: the page that the user asked for, or the page below the one that the router closed, which may be the main navigation of the app.
- The `flow` of a guard is its `redirectTo` and the routes below it. These routes show only while a guard with that `flow` does not allow. At any other time the router shows the screen that the app starts on in their place, or the `redirectTo` of a gate whose `allows` is `false`. So no code navigates into the `flow` of a gate, and no screen of a `flow` navigates out of it once its guard allows: the router does. The first does not hold for a guard with `routes`. While it does not allow and every gate does, its `redirectTo` shows like any route, so a screen may open it with `push()`. `go()` to it from a screen takes the place of the stack, with no way back. A link to a route of its `flow` opens that route over the screen that the app starts on, so back leads into the app. Such a link is lost while a gate with another `flow` does not allow: once the gate allows, the user is on the screen that the app starts on. Inside a `flow`, navigate with `push()` or `replace()`. `go()` takes the place of the pages below the `flow`, and the request that waits is lost with them.

## Theme

- `createLightTheme(context)` and `createDarkTheme(context)` in `lib/core/theme/app_theme.dart` return the light and the dark theme of the app. Change the look there. Keep both functions and their `BuildContext` parameter, because the root of the app calls them each time it builds, for the `theme` and the `darkTheme` of the root `MaterialApp`. Leave those two arguments and its `themeMode` as they are.
- The theme mode is in `lib/core/theme/theme_mode.dart`. Change it only with `appThemeMode.choose(mode)`, which also saves it in the preferences, and write nothing under the key `theme.mode` yourself. A widget reads the mode with `AppThemeModeScope.of(context)` and rebuilds when it changes.
- Take the colours and the text styles of a screen from `Theme.of(context)`, not from constants, so that the screen follows the mode.

## Values in .env

- Read a value of `.env` only through a static getter of `AppEnv` in `lib/core/env/app_env.dart`. The getter is the key in lowerCamelCase: `AppEnv.myServiceKey` for the key `MY_SERVICE_KEY`. It returns a `String?` that is `null` while the value is empty or missing, so handle `null`. Never read `.env` or `.env.example` from code.

- `.env` stays out of git. A new key goes into both `.env.example` and `.env`, in UPPER_SNAKE_CASE with a comment line above it, and `AppEnv` gets a getter for it.

| Flavor | Android application id | iOS bundle id |
| --- | --- | --- |
| `dev` | `com.example.fixture_app.dev` | `com.example.fixture-app.dev` |
| `staging` | `com.example.fixture_app.staging` | `com.example.fixture-app.staging` |
| `prod` | `com.example.fixture_app` | `com.example.fixture-app` |

A `flutter` command without `--flavor` builds `dev`, because `default-flavor` in `pubspec.yaml` says so. That holds in release mode too: `flutter build appbundle` and `flutter build ipa` build a release of `dev`, under its id. For a store, name the flavor:

```bash
flutter run --flavor staging
flutter build appbundle --flavor prod
flutter build ipa --flavor prod
```

Code reads the flavor from `appFlavor` of `package:flutter/services.dart`. A service that knows your app by its id, such as a store or a push provider, knows each flavor as an app of its own, so a step of its setup is repeated for each flavor that needs it.

## Flavors in the native projects

Each flavor is in two places, so change both when you rename, add or remove one:

- Android: `productFlavors` in `android/app/build.gradle.kts`, with its id suffix and its name on the device.
- iOS: `ios/Runner.xcodeproj/xcshareddata/xcschemes/<flavor>.xcscheme`, and the build configurations `Debug-<flavor>`, `Profile-<flavor>` and `Release-<flavor>` in each configuration list of `ios/Runner.xcodeproj/project.pbxproj`. The name of a flavor has no hyphen, since Flutter splits the name of a configuration on it.

In Xcode, select the scheme of a flavor, not `Runner`. That scheme builds the id and the name of `prod` with whichever flavor the last `flutter` command left in `ios/Flutter/Generated.xcconfig`.

## Sign-in

The sign-in mode of the app says who may use it without an account. This app was generated in the mode `required`: `authMode` in `lib/core/auth/app_session.dart` is `AuthMode.required`.

- In `required`, nobody may. `appSession.allowsApp` is true only for a user who signed in to an account.
- In `guest`, everyone may. The app has no user until someone signs in, and `appSession.allowsApp` is always true.
- In `anonymous`, everyone may, as an anonymous user that the app signs in itself when it starts. Code then has the id of a user, `appSession.value.uid`, before anyone has an account, and signing up gives that same user the account. The app waits up to 3 seconds for that sign-in. When it fails or takes longer, the app starts without a user and tries again each time the user comes back to it. `appSession.allowsApp` is always true.

The mode keeps nobody from a screen on its own. A guard of the routes does. One that reads `appSession.allowsApp` stands before the whole app. One that reads `appSession.hasAccount` stands only before the routes that it lists, the screens that need an account. A module with the screens of sign-in declares such guards. If the app was generated without such a module, every screen is open in every mode, `required` too, until you write a guard of your own that reads `appSession.allowsApp`. A screen that a module made for users with an account is open then too. A warning named each such route when the app was generated, and a guard of your own for them reads `appSession.hasAccount`.

To change the mode, change the value of `authMode`. The provider of sign-in has to allow what the new mode needs, such as anonymous users for the mode `anonymous`. Where the provider has a section in this README, that section tells how.

When an anonymous user signs in to an account that exists already, the user of the app changes, and what the app keeps under the id of the anonymous user would be left behind. `takeGuestData()` in `lib/core/auth/guest_data.dart` says what moves to the account. As generated it moves nothing.

Besides an email address and a password, the app signs in with these identity providers, the ways to sign in of `appSignInMethods` in `lib/core/auth/sign_in_methods.dart`:

- Continue with the fixture, on Android and iOS. Deleting an account that signs in this way asks the identity provider for a credential again first, so that the provider of sign-in can revoke the tokens that it gave the app. If the user closes its sheet, nothing is deleted.

A screen of sign-in shows the button of a way to sign in only on the platforms that it works on. When an anonymous user signs in this way and no account has the identity yet, the user gets the identity and keeps the id. Otherwise the user signs in to that account, as with a password, and `takeGuestData()` moves what the anonymous user had. The sign-in may also fail, because the address of the identity has an account that signs in in another way: the provider of sign-in decides which.

## Values in .env

`.env` at the root of the app holds the values you fill in after generating the app, such as the public key of a service. Code reads each value as a static getter of `AppEnv` in `lib/core/env/app_env.dart`. The getter is `null` while the value is empty or missing, so the app builds and starts before you fill anything in.

`.gitignore` lists `.env`, so it stays out of git. `.env.example` is in git and has the same keys without values: after a clone, run `cp .env.example .env` and fill in `.env`. Every value ends up in the app, where anyone can read it, so never put a secret there, such as the secret key of a server, a password or a private key.

The keys of the app:

- `FAKE_ENV_USER_FIRST`, read as `AppEnv.fakeEnvUserFirst`, from the module `fake_env_user`: The first value of the fixture
- `FAKE_ENV_USER_SECOND`, read as `AppEnv.fakeEnvUserSecond`, from the module `fake_env_user`: The second value of the fixture
- `FAKE_ENV_USER_THIRD`, read as `AppEnv.fakeEnvUserThird`, from the module `fake_env_user`: The third value of the fixture

To add a key of your own, put it into `.env.example` and `.env` and give `AppEnv` a getter for it. The section of the module that provides the values tells how they get into the app.

## Languages

The app is in the languages of `appLocales` in `lib/core/l10n/app_locale.dart`. It shows its texts in the language that the device prefers among them, and in the first of the list when the device asks for none of them. `appLocale.choose()` puts the app into another of its languages, whatever the device prefers, and the app remembers that choice between its launches. `appLocale.choose(null)` follows the device again.

To add a language in which Flutter has the texts of its own widgets, such as German, add the texts of the app in German, and then:

1. Add `Locale('de')` to `appLocales`, one locale for each language, since the app tells its languages apart by their codes.
2. Add `de` to `CFBundleLocalizations` in `ios/Runner/Info.plist`, which tells iOS the languages of the app.

## Notifications

The app shows notifications through `appNotifications` in `lib/core/notifications/app_notifications.dart`. `show()` shows one now and `schedule()` at a time to come, `cancel()` and `cancelAll()` remove them, and `scheduled()` lists those still to come. A scheduled notification shows at about its time, not to the minute, even if the app is closed by then, and after the device restarts. A tap on a notification reaches `appNotifications.taps` with the `data` of the notification, and `appNotifications.launchTap` is the tap that launched the app.

The app needs the permission of the user to show notifications. `appNotifications.permission` is `granted`, `denied` once the user said no or turned them off, or `notAsked`, and `appNotifications.request()` asks. Where the system has no question to show, as on Android before 13, the request opens the settings of the system for the notifications of the app instead. The onboarding asks on a page of its own, with the functions of `lib/core/notifications/notifications_step.dart`. A user who skips the onboarding does not see that page. After `denied` the system may not ask again: iOS asks only once, and Android stops asking after a second no. `appNotifications.openSettings()` opens the settings of the system, where the user turns the notifications on.

On Android a notification shows `android/app/src/main/res/drawable/ic_notification.xml` as its small icon. Replace the bell there with the icon of the app, a shape on a transparent background, and keep the name of the file: `android/app/src/main/res/raw/notifications_keep.xml` keeps the icon in a release build. In the settings of the system, the channel of the notifications has the name of the app.

## Purchases

The app sells premium access through `appPurchases` in `lib/core/purchases/app_purchases.dart`. Every plan of the current offer gives the same access, whether it renews or the user pays once.

`appPurchases.value` is `NoAccess` or `PremiumAccess`, and `appPurchases.hasPremium` tells which. The app knows it before the first frame, from what the device keeps. `PremiumAccess` tells when the access ends (`expiresAt`, `null` for an access that never ends), whether the plan `renews`, whether the access is a free trial (`inTrial`), and `manageUrl`, the page of the store where the user manages or cancels the plan. `appPurchases.plans()` gives the plans to sell, `appPurchases.purchase(plan)` buys one and returns `false` when the user cancels, and `appPurchases.restore()` gives the user what the store account bought. A call fails only with a `PurchasesFailure`: show a text of the app for its `reason`, and its `developerHint` in debug mode only.

A screen that sells a plan shows what the App Store and Google Play ask of it:
- the name of the plan, how long a period lasts and what the user gets;
- the full price that the store charges for each period, shown more clearly than any other price on the screen, and for a yearly plan never mainly as a price per month;
- for a free trial or a lower price at first, how long it lasts and the price after it;
- that the plan renews until the user cancels, and how to cancel it in the store;
- a way to restore purchases;
- links to the terms of use and the privacy policy of the app;
- a visible way to close the screen without buying.

A screen that only users with premium access may see stands behind a guard of the routes that reads `appPurchases.hasPremium`. Without such a guard, every user gets to it.

The purchases belong to the user of `appSession`, by the id of the user: the user of an account, or an anonymous user. While nobody is signed in, they belong to the user of this device. A user who buys before signing up keeps the purchase in the new account, which takes it over from the user of this device, and an anonymous user keeps it when the account takes the id of that user. A user who signs in to an account that exists already leaves the purchases with the user of this device. After a sign-out, the user of this device is a new one, with nothing bought. In both cases a purchase comes back only through a restore, which may also move purchases from another user, as the backend of the provider decides. Without a restore, the next user of the device never gets the purchases of a user who signed out. This app has no settings screen, so the screen that sells has to offer the restore itself.

Until the provider of purchases has what it needs, such as its keys, the app runs without purchases: `appPurchases.value` stays `NoAccess`, every call fails with the reason `notConfigured`, whose `developerHint` names what is missing, and in debug mode the app prints that hint once.

## Push messages

The app receives push messages through `appPush` in `lib/core/push/app_push.dart`.

`appPush.address` is the address of this device. The backend of the app sends its messages there. It is `null` until the platform gives one, and the app works without it. Send each new address to the backend: it may come late, and it may change. In debug mode the app prints it, so you can send this device a message by hand.

On iOS the address needs a token of the Apple Push Notification service (APNs). iOS gives one only to a build signed with the entitlement `aps-environment`, which `ios/Runner/Runner.entitlements` has. The iOS simulator on a Mac gets a token. One on a macOS virtual machine, such as a hosted CI runner, never does. On an iPhone, signing with the entitlement needs a team of the paid Apple Developer Program. With a free personal team, Xcode cannot sign the app: to run it on an iPhone, remove the key `aps-environment` from `ios/Runner/Runner.entitlements`, and the app runs there without an address. The simulator needs no change. The value `development` suits the builds that you run from Xcode. When Xcode exports the app for distribution, it takes the value of the provisioning profile (production for a distribution profile).

A message that arrives while the app is in the foreground reaches `appPush.messages`. One with a title or a body also shows as a notification, as it does in the background. Where the system does not show it, the app shows it with `appNotifications`. Either way the user has to allow the notifications of the app, as the section Notifications tells. In the background the system shows the message, on Android in the channel of the notifications of the app.

`appPush.taps` tells of each tap on a message while the app runs, and `appPush.launchMessage` is the message whose tap launched the app. Read both once the first screen is shown, and navigate as the rest of the app does. A tap on a message does not reach `appNotifications.taps`, so the code of the app sees each tap once.

A message with data and no title or body reaches the app only while it is in the foreground. In the background, or when the app is closed, it runs no code of the app. Images in a message do not show on iOS, which needs an extension of the app for them.

/// the way to sign in, up and out.

/// Its `value` is the [AppSession], and it tells its listeners when that

/// Keeps the session of the app up to date with the service of the provider
/// of sign-in, and signs in, up and out through that service. The app has
/// one, [appSession].
///
/// Every call here fails only with an [AuthFailure], whose reason the app
/// shows in a text of its own. An error of another kind becomes a failure
/// with the reason [AuthFailureReason.unknown] and the error as its
/// [AuthFailure.developerHint].
///
/// The calls run one after another, in the order they were made, and none
/// runs next to an anonymous sign-in that is on its way. So the user of the
/// app is the result of the call that was made last. In the mode
/// [AuthMode.anonymous], a call that leaves nobody signed in is followed by
/// an anonymous sign-in.
final class AppSessionController extends ChangeNotifier
    implements ValueListenable<AppSession> {
  /// Creates a controller for an app in [mode]. The app creates
  /// [appSession] and no other. A test creates one to see another mode, or
  /// a shorter [anonymousWait], and disposes of it.
  AppSessionController({
    required this.mode,
    required this.takeGuestData,
    this.anonymousWait = const Duration(seconds: 3),
  });

  /// Who may use the app without an account.
  final AuthMode mode;

  /// Takes what an anonymous user has before that user signs in to an
  /// account: `takeGuestData` of `guest_data.dart`.
  final Future<GiveGuestData?> Function(String guestUid) takeGuestData;

  /// How long the app waits for its anonymous user when it starts, and
  /// after a sign-out or the deletion of an account, in the mode
  /// [AuthMode.anonymous].
  final Duration anonymousWait;

  AuthService? _service;
  StreamSubscription<AuthUser?>? _userChanges;
  AppSession _session = const SignedOutSession();
  bool _disposed = false;

  /// Whether the app has started for the first time.
  bool _started = false;

  /// Completes at the first start. Only the first call made before it waits
  /// for it, and each later call waits for the call before it. That call
  /// creates it, so the start completes it in the zone of the call: created
  /// with the controller, it would complete in a microtask of the zone that
  /// read [appSession] first, which may run none any more, as the fake time
  /// of a widget test that is over before a later test starts the app in
  /// real time.
  Completer<void>? _untilStarted;

  /// The call that was made last, while a call is on its way: the next one
  /// waits for it. It is `null` when none is, and a call then awaits
  /// nothing. A future that completed in another zone would hold the call
  /// back in a widget test, where the app starts in real time and the test
  /// goes on in fake time.
  Future<void>? _lastCall;

  /// The anonymous sign-ins that are on their way, each by its service, so
  /// that the app starts no second one next to it.
  final Map<AuthService, Future<void>> _anonymousSignIns = Map.identity();

  /// Tells when the user comes back to the app, in the mode
  /// [AuthMode.anonymous].
  _ResumeObserver? _observer;

  /// Who uses the app.
  @override
  AppSession get value => _session;

  /// Whether the user may see the app: always in the modes [AuthMode.guest]
  /// and [AuthMode.anonymous], and with an account in the mode
  /// [AuthMode.required].
  ///
  /// It is computed from the session each time it is read, and its
  /// listeners are those of the session. So when the session changes, a
  /// listener finds this value and [hasAccount] both up to date, whichever
  /// of the two it listens to. A listener is also called for a change of
  /// the session that leaves this value as it was.
  late final ValueListenable<bool> allowsApp = _SessionFlag(
    this,
    (session) => mode != AuthMode.required || session is AccountSession,
  );

  /// Whether the user of an account is signed in, which an anonymous user
  /// is not. It follows the session as [allowsApp] does.
  late final ValueListenable<bool> hasAccount = _SessionFlag(
    this,
    (session) => session is AccountSession,
  );

  /// Starts the session with [service]: takes the user who is signed in on
  /// this device, and follows the changes that the service tells of.
  ///
  /// `initAuth()` calls it in `bootstrap()`, so the session is known before
  /// the first frame. In the mode [AuthMode.anonymous], an app without a
  /// user signs in anonymously here and waits for that for at most
  /// [anonymousWait]. When the sign-in fails or takes longer, the app
  /// starts without a user. A sign-in that takes longer still becomes the
  /// session when it comes, and the app tries again each time the user
  /// comes back to it.
  ///
  /// A call made before the first start waits for it: [signIn], [signUp],
  /// [signInWith], [sendPasswordReset], [signOut] and [deleteAccount]. Such
  /// calls run in
  /// their order once the start has the user, and the future of this start
  /// completes after them, but waits for no call that is made while it
  /// runs. The mocks of the tests of an app use this: a call of [signUp]
  /// made before `bootstrap()`, which nothing awaits, gives the app an
  /// account before its first frame. A test makes such a call outside the
  /// body of a test, as in a `setUpAll`: made in the body of a widget
  /// test, it waits in the fake time of that body, and a start that runs in
  /// real time never completes.
  ///
  /// It may be called again, with the service that the session has from
  /// then on: `initAuth()` does so in a test of the next launch of the app,
  /// and a test gives it a service of its own. Such a start takes its turn
  /// after the calls that are on their way.
  Future<void> start(AuthService service) async {
    // The calls that were made before this start. The first start lets
    // them run once it has the user, and a later one waits for them.
    final earlier = _lastCall;
    final first = !_started;
    if (!first) await earlier;
    unawaited(_userChanges?.cancel());
    _service = service;
    _userChanges = service.userChanges.listen(
      (_) => _sync(),
      onError: (Object error, StackTrace stackTrace) => _report(
        error,
        stackTrace,
        'while following the user of the provider of sign-in',
      ),
    );
    _sync();
    if (mode == AuthMode.anonymous) {
      if (_observer == null) {
        final observer = _observer = _ResumeObserver(_retry);
        WidgetsBinding.instance.addObserver(observer);
      }
      await _signInAnonymously();
    }
    if (!_started) {
      _started = true;
      _untilStarted?.complete();
    }
    if (first) await earlier;
  }

  /// Signs in to the account of [email] with [password].
  ///
  /// An anonymous user becomes the user of that account, and what the
  /// anonymous user had moves to the account as `takeGuestData` says.

      _call(

      );

  /// Creates an account for [email] with [password] and signs in to it.
  ///

            ? service.linkPassword(email: email, password: password)
            : service.signUp(email: email, password: password),
      );

  /// Signs in with [credential], which a way to sign in of
  /// `appSignInMethods` got from an identity provider.
  ///
  /// An anonymous user gets the identity of the credential and keeps the id,
  /// so everything that the user had stays. When that identity belongs to
  /// another user already, or its email address has an account that signs
  /// in in another way, the anonymous user signs in to that account
  /// instead, or the call fails with
  /// [AuthFailureReason.accountExistsWithOtherMethod], as the backend of the
  /// provider decides. What the anonymous user had moves to the account as
  /// `takeGuestData` says, as with [signIn].
  Future<void> signInWith(SignInCredential credential) => _call((
    service,
  ) async {
    if (_session is AnonymousSession) {
      try {
        await service.linkWith(credential);
        return;
      } on AuthFailure catch (failure) {
        if (failure.reason != AuthFailureReason.credentialInUse &&
            failure.reason != AuthFailureReason.accountExistsWithOtherMethod) {
          rethrow;
        }
      }
    }
    await _toAccount(() => service.signInWith(credential));
  });

  /// Sends the message with which the owner of the account of [email] sets
  /// a new password. It completes whether [email] has an account or not.
  Future<void> sendPasswordReset(String email) =>
      _call((service) => service.sendPasswordReset(email));

  /// Signs the user out. In the mode [AuthMode.anonymous], the app then
  /// signs in anonymously again, as when it starts.
  Future<void> signOut() =>
      _call((service) => service.signOut(), waitsForAnonymousUser: true);

  /// Deletes the user who is signed in. The app is then without a user, as
  /// after [signOut], and in the mode [AuthMode.anonymous] it signs in
  /// anonymously again.
  ///
  /// For an account that signs in with a way to sign in that
  /// `revokesOnDeletion` and is available on this platform, it first asks
  /// that way for a credential again, such as with the sheet of its
  /// identity provider, so that the provider of sign-in can revoke the
  /// tokens of the app. When the user closes the sheet, the call completes
  /// and deletes nothing, which is no failure.
  ///
  /// It may fail with [AuthFailureReason.recentSignInRequired]: the user
  /// then signs out, signs in again and repeats it.
  Future<void> deleteAccount() => _call((service) async {
    final revoking = _revokingMethod();
    if (revoking == null) {
      await service.deleteAccount();
      return;
    }
    final fresh = await revoking.credential();
    if (fresh != null) await service.deleteAccount(fresh: fresh);
  }, waitsForAnonymousUser: true);

  /// Stops following the service and the lifecycle of the app. A call that
  /// is on its way still ends as it would have, but tells no listener, and
  /// no anonymous sign-in follows it.
  @override
  void dispose() {
    _disposed = true;
    unawaited(_userChanges?.cancel());
    if (_observer case final observer?) {
      WidgetsBinding.instance.removeObserver(observer);
    }
    super.dispose();
  }

  /// The way to sign in of the account of the session that asks for a
  /// credential again before the account is deleted and is available on
  /// this platform, or `null` if it has none: the first of
  /// `appSignInMethods` that does.
  SignInMethod? _revokingMethod() => switch (_session) {
    AccountSession(:final issuers) =>
      appSignInMethods
          .where(
            (method) =>
                method.revokesOnDeletion &&
                method.isAvailable &&
                issuers.contains(method.issuer),
          )
          .firstOrNull,
    _ => null,
  };

  /// The user came back to the app. In the mode [AuthMode.anonymous], an
  /// app without a user then signs in anonymously again: as what follows
  /// every call, so this takes a turn among the calls with nothing else to
  /// do, and starts no anonymous sign-in next to a sign-in.
  void _retry() => unawaited(_call((service) async {}));

  /// Runs [call] with the service once the calls made before it are over,
  /// and not before the app has started for the first time.
  ///
  /// In the mode [AuthMode.anonymous], a call that leaves nobody signed in
  /// is followed by an anonymous sign-in. A call that
  /// [waitsForAnonymousUser], as a sign-out, completes once that sign-in is
  /// over or took too long, as the start does.
  Future<void> _call(
    Future<void> Function(AuthService service) call, {
    bool waitsForAnonymousUser = false,
  }) async {
    final earlier =
        _lastCall ??
        (_started ? null : (_untilStarted ??= Completer<void>()).future);
    final done = Completer<void>();
    final own = _lastCall = done.future;
    if (earlier != null) await earlier;
    try {
      await _guarded(call);
      final signIn = _signInAnonymously();
      if (waitsForAnonymousUser) await signIn;
    } finally {
      if (identical(_lastCall, own)) _lastCall = null;
      done.complete();
    }
  }

  /// Runs [call] with the service, once an anonymous sign-in that is on its
  /// way is over: of a call and a sign-in that run at the same time, the
  /// one that ended last would decide who the user is.
  ///
  /// Whatever [call] throws that is no [AuthFailure] becomes one, and the
  /// session has the user of the service when it is over, also when it
  /// failed. A call that failed does not wait for the anonymous sign-in
  /// that follows it, so that its failure is not late.
  Future<void> _guarded(Future<void> Function(AuthService service) call) async {
    final service = _service!;
    try {
      await _anonymousSignIns[service];
      await call(service);
    } on Object catch (error, stackTrace) {
      _sync();
      unawaited(_signInAnonymously());
      if (error is AuthFailure) rethrow;
      Error.throwWithStackTrace(
        AuthFailure(AuthFailureReason.unknown, developerHint: '$error'),
        stackTrace,
      );
    }
    _sync();
  }

  /// Signs in to an account with [signIn], in whichever way, and moves what
  /// an anonymous user had to that account, when it has another id.
  ///
  /// It takes the data before the sign-in, while the anonymous user is
  /// still signed in, and gives it once the user of another id has an
  /// account. If taking fails, the call fails and nothing has changed. If
  /// giving fails, the user is signed in already, so the call completes and
  /// the error is reported as an error of the app.
  Future<void> _toAccount(Future<void> Function() signIn) async {
    final guest = _session;
    final give = guest is AnonymousSession
        ? await takeGuestData(guest.uid)
        : null;
    await signIn();
    _sync();
    final account = _session;
    if (give == null ||
        account is! AccountSession ||
        account.uid == guest.uid) {
      return;
    }
    try {
      await give(account.uid);
    } on Object catch (error, stackTrace) {
      _report(
        error,
        stackTrace,
        'while giving the data of a guest to the account',
      );
    }
  }

  /// Reports [error], which no call can fail with, as an error of the app.
  void _report(Object error, StackTrace stackTrace, String during) =>
      FlutterError.reportError(
        FlutterErrorDetails(
          exception: error,
          stack: stackTrace,
          library: 'app session',
          context: ErrorDescription(during),
        ),
      );

  /// In the mode [AuthMode.anonymous], signs in anonymously when nobody is
  /// signed in, and waits for that for at most [anonymousWait].
  ///
  /// It never fails. A sign-in that takes longer goes on and becomes the
  /// session when it comes. One that fails leaves the app without a user
  /// until the next try, and in debug mode its error is printed.
  Future<void> _signInAnonymously() async {
    final service = _service!;
    if (_disposed ||
        mode != AuthMode.anonymous ||
        service.currentUser != null) {
      return;
    }
    final signIn = _anonymousSignIns[service] ??= _tryAnonymously(service)
        .whenComplete(() {
          _anonymousSignIns.remove(service);
          _sync();
        });
    await signIn.timeout(anonymousWait, onTimeout: () {});
  }

  Future<void> _tryAnonymously(AuthService service) async {
    try {
      await service.signInAnonymously();
    } on Object catch (error) {
      if (kDebugMode) {
        debugPrint(
          'The anonymous sign-in failed, so the app has no user: $error',
        );
      }
    }
  }

  /// Takes the user of the service as the session, and tells the listeners
  /// when that changes it, unless the session was disposed of.
  void _sync() {
    if (_disposed) return;
    final session = switch (_service!.currentUser) {
      null => const SignedOutSession(),
      AuthUser(isAnonymous: true, :final uid) => AnonymousSession(uid),
      AuthUser(:final uid, :final email, :final issuers) => AccountSession(
        uid,
        email: email,
        issuers: Set.unmodifiable(issuers),
      ),
    };
    if (session == _session) return;
    _session = session;
    notifyListeners();
  }
}

/// Why a call of sign-in failed.
enum AuthFailureReason {
  /// The email address and the password match no account. A wrong password
  /// and an address without an account are this one reason, so that nobody
  /// learns from the app which addresses have an account.
  ///
  /// It is also the reason of a [SignInCredential] that the provider
  /// refuses, such as one that expired or that was issued for another app,
  /// and of one of another user than the one whose account is deleted.
  invalidCredentials,

  /// The email address has an account already.
  emailInUse,

  /// The identity of a [SignInCredential] belongs to another user already,
  /// so [AuthService.linkWith] gives it to nobody else. The session then
  /// signs in to that user.
  credentialInUse,

  /// The email address of the identity of a [SignInCredential] has an
  /// account that signs in in another way, such as with a password. The
  /// user signs in that way.
  accountExistsWithOtherMethod,

  /// The provider takes no password as weak as this one.
  weakPassword,

  /// The text is no email address.
  invalidEmail,

  /// The account is disabled.
  userDisabled,

  /// Too many attempts: the provider takes no more for a while.
  tooManyAttempts,

  /// The device did not reach the provider.
  network,

  /// The call needs a user who signed in a short while ago, as the deletion
  /// of an account does: the user signs in again and repeats it.
  ///
  /// It is also the reason of a call for a user whose session has ended on
  /// the server. The service signs that user out on the device before it
  /// fails.
  recentSignInRequired,

  /// Sign-in is not set up at the provider, such as a way to sign in that
  /// is not enabled there. This is a mistake in the setup of the app, which
  /// [AuthFailure.developerHint] explains.
  notConfigured,

  /// Anything else. [AuthFailure.developerHint] has the error.
  unknown,
}

/// The accounts of the users of the app and the user of this device, as the
/// provider of sign-in keeps them.
///
/// The provider implements it. The code of the app does not call it: it
/// signs in through `appSession` of `app_session.dart`, which calls this
/// service and does what is the same with every provider.
///
/// Every implementation keeps to this, in every mode of the app, whatever
/// the provider generates for the mode:
/// - The service has [currentUser] from the moment it is created: the user
///   who was signed in on this device when the app last ran, without a
///   request to the server. The function that creates the service may be
///   called again, and the service that it returns then has the user who is
///   signed in now.
/// - When the future of a call completes, [currentUser] is the result of
///   the call. [userChanges] tells of every change of [currentUser], also
///   of one that no call here made, and when it tells of a user,
///   [currentUser] is that user.
/// - A call fails only with an [AuthFailure], and every call ends: when the
///   server does not answer, its future completes with
///   [AuthFailureReason.network].
/// - A call that fails leaves the user who is signed in as that user was:
///   an anonymous user stays signed in when [linkPassword] or [linkWith]
///   fails, and so does whoever is signed in when [signIn], [signUp] or
///   [signInWith] fails. The one exception is a call for a user whose
///   session has ended on the server.
/// - [linkPassword], [linkWith] and [deleteAccount] are calls for the user
///   who is signed in. Made when nobody is signed in, or when the session of
///   that user has ended on the server, such a call fails with
///   [AuthFailureReason.recentSignInRequired], and in the second case it
///   signs the user out on the device first.
/// - A [SignInCredential] whose identity provider the provider does not
///   take fails with [AuthFailureReason.notConfigured], with the issuer in
///   the [AuthFailure.developerHint].
abstract interface class AuthService {
  /// The user who is signed in on this device, or `null`.
  AuthUser? get currentUser;

  /// Tells of each change of [currentUser], once [currentUser] has changed:
  /// a broadcast stream. When it tells of a user, [currentUser] is that
  /// user. It may also tell of a user who has not changed.
  ///
  /// An error that it sends changes nothing: the session reports it as an
  /// error of the app and goes on listening.
  Stream<AuthUser?> get userChanges;

  /// Signs in to the account of [email] with [password].
  ///
  /// A wrong password and an address without an account both fail with
  /// [AuthFailureReason.invalidCredentials].
  ///
  /// It is also called while a user is signed in, an anonymous one or the
  /// user of another account: the user of this account then replaces that
  /// user on the device. When it fails, that user stays signed in.
  Future<void> signIn({required String email, required String password});

  /// Creates an account for [email] with [password] and signs in to it.
  ///
  /// For an address that has an account already, it fails with
  /// [AuthFailureReason.emailInUse] and changes nothing: that account keeps
  /// its password, and whoever is signed in stays signed in.
  ///
  /// It is also called while the user of another account is signed in, and
  /// the user of the new account then replaces that user on the device.
  /// For an anonymous user, the session calls [linkPassword] instead.
  Future<void> signUp({required String email, required String password});

  /// Gives the anonymous user who is signed in an account for [email] with
  /// [password]. The user keeps the [AuthUser.uid] and is no longer
  /// anonymous.
  ///
  /// For an address that has an account already, it fails with
  /// [AuthFailureReason.emailInUse] and changes nothing: the anonymous user
  /// stays signed in, with the same id.
  Future<void> linkPassword({required String email, required String password});

  /// Signs in with [credential], which a way to sign in got from an
  /// identity provider: to the user of its identity, whom it creates when
  /// the identity is new.
  ///
  /// It is also called while a user is signed in, an anonymous one or the
  /// user of another account: the user of the identity then replaces that
  /// user on the device. When it fails, that user stays signed in.
  ///
  /// It takes a credential that [linkWith] refused just before, with
  /// [AuthFailureReason.credentialInUse] or
  /// [AuthFailureReason.accountExistsWithOtherMethod]: the session passes
  /// the identical object. An identity provider may take a credential only
  /// once, so the service signs in with what its backend answered the
  /// refused link for that object, or with the credential itself when the
  /// backend gave nothing. For an identity whose email address has an
  /// account that signs in in another way, it fails with
  /// [AuthFailureReason.accountExistsWithOtherMethod] or signs in to that
  /// account, as the backend of the provider decides.
  Future<void> signInWith(SignInCredential credential);

  /// Gives the user who is signed in the identity of [credential]: the user
  /// keeps the [AuthUser.uid], is no longer anonymous, and signs in with

  ///
  /// When the identity belongs to another user, it fails with
  /// [AuthFailureReason.credentialInUse], and when its email address has an
  /// account of another user, with

  /// nothing: the user stays signed in, with the same id.
  ///
  /// When it fails with either reason, it keeps what its backend answered
  /// for this credential object, such as a credential to sign in with,
  /// without holding the token longer than needed. The session passes the
  /// identical object to [signInWith], which uses that answer, or the
  /// credential itself when the backend gave nothing.
  Future<void> linkWith(SignInCredential credential);

  /// Creates an anonymous user, with an id of its own, and signs in as that
  /// user.
  Future<void> signInAnonymously();

  /// Sends the message with which the owner of the account of [email] sets
  /// a new password.
  ///
  /// It completes whether [email] has an account or not, so that nobody
  /// learns from the app which addresses have one.
  Future<void> sendPasswordReset(String email);

  /// Signs the user out on this device. It completes when nobody is signed
  /// in too.
  Future<void> signOut();

  /// Deletes the user who is signed in, an anonymous one too, and signs
  /// out.
  ///
  /// It succeeds for a user who has just signed in, in whichever way, and
  /// for an anonymous user who was just created. For a user who signed in
  /// longer ago, such as one whom the service found on the device when it
  /// was created, it may fail with
  /// [AuthFailureReason.recentSignInRequired]. It then succeeds once the
  /// user has signed in again, in whichever way the account allows.
  ///

  /// that fails, such as one that the backend is not set up for, with
  /// [AuthFailureReason.notConfigured]. Either way nothing is deleted.
  Future<void> deleteAccount({SignInCredential? fresh});
}

    FutureOr<void> Function(T service)? dispose,

    if (dispose != null) _disposers.add(() => dispose(instance));

    String? name,
    FutureOr<void> Function(T service)? dispose,
  }) {

    _getters[(T, name)] = () => instance ??= create();

      // A lazy singleton that nothing resolved is not created only to be
      // disposed of.
      _disposers.add(() {
        if (instance case final created?) return dispose(created);
      });
    }
  }

      _getters[(T, name)] = create;

  Future<void> reset() async {
    for (final dispose in _disposers.reversed) {
      await dispose();
    }

    try {
      await _refresh();
    } on Object catch (error, stackTrace) {
      _firstStarted(error, stackTrace);
      rethrow;
    }
    _firstStarted();
  }

  /// has it, and completes with the permission once the user answered.
  ///
  /// Ask where the user turns on something that notifies, so that the
  /// question explains itself. Where the platform has no question, the
  /// service opens the settings of the system instead. After
  /// [NotificationPermission.denied] the system may ask no more: iOS asks
  /// once, and Android after a second no. So open its settings then:
  /// [openSettings].

  /// of the app takes it that the app has not asked.

  Future<void> openSettings() async => (await _ready()).openSettings();

  /// owner under [notificationOwnerKey] in its data, which takes a negative
  /// id. Its future fails with an [ArgumentError] for another id.
  Future<void> show(AppNotification notification) async {
    _check(notification);
    await (await _ready()).show(notification);
  }

  /// Shows [notification] at about [at], not to the minute, also when the
  /// app is closed then. Its future fails with an [ArgumentError] when [at]
  /// is not in the future, and for an id that [show] does not take.
  Future<void> schedule(
    AppNotification notification, {
    required DateTime at,
  }) async {
    _check(notification);
    if (!at.isAfter(DateTime.now())) {
      throw ArgumentError.value(at, 'at', 'The time is not in the future');
    }
    await (await _ready()).schedule(notification, at);
  }

  Future<void> cancel(int id) async => (await _ready()).cancel(id);

  /// Removes every notification of the app, shown or scheduled, those of an
  /// owner too.
  Future<void> cancelAll() async => (await _ready()).cancelAll();

  /// The notifications that are scheduled and not shown yet, those of an
  /// owner too.
  Future<List<AppNotification>> scheduled() async =>

  Future<NotificationsService> _ready() async {
    if (!_started) {
      final untilStarted = Completer<void>();
      _untilStarted.add(untilStarted);
      await untilStarted.future;
    }
    return _service!;
  }

  /// Takes it that the app has started for the first time, unless it had,
  /// and lets the calls that waited for that go on, or fail with [error] of
  /// the start. Nothing but these calls reports that error, which the start
  /// throws itself.
  void _firstStarted([Object? error, StackTrace? stackTrace]) {
    if (_started) return;
    _started = true;
    for (final untilStarted in _untilStarted) {
      if (error == null) {
        untilStarted.complete();
      } else {
        untilStarted.completeError(error, stackTrace);
      }
    }
    _untilStarted.clear();
  }

  Future<NotificationPermission> _ask() async {
    final service = await _ready();
    if (await service.areEnabled()) {
      _enabled = true;
      _update();
      return _permission.value;
    }
    await service.request();
    _asked = true;
    _enabled = await service.areEnabled();
    _update();
    await _preferences?.setBool(_askedKey, true);
    return _permission.value;
  }

  /// Asks the service whether the app may show notifications.
  Future<void> _refresh() async {
    _enabled = await _service!.areEnabled();
    _update();
  }

  /// Takes that the app asked from [preferences], and keeps it as it is when
  /// they have nothing saved. It keeps [preferences] for the next request.
  void _restore(AppPreferences preferences) {
    _preferences = preferences;
    _asked = preferences.getBool(_askedKey) ?? _asked;
    _update();
  }

  void _update() => _permission.value = _enabled
      ? NotificationPermission.granted
      : _asked
      ? NotificationPermission.denied
      : NotificationPermission.notAsked;

  static String? _ownerOf(NotificationTap tap) =>
      tap.data[notificationOwnerKey];

  /// Whether [tap] is on a notification of the app: one without an owner,
  /// whose id is not negative.
  static bool _isOfApp(NotificationTap tap) =>
      tap.id >= 0 && _ownerOf(tap) == null;

  /// Throws an [ArgumentError] for an id of [notification] that the app
  /// does not take; see [show].
  static void _check(AppNotification notification) {
    final AppNotification(:id, :data) = notification;
    if (id < _smallestId || id > _largestId) {
      throw ArgumentError.value(id, 'id', 'The id is no 32-bit integer');

        id,
        'id',
        'A negative id is for a notification with an owner, which names it '
            'under notificationOwnerKey in its data',
      );
    }
    if (id >= 0 && owned) {
      throw ArgumentError.value(
        id,
        'id',
        'A notification with an owner has a negative id',
      );
    }
  }

  /// [NoAccess] until the service has the new user, and the controller takes
  /// no change of the access that the service tells of meanwhile.
  ///
  /// `initPurchases()` calls it in `bootstrap()`, so [value] is known before
  /// the first frame. It waits for the access at most [startWait]: an access
  /// that comes later still becomes [value], and the app starts without
  /// waiting for it.
  ///
  /// A call made before the first start waits for it: [plans], [purchase]
  /// and [restore]. Such calls run in their order once the start has the
  /// access, and the future of this start completes after them, and after
  /// the calls that their completions make right away: it completes once no
  /// call is on its way in the microtask after the last one ended. The mocks
  /// of the tests of an app use this: `plans().then(...)` that buys a plan,
  /// made before `bootstrap()`, gives the app premium access before its first
  /// frame. A test makes such a call outside the body of a test, as in a
  /// `setUpAll`: made in the body of a widget test, it waits in the fake time
  /// of that body, and a start that runs in real time completes after
  /// [startWait] without it.
  ///
  /// It may be called again, with the service that the controller has from
  /// then on: `initPurchases()` does so in a test of the next launch of the
  /// app, and a test gives it a service of its own. Such a start takes its
  /// turn after the calls that are on their way, and [value] is then that of
  /// the new service.
  Future<void> start(
    PurchasesService service, {
    String? Function()? userId,
    Listenable? userChanges,
  }) =>
      _start(service, userId, userChanges).timeout(startWait, onTimeout: () {});

  /// The plans of the current offer of the app, at least one, in the order
  /// of the provider. Show them only to a user without premium access.
  Future<List<Plan>> plans() => _call((service, _) => service.plans());

  /// Buys [plan] through the sheet of the store, and completes with `true`
  /// once the user has bought it, or with `false` when the user cancelled,
  /// which is no failure. The access that the purchase gave becomes [value],
  /// unless the user of the app changed meanwhile.
  ///
  /// A payment that waits for an approval fails with
  /// [PurchasesFailureReason.pending]: the access comes once the store took
  /// the payment. A purchase whose answer gives no premium access, as with a
  /// plan that the backend of the provider does not tie to the access, fails
  /// with [PurchasesFailureReason.notConfigured]: the user paid, and a
  /// restore gives the access once the provider is set up.
  Future<bool> purchase(Plan plan) => _call((service, identity) async {
    final access = await service.purchase(plan);
    if (access == null) return false;
    if (access is! PremiumAccess) {
      throw const PurchasesFailure(
        PurchasesFailureReason.notConfigured,
        developerHint:
            'The plan was bought, but it gives no premium '
            'access: check the setup of the provider.',

    _take(identity, access);
    return true;

  /// Gives the user what the store account of the user bought, such as on a
  /// new device, and completes with the access of the user then. That access

  Future<AppAccess> restore() => _call((service, identity) async {
    final access = await service.restore();

    return access;

  /// Stops following the service, the user and the lifecycle of the app. A
  /// call that is on its way still ends as it would have, but tells no
  /// listener. A start or a look at the access that waits for its turn does
  /// nothing then.
  @override

    _disposed = true;
    unawaited(_accessChanges?.cancel());
    _userChanges?.removeListener(_onUserChange);
    if (_observer case final observer?) {
      WidgetsBinding.instance.removeObserver(observer);
    }
    super.dispose();
  }

  Future<void> _start(
    PurchasesService service,
    String? Function()? userId,
    Listenable? userChanges,
  ) async {
    if (_starting) {
      await _turn(() => _use(service, userId, userChanges));
    } else {
      _starting = true;
      await _use(service, userId, userChanges);
      _started = true;
      _untilStarted?.complete();
    }
    await _settled();
  }

  /// Takes [service] as the service of the controller, with the user of
  /// [userId], and looks at the user and at the access, unless the
  /// controller was disposed of while the start waited for its turn.
  Future<void> _use(
    PurchasesService service,
    String? Function()? userId,
    Listenable? userChanges,
  ) async {
    if (_disposed) return;
    unawaited(_accessChanges?.cancel());
    _userChanges?.removeListener(_onUserChange);
    _service = service;
    _userId = userId;
    _userChanges = userChanges?..addListener(_onUserChange);
    _identified = null;
    _set(const NoAccess());
    _accessChanges = service.accessChanges.listen(
      (access) => _onAccessChange(service, access),
      onError: _report,
    );
    if (_observer == null) {
      final observer = _observer = _ResumeObserver(_lookLater);
      WidgetsBinding.instance.addObserver(observer);
    }
    await _quietly(_look);
  }

  /// Completes once no call is on its way, and none was made in the
  /// microtask after the last one ended.
  Future<void> _settled() async {
    while (true) {
      final last = _lastCall;
      if (last != null) {
        await last;
        continue;
      }
      await Future<void>.microtask(() {});
      if (_lastCall == null) return;
    }
  }

  /// Runs [call] with the service and the user of the app, once the calls
  /// made before it are over, and turns whatever it throws that is no
  /// [PurchasesFailure] into one.
  Future<T> _call<T>(
    Future<T> Function(PurchasesService service, _Identity identity) call,
  ) => _turn(() async {
    try {
      final service = _service!;
      final before = _identified;
      final identity = await _identify(service);
      // A call that identified the user again, as after an
      // identification that failed, is followed by a look at the access
      // of the user.
      if (identity != before) _lookLater();
      return await call(service, identity);
    } on PurchasesFailure {
      rethrow;
    } on Object catch (error, stackTrace) {
      Error.throwWithStackTrace(
        PurchasesFailure(
          PurchasesFailureReason.unknown,
          developerHint: '$error',
        ),
        stackTrace,
      );
    }
  });

  /// Runs [job] once the calls made before it are over, and not before the
  /// controller has started for the first time.
  Future<T> _turn<T>(Future<T> Function() job) async {
    final earlier =
        _lastCall ??
        (_started ? null : (_untilStarted ??= Completer<void>()).future);
    final done = Completer<void>();
    final own = _lastCall = done.future;
    if (earlier != null) await earlier;
    try {
      return await job();
    } finally {
      if (identical(_lastCall, own)) _lastCall = null;
      done.complete();
    }
  }

  /// Identifies the user of the app with [service], unless [service] has
  /// that user already, and returns the identity.
  Future<_Identity> _identify(PurchasesService service) async {
    final user = _userId?.call();
    final identified = _identified;
    if (identified != null &&
        identical(identified.service, service) &&
        identified.user == user) {
      return identified;
    }
    // Until the identification succeeds, the service has no user that the
    // controller knows of, and the user has no access.
    _identified = null;
    _set(const NoAccess());
    await service.identify(user);
    final identity = (service: service, user: user);
    if (identical(service, _service)) _identified = identity;
    return identity;
  }

  /// Identifies the user, and takes the access of that user, unless the
  /// controller was disposed of while the look waited for its turn.
  Future<void> _look() async {
    if (_disposed) return;
    final service = _service!;
    final identity = await _identify(service);
    _take(identity, await service.access());
  }

  /// Looks at the user and at the access in its turn, unless a look waits
  /// for its turn already.
  void _lookLater() {
    if (_lookWaits || _disposed) return;
    _lookWaits = true;
    unawaited(
      _turn(() {
        _lookWaits = false;
        return _quietly(_look);
      }),
    );
  }

  /// The user of the app may have changed. If it has, [value] is [NoAccess]
  /// until the service has the new user.
  void _onUserChange() {
    final identified = _identified;
    if (identified != null && identified.user == _userId?.call()) return;
    _set(const NoAccess());
    _lookLater();
  }

  /// Takes [access], which [service] told of, while [service] has the user
  /// of the app.
  void _onAccessChange(PurchasesService service, AppAccess access) {
    final identified = _identified;
    if (identified != null && identical(identified.service, service)) {
      _take(identified, access);
    }
  }

  /// Takes [access], the answer of the service of [identity], as [value],
  /// while the controller has that service and the service has the user of
  /// [identity], who is still the user of the app. The answer for a user
  /// who is no longer the user of the app changes nothing.
  void _take(_Identity identity, AppAccess access) {

    if (identified != null &&
        identical(identified.service, identity.service) &&
        identical(identity.service, _service) &&
        identified.user == identity.user &&
        identity.user == _userId?.call()) {
      _set(access);
    }
  }

  /// Takes [access] as [value], and tells the listeners when that changes
  /// it, unless the controller was disposed of.
  void _set(AppAccess access) {
    if (_disposed || access == _access) return;
    _access = access;
    notifyListeners();
  }

  /// Runs [job], whose errors no caller sees, and reports what it throws.
  Future<void> _quietly(Future<void> Function() job) async {
    try {
      await job();
    } on Object catch (error, stackTrace) {
      _report(error, stackTrace);
    }
  }

  /// Reports [error], which no caller sees.
  void _report(Object error, StackTrace stackTrace) {
    switch (error) {
      case PurchasesFailure(
        reason: PurchasesFailureReason.notConfigured,
        :final developerHint,
      ):

            PurchasesFailureReason.storeProblem,

      default:
        Zone.current.handleUncaughtError(error, stackTrace);
    }
  }
}

/// the store keep them.

/// uses `appPurchases` of `app_purchases.dart`, which calls this service and
/// does what is the same with every provider.
///
/// Every implementation keeps to this:
/// - The function that creates the service creates it without a user, asks
///   the user nothing, and never throws. It may be called again, and the
///   service that it returns then has what the store and the provider kept.
/// - [identify] comes before any other call, so a provider can set itself up
///   with the user. Each call is for the user that [identify] last gave.
/// - `identify(null)` makes the user of this device the user whose
///   purchases count. When it follows another user, also one of an earlier
///   launch of the app, it starts a new user of this device, with nothing
///   bought: what a user of the device had before comes back only through
///   [restore].
/// - When the user of this device is identified as a user that no
///   [identify] named before, on any device, that user takes over the
///   purchases of the user of this device, who no longer has them. So a
///   purchase before a sign-up stays with the new account.
/// - Any other [identify] keeps the purchases of each user apart.
/// - [restore] gives the user what the store account bought, and may move
///   purchases from another user to this one, as the backend of the
///   provider decides. So no test relies on a restore that moves them, or on
///   one that leaves them.
/// - [access] completes from what the device keeps, without the network
///   when it keeps anything.
/// - A call fails only with a [PurchasesFailure]. Without what it needs,
///   such as a key, the service fails every call with

///   [PurchasesFailure.developerHint] that names what is missing, and it
///   never stops the app.

  /// app.

  /// with nothing bought. The user of this device identified as a user that
  /// no call named before, on any device, takes over the purchases of the
  /// user of this device. Identifying the user who is identified already
  /// does nothing and does not fail, `null` too.
  Future<void> identify(String? userId);

  /// The access of the user, from what the device keeps, without the
  /// network when it keeps anything.
  Future<AppAccess> access();

  /// Tells of each change of the access of the user that the provider
  /// learns of, such as a renewal, an expiry, or a grant made elsewhere: a
  /// broadcast stream. It may also tell of an access that has not changed.
  Stream<AppAccess> get accessChanges;

  /// The plans of the current offer of the app, at least one, in the order
  /// of the provider. With nothing to offer, it fails with
  /// [PurchasesFailureReason.notConfigured] and a hint.
  Future<List<Plan>> plans();

}

  Future<void> _answer(PushService service) async {

      }

    }

  /// or body counts as none.
  void _onMessage(PushMessage message) {

      'body': message.body,
      'data': message.data,

          // the place of the one that showed it before rather than adding
          // another, and a negative one, so it never takes the place of a
          // notification of the app.
          id: -1 - (json.hashCode & 0x7FFFFFFF),

          title: text,
          body: title == null ? null : body,
          data: {
            ...message.data,
            notificationOwnerKey: _owner,
            _messageKey: json,
          },
        ),
      ),
    );
  }

  /// [text], or `null` if it is empty.
  static String? _textOf(String? text) =>
      text == null || text.isEmpty ? null : text;

  /// The message that [data], the data of a notification that showed a
  /// message, keeps under [_messageKey], or a message with the rest of the
  /// data if the notification lost it.
  static PushMessage _messageIn(Map<String, String> data) =>
      switch (_decoded(data[_messageKey])) {

          'title': final String? title,
          'body': final String? body,

          PushMessage(
            id: id,
            title: title,
            body: body,
            data: Map<String, String>.from(values),
          ),
        _ => PushMessage(
          data: {
            for (final MapEntry(:key, :value) in data.entries)
              if (key != notificationOwnerKey && key != _messageKey) key: value,
          },
        ),
      };

  /// What the JSON [text] holds, or `null` for no text or one that is no
  /// JSON.
  static Object? _decoded(String? text) {
    if (text == null) return null;
    try {
      return jsonDecode(text);
    } on FormatException {
      return null;
    }
  }

  /// - [ShowInstead] of the target of the gate that keeps the user from the
  ///   location (see [redirectOf]). The location is then remembered in place of
  ///   the one before it, so the user comes back to the latest one that
  ///   they or the platform asked for, whether or not that gate brings the
  ///   user back (see [RouteGuard.resumes]). A location in the flow of a
  ///   guard is never remembered: once that guard allows, its flow is over.
  /// - [ShowInstead] of [start] for a location in a flow that is over (see
  ///   [flowIsOver]).
  /// - for a location that a guard with [RouteGuard.routes] keeps the user
  ///   from: [ShowNothing] while a page of the flow of that guard is among
  ///   [onTopOf], on top or below another page, since the flow is open
  ///   already; and else [ShowOver] of the target of the guard, with its
  ///   flow.
  /// - for a location that no guard keeps the user from and that is asked
  ///   for with no pages, in a flow that only guards with
  ///   [RouteGuard.routes] keep open: [ShowOver] of the location itself,
  ///   with that flow. So a page of such a flow never stands alone when a
  ///   link asks for it: the router shows it over [start], and back leads
  ///   into the app. The request that waits is the page itself: asked
  ///   about again once the flow closes, it is answered with [start],
  ///   where the user is then. A flow that a gate keeps open too is the
  ///   gate's, and takes the place of the stack.
  ///
  /// For a guard with routes the class remembers no location, only over
  /// how many pages its flow was opened, for [changed]. So the answer
  /// depends on [onTopOf] and not on what the class answered before. Asked
  /// again about a location that it answered [ShowOver] for, with a page of
  /// the flow among [onTopOf], it answers [ShowNothing] for a location that
  /// the guard keeps the user from and `null` for a page of the flow. With
  /// no pages it answers [ShowOver] again, so a router never asks with none
  /// about a location that it shows over a page.
  ///
  /// What a gate made the class remember is forgotten when no gate keeps
  /// the user from the location and it is outside every flow, or in one
  /// that is over: the user has moved on, as when the code of the app
  /// navigates right when a gate starts allowing. Before that, it is
  /// forgotten if a guard that does not bring the user back stopped
  /// allowing, as [changed] says.
  WhenAsked<L>? asked(
    String? route,
    L location, {
    required Iterable<String?> onTopOf,
  }) {
    _forgetAfterStop();

    if (guard != null && guard.routes == null) {
      if (!_inAFlow(route)) _remembered = (route: route, location: location);
      return ShowInstead(locationOf(guard.redirectTo));
    }
    final over = flowIsOver(route);
    if (over || !_inAFlow(route)) _remembered = null;
    if (over) return ShowInstead(start);
    if (guard == null) {
      final flow = onTopOf.isEmpty ? _openFlowOf(route) : null;
      if (flow == null) return null;
      _below = 0;
      return ShowOver(location, flow: flow);
    }
    if (onTopOf.any(guard.flow.contains)) return const ShowNothing();
    _below = onTopOf.length;
    return ShowOver(locationOf(guard.redirectTo), flow: guard.flow);
  }

  /// What the router does now that a guard started or stopped allowing, or
  /// `null` to leave its pages as they are. With `null` the router changes
  /// nothing: its pages stay, and so do the routes without a page that code
  /// pushed over them, such as a dialog or the screen that the action of an
  /// onboarding step shows.
  ///
  /// [pages] are the pages that the user can get back to, the one on top
  /// first: those of the root navigator and of the selected branch of the
  /// main navigation, each with the full name of its route, its location,
  /// and whether the router can close it on its own and leave the pages
  /// below it as they are. That holds for a page that `push()` showed, and
  /// for one that `replace()` showed in place of such a page. There are
  /// none for a router that has no page yet.
  ///
  /// First, the remembered location is forgotten if a guard that does not
  /// bring the user back (see [RouteGuard.resumes]) stopped allowing: it
  /// allowed when the class was last asked or told, and does not now. That
  /// holds whichever guard decides and whatever the pages are, and for
  /// whichever gate the location was remembered, so that the next user
  /// does not come to a location of the last one. A guard that stops and
  /// allows again without the class being asked or told in between is not
  /// seen to stop.
  ///
  /// The answer is then the first of these:
  /// - [ShowInstead] of the target of the gate that keeps the user from one
  ///   of the pages. If that gate brings the user back, the location below
  ///   the pages that the router can close is then remembered, or [start]
  ///   if it can close them all, unless one is remembered already or it is
  ///   in the flow of a guard.
  /// - with a location remembered: `null` while a gate keeps the user from
  ///   it. Otherwise the location is forgotten, and the answer is
  ///   [ShowInstead] of it, or of [start] if a guard with
  ///   [RouteGuard.routes] keeps the user from it: the class cannot keep a
  ///   request waiting, so the user moves on to [start].
  /// - for the lowest page that has to leave, which is in a flow that is
  ///   over (see [flowIsOver]) or which a guard with [RouteGuard.routes] keeps
  ///   the user from: [ClosePages] of that page and the pages over it, if the
  ///   router can close each of them and a page stays below; and else
  ///   [ShowInstead] of [start]. The request that waits is dropped when the
  ///   pages that close reach below the flow that [asked] opened last: the
  ///   page that the request was made on closes then, as when it asks for
  ///   a condition that stopped holding while the flow of another one was
  ///   open over it.
  ///
  /// So the pages of a flow close once its guards allow, also below a page
  /// that was pushed from them, and a page that asks for a condition
  /// closes when the condition stops holding. A page that took the place
  /// of the stack, as after `go()` to it, has nothing below it: the user
  /// then comes to [start].
  ///
  /// A known limit of the second answer: a location that a guard with
  /// [RouteGuard.routes] keeps the user from, and that was asked for
  /// behind a gate, is lost once the gate allows. A link to such a route
  /// that opens the app on a first launch, behind an onboarding, leaves
  /// the user on [start], though [asked] opens the flow of the guard over
  /// [start] for the same link when no gate is in its way.
  WhenChanged<L>? changed(
    Iterable<({String? route, L location, bool pushed})> pages,
  ) {
    _forgetAfterStop();
    final all = pages.toList();
    for (final page in all) {
      final gate = _guardKeepingFrom(page.route);
      if (gate == null || gate.routes != null) continue;
      final below = all.where((other) => !other.pushed).firstOrNull;
      if (gate.resumes && _remembered == null && !_inAFlow(below?.route)) {
        _remembered = (
          route: below?.route,
          location: below == null ? start : below.location,
        );
      }
      return ShowInstead(locationOf(gate.redirectTo));
    }
    if (_remembered case final remembered?) {
      final guard = _guardKeepingFrom(remembered.route);
      // The pages are those of the flow of the gate, which is not over.
      if (guard != null && guard.routes == null) return null;
      _remembered = null;
      return ShowInstead(guard == null ? remembered.location : start);
    }
    // No gate keeps the user from a page, so a guard that does is one with
    // routes.
    final lowest = all.lastIndexWhere(
      (page) => flowIsOver(page.route) || _guardKeepingFrom(page.route) != null,
    );
    if (lowest < 0) return null;
    final closed = lowest + 1;
    return all.take(closed).every((page) => page.pushed) && closed < all.length
        ? ClosePages(closed, dropsRequest: all.length - closed < _below)
        : ShowInstead(start);
  }

  /// Forgets the remembered location if a guard that does not bring the
  /// user back stopped allowing since the class last looked at the guards,
  /// and notes which of those guards allow now.
  void _forgetAfterStop() {
    for (final guard in routeGuards) {
      if (guard.resumes) continue;
      if (guard.allows.value) {
        _allowed.add(guard);
      } else if (_allowed.remove(guard)) {
        _remembered = null;
      }
    }
  }

  /// Whether [route] is in the flow of a guard, of whichever guard.
  static bool _inAFlow(String? route) =>
      routeGuards.any((guard) => guard.flow.contains(route));

  /// The flow that [route] is a page of and that only guards with
  /// [RouteGuard.routes] keep open: that of the first guard that does not
  /// allow and has the route in its flow; or `null` if there is none, or if
  /// a gate that does not allow has the route in its flow too, since the
  /// flow of a gate takes the place of the stack.
  static Set<String>? _openFlowOf(String? route) {
    Set<String>? flow;
    for (final guard in routeGuards) {
      if (guard.allows.value || !guard.flow.contains(route)) continue;
      if (guard.routes == null) return null;
      flow ??= guard.flow;
    }
    return flow;
  }

    // completes with when the router makes it again, or with `null`.
    final waiting = Completer<T?>();
    if (_redirected(
      location,
      again: () => waiting.complete(push<T>(location)),
      drop: waiting.complete,
    )) {
      return waiting.future;
    }
    final branch = _branchOf(location);
    _checkMainNavigation(location, branch, 'push');
    if (branch == null) {
      _stack.add(location);
    } else if (_onMainNavigation) {
      _branches[_selected].add(location);
    } else {
      _showMainNavigation(branch, location);
    }
    final result = Completer<Object?>();
    _results[location] = result;
    notifyListeners();
    return result.future.then((value) => value as T?);
  }

  @override
  void replace(AppLocation location) {
    if (_redirected(location, again: () => replace(location))) return;
    final branch = _branchOf(location);
    _checkMainNavigation(location, branch, 'replace');
    // A page that takes the place of one that a push showed closes without
    // the pages below it too, so it is one that a push showed.
    final (_, replaced) = _top;
    if (branch != null && _onMainNavigation) {
      _branches[_selected]
        ..removeLast()
        ..add(location);
    } else {
      if (_stack.isNotEmpty) _stack.removeLast();
      if (branch == null) {
        _stack.add(location);
      } else {
        _showMainNavigation(branch, location);
      }
    }
    if (_results.containsKey(replaced)) {
      _results[location] = Completer<Object?>();
    }
    notifyListeners();
  }
}

  AppThemeModeController._();

  /// The key of the mode in the preferences, which keep it by its name.
  static const _key = 'theme.mode';

  /// The preferences that remember the mode, once the app opened them.
  AppPreferences? _preferences;

  ThemeMode _mode = ThemeMode.system;

  /// The mode of the app: [ThemeMode.system], which follows the device,
  /// unless the user selected another.
  ThemeMode get value => _mode;

  /// Chooses [mode] as the mode of the app, at once, and saves the choice:
  /// the future completes once the mode is saved. Until the app opened its

  /// it saves through the preferences that the app opened last.

      _mode = mode;
      notifyListeners();

Future<SystemUiOverlayStyle> _styleIn(
  WidgetTester tester,
  ThemeData theme,
) async {
  await tester.pumpWidget(
    MaterialApp(
      theme: theme,
      home: const StatusBarIcons(child: Text('A screen')),
    ),
  );
  return tester
      .widget<AnnotatedRegion<SystemUiOverlayStyle>>(
        find.descendant(
          of: find.byType(StatusBarIcons),
          matching: find.byType(AnnotatedRegion<SystemUiOverlayStyle>),
        ),
      )
      .value;
}
